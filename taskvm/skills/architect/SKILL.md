# 任务架构师 Skill

## 触发条件

- 当输入包含「任务目标 + 已观察状态」且需要产出完整任务架构（变量/工作流/检查点）时注入。

## 通用领域与操作先验

- **检查点是被动边界**：checkpoint 节点只标记可暂停/回退的边界，自身不产生执行事件——任何动作的 after 都不要依赖 checkpoint；序列的首个动作节点 after 必须为空（或仅依赖容器），否则整个工作流可能没有任何就绪节点、零步即停滞。
- **导航型动作不写变量**：「打开应用/进入页面」类动作只改变位置，sets 保持空（{}）；变量写入留给产生业务状态变化的动作（发送、设置、提交）。给导航步挂 Set 会让界面验证员无法在屏幕上确认该写入，动作会被反复打回。
- **写入值与变量类型严格一致**：sets 里的值必须与变量 value_type 逐字一致——number 型用数字字面量（如 30，不带引号），string 型才带引号；每个变量的最终写入值必须与其 desired 完全相等（一致性检查逐字比对，'30' 不等于 30）。
- **sets 写业务值不写过程描述**：写入值应是目标业务值本身；查询结果在运行时才可知——把查询产物建为只读变量由后续动作读取，不要把「如何获得该值」的描述文本写进 sets。
- **预算意识**：每个动作节点有固定的 GUI 步数上限；架构上优先少而完整的动作（如「进入账单列表并展示记录」一步完成），不要把同一界面目标拆成一串小步。

## 蒸馏少样本

- （L0 基线教训，匿名化）某架构把序列首个动作的 after 指向一个前置检查点，检查点不执行、动作永不就绪，整图零步停滞——教训：动作只等待动作/验证节点，检查点只作旁注。
- （L0 基线教训，匿名化）某架构给数值变量 desired=30（数字）而最终写入动作 sets '30'（字符串），多轮修复均被一致性检查拒绝——教训：类型逐字一致，数字不带引号。
- （L0 基线教训，匿名化）某架构给「进入聊天应用」的导航动作挂 Set 变量，执行代理已到达应用首页仍被判未完成、两次如实报完成被打回后升级——教训：导航步 sets 留空。
