A2UI搭配GPT实现流程
=============

【提问 轮数1】
A2UI 0.9协议搭配GPT-5.6-SOL如何实现呢？给出完整的流程，我需要在本地准备什么东西？如何渲染，模型应该返回什么呢？需要有本地素材库吗？

【回答内容 轮数1.A】
可以，而且 **A2UI 0.9 + GPT-5.6-SOL** 这套组合非常适合做“模型生成界面，但客户端不执行模型生成代码”的 Generative UI。

先把最重要的架构关系定下来：

```text
┌───────────────────────────────────────────────────────┐
│                    GPT-5.6-SOL                        │
│                                                       │
│  输入：用户意图 + 当前状态 + A2UI Catalog + 规则       │
│  输出：A2UI JSON / JSONL                              │
└───────────────────────┬───────────────────────────────┘
                        │
                        ▼
                A2UI Validator
                        │
                        ▼
               SSE / WebSocket
                        │
                        ▼
┌───────────────────────────────────────────────────────┐
│                  Local Renderer                       │
│                                                       │
│  A2UI MessageProcessor                                │
│           ↓                                           │
│  Surface / DataModel                                  │
│           ↓                                           │
│  Component Catalog                                    │
│           ↓                                           │
│  React / Angular / Lit / Flutter 原生组件              │
└───────────────────────┬───────────────────────────────┘
                        │
                    用户点击/输入
                        │
                        ▼
                 action + context
                        │
                        ▼
                  GPT-5.6-SOL
```

**模型不生成 React，不生成 HTML，不生成 JS。模型生成的就是 UI 的“声明”。**

A2UI v0.9 本身就是 JSON-based streaming UI protocol，服务端向客户端发送 `createSurface`、`updateComponents`、`updateDataModel`、`deleteSurface` 四类消息；组件结构和 Data Model 是分开的，因此后续只更新数据也不用重发整棵 UI。turn736390view0

# 一、完整流程

我建议你的实现按照下面这 10 步做。

1. **客户端启动时准备 Component Catalog。** 比如允许 GPT 使用 `Text / Image / Row / Column / Card / Button / TextField / ChoicePicker / Slider`，或者你自己的 `ProductCard / StockChart / WeatherCard`。Catalog 本质上是 **Agent 与 Renderer 之间的契约**；A2UI 官方也建议让 Catalog 直接对应你现有的 Design System。

2. **把 Catalog 描述提供给 GPT-5.6-SOL。** 后端 System/Developer Prompt 告诉模型：“你只能使用这些组件，它们有哪些属性，输出必须符合 A2UI v0.9。”A2UI 0.9 特别改成了 prompt-first 设计，即协议/schema 描述本来就是设计成可以直接放进模型上下文的。

3. **用户发送自然语言请求。** 例如：“帮我做一个创建会议的表单，需要标题、日期、参会人和确认按钮。”

4. **后端调用 OpenAI Responses API。** 使用 `model: "gpt-5.6-sol"`。GPT-5.6 Sol 当前支持 Responses API、Streaming、Function Calling 和 Structured Outputs。

5. **模型返回 A2UI JSONL。** 第一个消息通常创建 Surface；之后发组件；然后发初始 Data Model。A2UI 使用逐消息流式处理，所以 Renderer 可以 progressive render。turn736390view0

6. **服务端不要直接信任模型输出。** 每一个完整 JSON 对象先做 JSON parse，再用 A2UI `server_to_client + common_types + catalog` 做 schema validation，同时检查 component id、root、children 引用和 catalog 权限。A2UI 0.9 官方明确指出 prompt-first 的代价就是需要更强的生成后验证与纠错。turn455456view2

7. **验证成功后通过 SSE/WebSocket 发给前端。** A2UI 不限定 transport，只要求消息有序、有明确 framing；JSONL、SSE event、WebSocket frame 都可以。

8. **前端 MessageProcessor 消费消息并渲染 Surface。** 官方 Web Renderer 已有 React、Angular、Lit；Web 端共享 `@a2ui/web_core`，React 提供 `MessageProcessor`、`A2UISurface` 和 `useA2UI()`。Flutter 则可用 GenUI SDK。

9. **用户输入首先修改客户端 Data Model。** TextField、CheckBox、Slider、ChoicePicker、DateTimeInput 都支持 two-way binding；用户每敲一个字不会自动请求模型，而是先更新本地状态。

10. **Button action 再发回 Agent。** Renderer 解析 action 的 `context`，把当前输入发送给你的 Agent；Agent/GPT 根据结果返回新的 `updateComponents` 或 `updateDataModel`，页面增量变化，不必重新创建整个页面。turn449956view0

这就是完整闭环：

```text
User Prompt
   ↓
GPT
   ↓
createSurface
   ↓
updateComponents
   ↓
updateDataModel
   ↓
Renderer
   ↓
User Input
   ↓
local DataModel
   ↓
Button Action
   ↓
Backend / GPT
   ↓
updateDataModel / updateComponents
   ↓
Renderer update
```

# 三、Catalog 才是整个方案最关键的东西

很多人第一次理解 A2UI 会把 **Catalog** 和“素材库”混为一谈。

其实不是。

Catalog 更像：

```text
GPT 可使用 UI API
```

假设你告诉 GPT：

```json
{
  "components": {
    "Text": {},
    "Button": {},
    "Card": {},
    "Column": {},
    "ProductCard": {},
    "Price": {},
    "StockChart": {}
  }
}
```

Renderer 端则存在真正的实现：

```text
"Text"        → <Text />
"Button"      → <MyButton />
"Card"        → <MyCard />
"ProductCard" → <ProductCard />
"StockChart"  → <StockChart />
```

所以 GPT 输出：

```json
{
  "id": "chart",
  "component": "StockChart",
  "symbol": "AAPL",
  "period": "1M"
}
```

它**没有生成 Chart 的 JavaScript**。

你的客户端只是看到：

```text
component = StockChart
```

然后从 Registry 中找到：

```tsx
StockChart
```

再进行渲染。

这也是 A2UI 安全模型的核心：Agent 请求的是你预先允许的 trusted components，而不是下发任意代码。

# 四、模型到底应该返回什么？

比如用户说：

> 给我一个填写姓名并提交的界面。

模型理想输出不是：

```html
<form>
...
</form>
```

而应该是一串 **A2UI JSONL**：

```jsonl
{"version":"v0.9","createSurface":{"surfaceId":"profile_form","catalogId":"https://a2ui.org/specification/v0_9/catalogs/basic/catalog.json","sendDataModel":true}}
{"version":"v0.9","updateComponents":{"surfaceId":"profile_form","components":[{"id":"root","component":"Card","child":"content"},{"id":"content","component":"Column","children":["title","name","submit"]},{"id":"title","component":"Text","text":"# 创建个人资料"},{"id":"name","component":"TextField","label":"姓名","value":{"path":"/form/name"},"variant":"shortText"},{"id":"submit_text","component":"Text","text":"确认"},{"id":"submit","component":"Button","child":"submit_text","variant":"primary","action":{"event":{"name":"submitProfile","context":{"name":{"path":"/form/name"}}}}}]}}
{"version":"v0.9","updateDataModel":{"surfaceId":"profile_form","value":{"form":{"name":""}}}}
```

这个结构包含三件事情。

第一条：

```text
createSurface
```

意思是：

> Renderer，创建一个叫 profile_form 的 UI 区域。

第二条：

```text
updateComponents
```

定义：

```text
Card
 └── Column
      ├── Text
      ├── TextField
      └── Button
```

A2UI 0.9 要求 Surface 最终存在一个 `id: "root"` 的组件作为组件树根节点。

第三条：

```text
updateDataModel
```

提供：

```json
{
  "form": {
    "name": ""
  }
}
```

然后：

```json
"value": {
  "path": "/form/name"
}
```

就建立：

```text
TextField
     ⇅
DataModel.form.name
```

A2UI 的 binding 使用 JSON Pointer，并且 input component 会把输入即时写回本地 Data Model。turn736390view2

# 五、用户点“确认”之后发生什么？

上面的 Button：

```json
{
  "action": {
    "event": {
      "name": "submitProfile",
      "context": {
        "name": {
          "path": "/form/name"
        }
      }
    }
  }
}
```

假设用户输入：

```text
张三
```

Renderer 会解析 context，发给后端类似：

```json
{
  "type": "action",
  "surfaceId": "profile_form",
  "name": "submitProfile",
  "context": {
    "name": "张三"
  }
}
```

如果 `createSurface.sendDataModel = true`，客户端还可以随 action 把 Surface 的完整当前 Data Model 发给创建它的 server。

你的 Backend 可以先执行真正业务：

```text
saveProfile("张三")
```

然后再把：

```text
action result
+
current surface
+
current data model
```

交给 GPT。

GPT 不需要重新做整个 UI。

它可以只返回：

```json
{
  "version": "v0.9",
  "updateDataModel": {
    "surfaceId": "profile_form",
    "path": "/status",
    "value": "success"
  }
}
```

或者替换部分组件：

```text
Form
↓
Success Card
```

这就是 A2UI 很漂亮的地方：**UI 是 stateful、incremental 的，而不是每轮重新生成整个 HTML。** turn455456view3

# 六、GPT-5.6-SOL 这边怎么调用？

后端推荐直接使用 Responses API。GPT-5.6 Sol 当前支持 Responses API 和 streaming。turn615714view1

Node.js 最小结构：

```ts
import OpenAI from "openai";

const openai = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY
});

const stream = await openai.responses.create({
  model: "gpt-5.6-sol",

  input: [
    {
      role: "developer",
      content: A2UI_SYSTEM_PROMPT
    },
    {
      role: "user",
      content: userMessage
    }
  ],

  stream: true
});

for await (const event of stream) {
  if (event.type === "response.output_text.delta") {
    consumeA2UIDelta(event.delta);
  }
}
```

Responses streaming 会提供诸如 `response.output_text.delta` 的 typed events。turn615714view2

你的 `consumeA2UIDelta()` 不要每来几个 token 就 `JSON.parse()`。

而应该维护 buffer：

```ts
let buffer = "";

function consumeA2UIDelta(delta: string) {
  buffer += delta;

  while (buffer.includes("\n")) {
    const index = buffer.indexOf("\n");

    const line = buffer.slice(0, index).trim();
    buffer = buffer.slice(index + 1);

    if (!line) continue;

    try {
      const message = JSON.parse(line);

      validateA2UI(message);

      sendToBrowser(message);
    } catch (err) {
      // invalid A2UI
    }
  }
}
```

也就是说：

```text
OpenAI token stream
       ↓
JSONL buffer
       ↓
完整一行 JSON
       ↓
JSON.parse
       ↓
A2UI Schema Validator
       ↓
Renderer
```

而不是：

```text
GPT token
↓
直接 Renderer
```

# 七、System Prompt 应该怎么设计？

我会让 Agent Prompt 大致长这样：

```text
You are an A2UI v0.9 UI generation agent.

Your job is to translate the user's intent into A2UI protocol messages.

RULES:

1. Output A2UI JSON objects only.
2. Use JSONL: exactly one complete JSON object per line.
3. Never output Markdown fences.
4. Never output HTML, CSS, JavaScript, JSX or React code.
5. Only use components defined by the supplied catalog.
6. Every new surface must first emit createSurface.
7. Every surface must eventually contain a component with id "root".
8. Use updateDataModel for content/state changes whenever rebuilding the
   component tree is unnecessary.
9. Use JSON Pointer paths for data binding.
10. Interactive controls must bind their value to the data model.
11. Buttons should dispatch semantic action names.
12. Never invent component types or component properties.

AVAILABLE CATALOG:

<CATALOG HERE>

CURRENT SURFACES:

<CURRENT STATE HERE>
```

然后放进去：

```text
common_types
+
catalog definition
+
必要的 A2UI protocol instructions
```

这是比较符合 **A2UI 0.9 自身设计方向** 的做法，因为 v0.9 从以 Structured Outputs 为中心转成了 prompt-first，并明确要求生成后的验证。

# 八、那 GPT-5.6-SOL 明明支持 Structured Outputs，要不要用？

**可以用，但我不会把“完整原版 A2UI v0.9 schema + strict Structured Outputs”作为第一版架构。**

原因很简单。

OpenAI 的 Structured Outputs 确实能保证模型遵循所给 JSON Schema，但 strict mode 支持的是 JSON Schema 的一个子集。

而 A2UI 0.9 自己之所以转向 prompt-first，就是为了不再受 Structured Output schema 表达能力限制，支持更丰富的 Catalog/schema。

所以我建议：

```text
GPT
 │
 │ prompt-first
 ▼
A2UI JSONL
 │
 ▼
Schema validator
 │
 ├─ valid ─────────→ Renderer
 │
 └─ invalid
      ↓
   repair/retry
```

而不是一开始做：

```text
整个 A2UI schema
      ↓
OpenAI strict structured output
```

当然，如果你自己的 Catalog 很小，例如只有：

```text
Card
Text
Button
Image
Row
Column
```

那么完全可以做一个简化后的 JSON Schema，再让 GPT-5.6-SOL Structured Outputs 强约束。

# 九、Renderer 到底做什么？

Renderer 实际上就是：

```text
A2UI JSON
      ↓
MessageProcessor
      ↓
Surface state
      ↓
component.id graph
      ↓
Catalog lookup
      ↓
React Component
```

例如收到：

```json
{
  "id": "submit",
  "component": "Button",
  "variant": "primary"
}
```

Renderer 会做类似：

```ts
const Component = registry["Button"];
```

然后：

```tsx
<Component {...props} />
```

所以 Renderer 才是真正决定：

```text
圆角多少
字体多大
hover 什么效果
暗黑模式什么颜色
是否支持 animation
是否符合品牌 Design System
```

GPT 并不决定这些。

这也是为什么同样一份 A2UI JSON 可以由 React、Angular、Lit 或 Flutter Renderer 映射为各自原生 UI。turn449956view0

# 十、是否需要“本地素材库”？

**协议层面完全不需要。**

你真正需要的是：

> **本地 Component Catalog**

而不是：

> 本地图片素材库。

Basic Catalog 已经包含 `Image`、`Video`、`AudioPlayer` 这类基于 URL 的媒体组件，以及使用预定义系统图标的 `Icon`。

所以最简单可以：

```json
{
  "component": "Image",
  "src": "..."
}
```

然后 Renderer 加载 URL。

不过生产环境我会再加一层：

```text
GPT
 ↓
logical asset
 ↓
Asset Resolver
 ↓
allowlist / CDN / local assets
```

例如不要让 GPT 自己随便生成：

```text
https://random-domain.example/x.png
```

而是自定义：

```json
{
  "component": "BrandImage",
  "assetId": "product_iphone_17"
}
```

Renderer：

```ts
assetResolver("product_iphone_17")
```

得到你真正允许的资源。

这样你可以控制：

```text
品牌图片
产品图
icon
avatar
背景
CDN
授权素材
```

# 十一、我更推荐你做“领域组件”，而不是全部让 GPT 拼 Row/Column

这会直接决定最终体验。

第一版很多人会做：

```text
Text
Row
Column
Image
Button
Card
```

于是 GPT 得自己拼：

```text
Column
├── Row
│   ├── Image
│   └── Column
│       ├── Text
│       └── Text
├── Divider
└── Button
```

能用，但是模型 token 多，而且 UI 容易变化。

生产系统更适合定义：

```text
ProductCard
HotelCard
FlightCard
UserCard
StockChart
OrderSummary
PaymentMethodSelector
CalendarPicker
AddressForm
ConfirmDialog
```

于是 GPT 只需要说：

```json
{
  "id": "product",
  "component": "ProductCard",
  "productId": "123",
  "showBuyButton": true
}
```

Renderer 自己保证它长这样：

```text
┌────────────────────┐
│      Product image │
│                    │
│ MacBook Pro        │
│ ¥14,999            │
│ ★ 4.8              │
│                    │
│     [立即购买]      │
└────────────────────┘
```

A2UI 官方也明确推荐 custom catalog 尽量直接对应你自己的设计系统，而不是在通用 Catalog 和产品组件之间套很多转换层。

这套结构里，**GPT-5.6-SOL 是 Planner / UI Composer，不是 Renderer。**

A2UI 是：

```text
GPT → Renderer
```

之间的 UI IR / DSL。

Catalog 是：

```text
GPT ↔ Renderer
```

之间的 ABI / contract。

Data Model 是：

```text
UI state
```

Surface 是：

```text
一块独立、持续存在、可增量更新的 UI
```

而 Component Library 才是：

```text
真正显示给用户的 UI
```

这几个概念分开之后，整个 A2UI 就很好理解了。

**最小可用版，你本地甚至完全不需要素材库：`React + @a2ui/react + @a2ui/web_core + Basic Catalog + Node 后端 + GPT-5.6-SOL + SSE + Validator` 就可以跑起来。** 官方 React Renderer 已负责 MessageProcessor 和 Surface 渲染部分；GPT-5.6 Sol 则可以通过 Responses API 流式产生 Agent 输出。turn825560view3

# 三、最重要的东西：Catalog

你问到：

> 需要有本地素材库吗？

严格来说：

**不需要“素材库”，但必须有“组件能力库 / Catalog”的概念。**

这是两件完全不同的事情。

### Catalog

Catalog 告诉模型：

```text
你只能用：

Text
Button
Image
Card
Row
Column
TextField
Checkbox
List
Tabs
...

不能自己发明组件。
```

同时告诉 Renderer：

```text

↓
对应我的 React Button

A2UI 的 Card
↓
对应我的 DesignSystem.Card
```

这就是 A2UI 安全模型里最核心的一层：Agent 只能请求使用预先批准的组件。

官方 Basic Catalog 本身就包含 Text、Image、Icon、Row、Column、Button、TextField 等组件以及客户端函数。turn803814view4

# 四、Catalog 和“素材库”的区别

比如你的公司已经有：

```text
MyButton
MyCard
MyProductCard
MyPrice
MyAvatar
MyChart
MyMap
MyDatePicker
```

那么你可以创建自己的：

```text
https://yourcompany.com/a2ui/catalog/v1
```

模型收到的是这个 Catalog 的定义。

例如：

```json
{
  "catalogId": "https://example.com/a2ui/catalog/v1",
  "components": {
    "ProductCard": {
      "properties": {
        "title": {},
        "price": {},
        "image": {},
        "productId": {}
      }
    }
  }
}
```

而前端：

```tsx
const componentRegistry = {
  Text: A2UIText,
  Button: MyButton,
  Card: MyCard,
  ProductCard: MyProductCard
};
```

于是模型返回：

```json
{
  "id": "product1",
  "component": "ProductCard",
  "title": "MacBook Pro",
  "price": "14999",
  "image": "/assets/macbook.jpg",
  "productId": "123"
}
```

Renderer 最后执行：

```tsx
<MyProductCard
  title="MacBook Pro"
  price="14999"
  image="/assets/macbook.jpg"
/>
```

注意：

**模型没有返回 JSX。**

模型只是返回：

```json
"component": "ProductCard"
```

# 五、图片素材要不要存在本地？

不强制。

A2UI Basic Catalog 的 `Image` 接收的是一个 `url`，所以它可以指向 CDN、你自己的 API、静态资源服务等。

例如：

```json
{
  "id": "hero",
  "component": "Image",
  "url": "https://cdn.example.com/product/123.jpg",
  "description": "产品图片",
  "fit": "cover"
}
```

因此你可以采用三种模式。

### 模式 A：远程 CDN

```text
https://cdn.xxx.com/image1.webp
```

最简单。

### 模式 B：本地静态资源

```text
/assets/product-a.png
```

也没问题。

### 模式 C：素材 ID

我其实更推荐企业系统使用：

```json
{
  "component": "ProductImage",
  "assetId": "product_123_main"
}
```

本地 Renderer 自己：

```ts
assetRegistry.resolve("product_123_main")
```

得到：

```text
https://cdn.xxx.com/products/123/main.webp
```

这样 **GPT 根本不需要知道真实 URL**。

这个方式更安全，也更容易换 CDN。

所以：

```text
组件库：强烈需要
素材库：可选
Asset Registry：复杂产品推荐有
```

# 八、为什么一定有一个 `root`

在 `updateComponents` 中：

```json
{
  "id": "root",
  "component": "Column"
}
```

非常重要。

A2UI 0.9 要求 component tree 中有一个：

```text
id = "root"
```

它就是 UI 树的根。

Renderer 在收到 root 之前可以先缓存其他 component；一旦 root 出现，就可以开始 progressive rendering。

# 九、组件为什么是“平铺”的

你可能会觉得奇怪，为什么不是：

```json
{
  "Column": {
    "children": [
      {
        "Text": {}
      },
      {
        "Button": {}
      }
    ]
  }
}
```

而是：

```json
[
  {
    "id": "root",
    "component": "Column",
    "children": ["title", "button"]
  },
  {
    "id": "title",
    "component": "Text"
  },
  {
    "id": "button",
    "component": "Button"
  }
]
```

这是 A2UI 很漂亮的地方。

它是 **adjacency list**。

这样 GPT 可以分块输出：

```text
root
↓
header
↓
form
↓
buttons
↓
footer
```

不需要一次把一个巨大嵌套 JSON 闭合完。

同时修改某个组件时：

```json
{
  "updateComponents": {
    "surfaceId": "xxx",
    "components": [
      {
        "id": "submit-label",
        "component": "Text",
        "text": "提交成功"
      }
    ]
  }
}
```

就能局部更新。

这也是 A2UI 为 LLM streaming 特意做的设计。

# 十、UI 数据和 UI 结构最好分开

这是非常重要的工程实践。

不要让 GPT 每次修改温度都重新生成：

```text
Column
Text
Card
Button
...
```

应该第一次：

```text
updateComponents
```

建立 UI。

然后：

```json
{
  "version": "v0.9",
  "updateDataModel": {
    "surfaceId": "weather-001",
    "path": "/weather/temperature",
    "value": "31°C"
  }
}
```

组件：

```json
{
  "id": "temperature",
  "component": "Text",
  "text": {
    "path": "/weather/temperature"
  }
}
```

Renderer 自动重新渲染。

A2UI 的 `updateDataModel` 就是为了在不重复发送组件结构的情况下更新内容；path 使用 JSON Pointer。

```json
  "child": "submit-label",
```

# 十四、GPT-5.6 Sol 后端怎么调用

我建议直接使用 **Responses API**。OpenAI 当前也推荐新的 agent/workflow 使用 Responses API；它支持 streaming、Structured Outputs、function calling 等能力。

基础代码：

```ts
import OpenAI from "openai";

const openai = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY
});

const stream = await openai.responses.create({
  model: "gpt-5.6",

  reasoning: {
    effort: "medium"
  },

  input: [
    {
      role: "developer",
      content: A2UI_SYSTEM_PROMPT
    },
    {
      role: "user",
      content: userMessage
    }
  ],

  stream: true
});
```

GPT-5.6 Sol 这种 UI planning，大多数情况：

```text
medium
```

已经可以。

复杂 dashboard：

```text
high
```

非常复杂的业务编排才建议：

```text
xhigh / max
```

GPT-5.6 的模型文档目前支持 `none / low / medium / high / xhigh / max`。

# 十七、GPT Stream 怎么变成 A2UI Stream

OpenAI Responses API 开 streaming 后，本身也是 SSE streaming。

但是要注意：

模型可能先给你：

```text
{"vers
```

下一 chunk：

```text
ion":"v0.9"
```

下一 chunk：

```text
,...
}
```

所以**不能一个 token delta 就喂 Renderer**。

你需要一个 buffer：

```ts
let buffer = "";

for await (const event of stream) {

  if (event.type !== "response.output_text.delta") {
    continue;
  }

  buffer += event.delta;

  while (buffer.includes("\n")) {

    const index = buffer.indexOf("\n");

    const line = buffer.slice(0, index).trim();

    buffer = buffer.slice(index + 1);

    if (!line) continue;

    const message = JSON.parse(line);

    validateA2UI(message);

    sendToFrontend(message);
  }
}
```

变成：

```text
OpenAI token stream
       ↓
JSONL buffer
       ↓
完整 JSON object
       ↓
schema validation
       ↓
frontend
```

这层我通常叫：

```text
A2UI Gateway
```

# 二十二、`catalogId` 不一定真的能访问

一个很有意思的细节：

```json
"catalogId":
"https://example.com/a2ui/catalog/v1"
```

虽然长得像 URL，但 **它实际上首先是 identifier**。

不要求浏览器真的：

```http

```

官方明确说明 `catalogId` 可以使用 URI 风格避免命名冲突，但它并不要求是实际可下载地址。

所以你完全可以：

```ts
catalogRegistry.register(
  "https://mycompany.com/a2ui/v1",
  MyCompanyCatalog
);
```

# 二十三、本地 Renderer 本质上是什么

如果你不用官方 Renderer，自己做其实也是：

```ts
function renderComponent(id: string) {

  const node = surface.components.get(id);

  switch (node.component) {

    case "Text":
      return (
        <Text>
          {resolve(node.text)}
        </Text>
      );

    case "Column":
      return (
        <Column>
          {node.children.map(renderComponent)}
        </Column>
      );

    case "Button":
      return (
        <Button
          onClick={() => dispatch(node.action)}
        >
          {renderComponent(node.child)}
        </Button>
      );

    default:
      return null;
  }
}
```

真正复杂的部分不是 JSX。

而是：

```text
surface lifecycle
component buffer
JSON pointer
data binding
template lists
two-way binding
actions
function calls
validation
progressive rendering
```

这也是为什么官方建议 Web 端使用 `@a2ui/web_core`，而不是自己重新实现这一层。

L1（通用）：模型自治操作——看屏幕、点坐标。对应 Repository Contract 原则 4“Agent 在边界内持续自治”。
L2（per-app）：任务变量级的写回——对应原则 2“双向可执行性”（用户改任务变量 → Agent 写回真实应用）和原则 5“独立验证与诚实可逆性”。投影上一个变量（“这条消息发出去了吗”）需要一个确定性的、可验证、可回退的执行入口。mutate_wechat 返回的 {"status","old","new","message_id","trace"} 是给 governance 层做 checkpoint/rollback 的事务回执，纯 click 流给不出这个。
四、打个比方
L1 的 click(x,y) 是“手指”——这只手按电梯按钮、按计算器、按微信发送键，动作完全一样，全宇宙通用。
L2 的 send_message 是“快递承诺”——“把包裹送到张三家”。送完要核对签收（验证），送错了要能退回（回退）。而“签收凭证长什么样”每个 app 不一样：微信的凭证是聊天记录里多了条消息，X 的凭证是点赞标志翻转。你不能用同一张签收单核对两家快递。
所以：手指是通用的，回执单是每家自己的。 mutate_* 那 100~200 行里，大部分写的是回执单和退换货规则，不是手指动作。
五、修正后的结论（比上一轮更准确）

## 核心裁决

你最后几句话里，有一半成立，另一半需要纠正：

1. **后端确实已经有真实模型生成的任务相关结构。**
   `TaskArchitect` 会根据 goal 和观测到的 VM-state 动态生成任务变量、工作流、ActionContract、checkpoint 和一棵 projection 组件树。

2. **但它目前没有真正生成“可渲染的灵活控件”。**
   它生成的是 TaskVM 自定义的抽象 `ProjectionSchema`，模型提示里只有 `card | field | list | progress | note` 五类语义节点，而且没有 TextField、DateTimeInput、ChoicePicker、Button action 等完整控件属性。

3. **前端目前完全没有消费这棵模型生成的 projection tree。**
   浏览器仍然把所有变量统一渲染成文本输入框，并使用固定的 Workflow / Variables / Surfaces / Checkpoints / Conflicts dashboard。

4. **模型当前的生产输出不符合 A2UI v0.9。**
   它不是 `createSurface / updateComponents / updateDataModel / deleteSurface` 消息，也没有 `version`、`surfaceId`、`catalogId`、`root` 等 A2UI 协议结构。

5. **仓库里确实存在一套 A2UI v0.9 prompt、官方 schema 和 validator，但它在 `taskvm_bench` 中，没有接入生产路径，而且其中还有旧版绑定语法错误。**

所以当前最准确的定义是：

> **TaskVM 已经有“模型生成的语义任务架构”，但还没有真正完成“模型生成 A2UI → A2UI Renderer 渲染 → A2UI action 写回”的 Agentic GenUI 闭环。**

# 四、当前模型输出并不符合 A2UI

正式 A2UI v0.9/v0.9.1 的服务器输出是四类消息：

```text
createSurface
updateComponents
updateDataModel
deleteSurface
```

它把组件结构与 Data Model 分离，客户端逐条处理消息并增量渲染。官方当前把 v0.9.1 列为生产版本，而 v0.9 是上一稳定版本；二者延续相同的四消息模型。

TaskVM 当前生产输出是：

```json
{
  "projection": {
    "root": "...",
    "components": [
      {
        "label": "...",
        "type": "field",
        "binds": "release_date"
      }
    ]
  }
}
```

A2UI 应当是：

```json
{
  "version": "v0.9",
  "updateComponents": {
    "surfaceId": "taskvm-task",
    "components": [
      {
        "id": "root",
        "component": "Column",
        "children": ["release_date"]
      },
      {
        "id": "release_date",
        "component": "DateTimeInput",
        "label": "发布日期",
        "value": {
          "path": "/variables/release_date/desired"
        },
        "enableDate": true,
        "enableTime": false
      }
    ]
  }
}
```

两者不是同一种 schema。

因此：

> **不能说“模型输出已经符合 A2UI，只是前端没有 Renderer”。**

更准确的是：

> **当前模型输出具备一些与 A2UI 相似的思想，例如平铺组件、稳定 ID、结构/数据分离，但协议格式和控件语义都不是 A2UI。**

`taskvm_bench/benchmark/a2ui_schema_manager.py` 也加载了正式 schema，并提供：

# 六、你所说的“灵活度只受模型能力制约”需要稍微换一种表述

从产品目标看，你的要求是合理的：

> 任务相关 area 应由模型根据当前任务动态组成，不应该为微信、日历、转账、发消息等场景分别写模板。

但是在 A2UI 架构中，它不可能真的“完全只受模型能力限制”。

A2UI 的安全基础正是：

> 模型只能使用客户端预先批准的 Catalog 组件，而不能生成任意 HTML、CSS 或 JavaScript。

Catalog 可以是 Basic Catalog，也可以是自定义 Catalog；Renderer 将这些抽象组件映射为本地可信控件。

所以更准确的验收目标应该是：

> **UI 的任务语义、控件选择、分组方式和组件树由模型决定；Harness 只施加任务无关、应用无关的协议与 Catalog 约束。**

允许的通用约束：

```text
只能使用 Text / Card / Column / DateTimeInput / ChoicePicker / Button
必须绑定合法 task variable
必须使用允许的 action 名
必须通过 schema validation
不能生成 JS/HTML
```

不允许的场景特异硬编码：

```javascript
if (app === "wechat") renderMessageEditor();
if (goal.includes("日历")) renderDatePicker();
if (semanticKey === "release_date") renderSpecialReleaseForm();
```

判断是否真正泛化的试金石是：

> 加入一个未见任务时，是否只需要模型输出新的 A2UI component tree，而不需要修改前端代码。

# 十一、正常状态变化不应该重新调用 GPT

这点对 TaskVM 特别重要。

第一次任务创建：

```text
StateCompiler       1 次
TaskArchitect       1 次
GenUI Decoder       1 次
```

普通 GUI 执行后状态变化：

```text
StateCompiler fast-path / deterministic extraction
TaskArchitect       0 次
GenUI Decoder       0 次
updateDataModel     直接发送
```

LocalPatch：

```text
TaskArchitect       0 次
GenUI Decoder       通常 0 次
CUA                 执行修改
updateDataModel     更新
```

GoalPatch 或结构性变化：

```text
TaskArchitect       1 次
GenUI Decoder       1 次
updateComponents    更新结构
updateDataModel     更新数据
```

这正是 A2UI 把结构和数据分开的价值：普通值变化只发 `updateDataModel`，不需要重新生成整棵 UI。官方协议和 Renderer 都围绕这种增量状态管理设计。

## 结论二：当前模型输出不符合 A2UI v0.9

这是一个明确的 **否**。

A2UI v0.9 服务端消息必须是以下四种之一：

```text
createSurface
updateComponents
updateDataModel
deleteSurface
```

并带：

```json
{
  "version": "v0.9"
}
```

A2UI 把组件结构和 Data Model 分开；用户行为则以独立的客户端 action 消息返回服务器。

当前 `TaskArchitect` 输出没有：

```text
version
createSurface
updateComponents
updateDataModel
deleteSurface
surfaceId
catalogId
A2UI component 名称
action.event
JSON Pointer binding
```

所以不能说：

> 虽然还没有 A2UI Renderer，但模型已经在输出 A2UI。

更准确的说法是：

> 当前模型输出的是 TaskVM 自定义 ProjectionSchema，它和 A2UI 在“组件树+绑定”的概念上相似，但协议上完全不是 A2UI。

两者的关系类似：

```text
当前 ProjectionSchema = 内部 UI 草图 DSL
A2UI                  = 可验证、可传输、可执行的正式 UI 协议
```

```text
结构化意图
    ↓
ActionContractSerializer
    ↓
自然语言 CUA goal
    ↓
CUA 看屏幕并操作
```

而且它是确定性的，不需要再额外调用一个 LLM 来“润色一次自然语言”。

这其实是合理的。

因为：

```text
用户在日期控件里选了 2026-08-25
```

本身已经是非常明确的结构化信息，没有必要再让另一个模型猜：

> 用户到底想表达什么？

正确链路应该是：

```text
A2UI DateTimeInput
    ↓
结构化 action context
    ↓
LocalPatch
    ↓
Kernel retarget
    ↓
ActionContract
    ↓
确定性 serializer
    ↓
CUA goal
    ↓
GUI 操作
```

不应该是：

```text
A2UI 控件
    ↓
先转成一段模糊自然语言
    ↓
再让另一个模型重新理解
    ↓
再产生操作目标
```

后者会平白增加语义漂移。

A2UI 不应该替代 CUA，也不应该替代 TaskVM Kernel。

它应该替代的是：

> 当前固定的 `Task Variables` 面板，以及没有被消费的内部 ProjectionSchema 渲染层。

# “灵活度应该完全只受模型能力制约”需要稍微改写

你的核心意图是对的：

> 不应该由 TaskVM 为每个任务硬编码页面结构。

但生产系统中，灵活度也不能真的“只受模型能力制约”。

正确边界应该是：

```text
模型能力
+
受信任组件 Catalog
+
协议 Schema
+
TaskVM 权限与治理约束
```

也就是说：

> **模型应自由决定使用哪些允许的组件、如何组合、绑定什么变量、暴露什么语义操作；但不能自由生成 HTML、JavaScript、坐标操作或任意后端接口。**

A2UI 的官方设计正是这种模式：Agent 输出声明式消息，客户端只渲染受信任 Catalog 中的组件。官方 React Renderer 提供 `MessageProcessor`、Surface 渲染组件和 Catalog 扩展机制。

因此可以固定：

```text
TaskVM 顶栏
Workflow
Checkpoint
Live Phone
Verifier
Conflict panel
```

只把中间的任务 area 交给 A2UI。

这不会降低 Agentic GenUI 的成立性。

论文或系统 claim 可以是：

> 固定治理外壳中的任务相关交互面，由模型根据实时 VM-state 动态编译。

而不是必须声称：

> 整个网页的每个像素都由模型决定。

# A2UI 可以解决什么，不能解决什么

## A2UI 能解决

### 1. 任务相关控件动态生成

同一个 `due_date` 变量，模型可以输出：

```text
DateTimeInput
```

而不是固定文本框。

同一个 `assignee` 可以输出：

```text
ChoicePicker
```

一个多任务批处理可以输出：

```text
List + CheckBox + Button
```

一个转账审查任务可以输出：

```text
Card + List + Text + ChoicePicker + confirmation Button
```

### 2. 结构和数据分离

第一次：

```text
createSurface
updateComponents
updateDataModel
```

之后世界状态变化时只发：

```text
updateDataModel
```

不需要每次重新让模型生成整个页面。

这是 A2UI 的核心价值之一。

### 3. 用户操作结构化返回

A2UI v0.9 的客户端 action 包含：

```json
{
  "version": "v0.9",
  "action": {
    "name": "set_variable",
    "surfaceId": "task_surface",
    "sourceComponentId": "due_date_editor",
    "timestamp": "...",
    "context": {
      "semantic_key": "due_date",
      "value": "2026-08-25"
    }
  }
}
```

这可以直接转成：

```python
LocalPatchRequested(
    updates={"due_date": "2026-08-25"}
)
```

不需要重新自然语言理解。

### 4. 本地 Design System

同一份 A2UI：

```json
{
  "component": "Button",
  "variant": "primary"
}
```

实际可以映射成 TaskVM 自己的按钮样式。

模型不需要知道：

```text
CSS
圆角
颜色
hover
暗黑模式
响应式断点
```

---

## A2UI 不能解决

### 1. 它不会替代 CUA

A2UI 只描述 TaskVM 投影界面，不会自动点击微信、支付宝、日历。

### 2. 它不会自动解决验证和回退

A2UI Button 被点击，不代表真实世界写入成功。

仍然必须：

```text
CUA 操作
→ fresh observe
→ verifier
→ commit / repair / fail
```

### 3. 它不会自动消除 per-app 真实性问题

对于：

```text
微信消息是否真的发出
支付宝转账是否真的成功
日历事件是否真的保存
```

仍然要有可信证据。

验证器可以逐步做得更通用、更视觉化，但不能简单相信 CUA 自报成功。

### 4. 它不应该携带坐标或 app 内部操作

A2UI action 应该是：

```text
set_variable
change_goal
rollback
confirm
resolve_conflict
```

而不应该是：

```text
click_wechat_send
tap_320_840
call_mutate_wechat
```

否则又会把 GUI 层的 app 特异性泄漏到投影层。

---

# 推荐不要让现有 TaskArchitect 直接承担完整 A2UI 生成

当前 contract 把：

```text
Workflow Architect
GenUI structural decoder
```

合成了一个模型角色。

这对小型内部 schema 尚可，但一旦接完整 A2UI，会让一次输出同时承担：

```text
变量发现
workflow 拓扑
ActionContract
checkpoint
reversibility
projection component tree
data binding
action semantics
A2UI protocol合法性
```

输出会非常大，修复也会互相干扰。

更合适的拆法是两个阶段。

## 阶段 A：TaskArchitect

输入：

```text
Goal
Compiled VM-state
Committed history
```

输出：

```text
Task variables
Workflow
ActionContracts
Checkpoint semantics
Governance capabilities
```

它决定“任务是什么”。

## 阶段 B：GenUIDecoder

输入：

```text
TaskArchitecture
Current VM-state
Current workflow summary
Editable variables
Allowed governance actions
A2UI Catalog
```

输出：

```text
A2UI v0.9 messages
```

它决定“任务应该如何让人操作”。

链路：

```text
StateCompiler
    ↓
TaskArchitect
    ↓
TaskArchitecture
    ↓
GenUIDecoder
    ↓
A2UI Validator
    ↓
Renderer
```

只有以下情况需要重新调用 GenUIDecoder：

```text
首次任务创建
GoalPatch
变量集合或交互能力发生结构性变化
原 surface 无法容纳新任务结构
```

普通世界状态变化：

```text
金额变了
任务完成了
验证状态变了
进度变了
```

只发：

```text
updateDataModel
```

不产生模型调用。

这也符合当前 `projection.md` 里“普通 data delta 不重新生成 schema”的设计原则。

# “重新交付”应该分成两种情况

你提到用户“重新交付，想把这个东西转换为投影”，这里必须区分语义。

## 情况一：用户修改现有字段

例如：

> 把会议时间改成下午三点。

如果用户是在生成的时间控件里操作：

```text
DateTimeInput
→ A2UI action
→ LocalPatch
→ ActionContract
→ serializer
→ CUA
```

不需要重新调用 TaskArchitect，也不需要自然语言 Intent Model。

## 情况二：用户改变任务结构

例如：

> 不只是通知张伟，把所有参会人都通知一下，并且要求每个人回复确认。

这不是局部变量修改，而是：

```text
GoalPatch
```

正确链路：

```text
用户自然语言
    ↓
GoalPatchRequested
    ↓
TaskArchitect.recompose()
    ↓
新 workflow / variables / contracts
    ↓
GenUIDecoder
    ↓
新的 A2UI component structure
    ↓
updateComponents / updateDataModel
```

这里需要重新生成投影，因为任务本身的结构已经变了。

## 情况三：用户在 UI 里触发治理动作

例如：

```text
回退到“发送消息之前”
暂停
继续
解决冲突
创建 checkpoint
```

应由 A2UI action 直接映射到已有的 GovernanceEvent：

```text
RollbackRequested
PauseRequested
ResumeRequested
ConflictResolutionRequested
CheckpointRequested
```

也不需要让模型重新猜意图。

# 最终架构判断

你最初设想的 Agentic UI 并不是：

```text
固定 dashboard
+
模型动态填写几行字段名称
```

而应该是：

```text
真实世界状态
    ↓
StateCompiler
    ↓
Task VM-state
    ↓
TaskArchitect 生成任务语义
    ↓
GenUIDecoder 生成 A2UI
    ↓
模型选择任务相关控件和信息架构
    ↓
用户结构化修改
    ↓
Kernel 形成新的 desired state
    ↓
ActionContractSerializer 形成 CUA goal
    ↓
CUA 操作真实软件
    ↓
独立观察与验证
    ↓
A2UI updateDataModel 重投影
```

因此，对你最后一句话最准确的修正是：

> 当前 TaskVM 的 TaskArchitect 已经具备一定的任务相关结构生成能力，但只输出五种内部抽象组件；该 schema 在 workspace 启动路径中还可能被丢弃，前端也完全没有消费。当前生产模型输出不符合 A2UI v0.9，正式 A2UI prompt/validator 只存在于 benchmark 目录。要实现你最初定义的 Agentic GenUI，应该保留固定治理外壳，新增一个真正由 A2UI 驱动的动态任务区域，并把 A2UI action 接到现有 LocalPatch/GoalPatch → ActionContractSerializer → CUA 链路上。

这不是单纯“换一个 Renderer”就结束。

真正缺失的是三段：

```text
TaskArchitecture / VM-state
    → A2UI GenUI Decoder

A2UI messages
    → 浏览器 MessageProcessor / Renderer

A2UI user action
    → TaskVM Governance Action Router
```

而你担心的：

```text
结构化用户意图
→ 自然语言 CUA 指令
```

这一段其实已经由 `ActionContractSerializer` 实现了，不需要再造一层自由文本翻译 Agent。
