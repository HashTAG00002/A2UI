# 结论先行

我对 `gg-phase` 分支中的权威设计文档、GG 阶段文档，以及 `task_state`、`governance`、`execution`、`workspace_ui`、`substrate`、`verifier`、`benchmark`、`evaluation` 等关键链路做了静态代码审计。以下判断基于当前公开代码；我没有在本轮真正启动全部 App 服务、Playwright 浏览器和模型端点，因此不能把代码中的注释性结果当成我独立复现过的实验结果。

我的核心判断是：

> **TaskVM 的研究概念具有很强的 CHI 潜力，但当前 prototype 还不是一个真正闭环的开放世界 Task VM。现在最严重的问题不是 CUA 模型不够强，而是“真实 Workspace 主链路”仍然绕过了你已经实现的开放世界 compiler 和动态规划组件。**

更直白地说：

- 你已经造好了发动机、刹车、仪表盘、行车记录仪、倒车机构。
- 但真正演示时，车仍然沿着预先铺好的测试轨道走。
- `compile_binding(...)` 像一套可以现场识路的导航系统，但实际 `/seed` 启动车辆时没有使用它。
- 当前主路径直接用 `_gt_binding(fixture)` 把正确地图塞进系统，再由 scripted driver 生成预定工作流。
- 所以现在演示能证明“系统各部件能够协作”，却还不能证明“随便给一个目标和未见 App，系统能自己发现状态、生成计划并执行”。

当前权威文档已经把 TaskVM 的五个锚点定义得很准确：实时投影、双向可执行绑定、substrate independence、人类治理与 Agent 自治、独立验证与可逆性。这个理论框架本身是你最有价值的部分。turn561149view2

但是当前实现对这五个锚点的完成度大致是：

| 锚点 | 当前状态 | 我的判断 |
|---|---|---|
| 实时投影 | 有 SSE 心跳和 canonical reread | **部分完成**，但只是在已有 binding 上刷新数值，不会发现新结构、新实体、新 App |
| 双向绑定 | GenUI 编辑可转成 PatchOp，再写回 App | **部分完成**，因为真实 Workspace 使用 GT binding |
| substrate independence | 有 adapter 抽象和 held-out App | **明显不足**，运行时仍依赖每个 App 的 adapter、operator 表和内部 canonical API |
| 人类治理 + Agent 自治 | 有 start、pause、checkpoint、rollback、conflict resolve | **部分完成**，但没有真正的动态 goal redesign 和 subtree replan |
| 独立验证与可逆性 | canonical verifier、non-interference、Saga rollback 做得较完整 | **目前最强的一部分**，且能诚实表示不可逆操作 |

因此：

> **以现在代码原样提交，不能安全地把“开放世界、任意 App、任意任务的 Task VM”作为论文已经实现的核心事实。**
> **但把下面的 P0 闭环补完后，它非常可能成为一套有明显范式差异、足以支撑强 CHI 投稿的 prototype。**

# 一、现在真实的 TaskVM Harness 到底是怎么运行的

我先不讲抽象术语，用一个具体任务解释。

假设用户想做：

> “把项目发布会议从 8 月 14 日推迟到 8 月 18 日，并同步所有依赖任务的截止日期。”

## 1. 用户还没有给任务时，系统是什么状态

从当前 Workspace 主路径来看，它并不是一个真正的：

> “空白 TaskVM 桌面 → 用户随便输入一句自然语言任务”

而更像是：

> “测试任务启动器 → 选择一个已经注册的 task_id → 创建工作区”

核心入口是：

```python
seed_route()
```

它接受的是：

```json
{"task_id": "..."}
```

而不是任意 `goal`。默认任务还是 `doc_handoff`。随后：

```python
_get_fixture_and_adapters(task_id)
```

会根据这个预定义 `task_id` 找到一个 `CanonicalTaskGraph fixture`，再根据 fixture 中出现的 App 建立对应 adapters。

所以当前“用户给任务之前”的本质状态是：

- 还没有 `WorkspaceSession`。
- 还没有真正观察用户当前桌面。
- 还没有扫描用户当前打开了哪些 App。
- 还没有从屏幕中发现可操纵对象。
- 等待的是一个预注册的任务编号，而不是任意任务描述。

这是第一个必须修改的地方。

---

## 2. 用户“给出任务”之后，系统当前实际做了什么

调用链是：

```text
POST /seed
  └─ _get_fixture_and_adapters(task_id)
      └─ seed_session(fixture, adapters)
```

`seed_session(...)` 做四件主要事情。

### 第一步：重置并注入测试环境

```python
ad.reset(sid)
replay.seed_apps(fixture, adapters, sid)
```

这相当于拍电影之前，剧组先把所有道具摆到正确位置：

- Calendar 里提前放好发布会议；
- TaskBoard 里提前放好依赖任务；
- Drive、Mail 等也按 fixture 填好内容。

这对 benchmark 是合理的，因为实验必须可复现。

问题不在“有 fixture”，而在于后面真实运行路径继续使用了 fixture 的答案。

---

### 第二步：直接从 fixture 构造正确 binding

```python
binding = _gt_binding(fixture)
```

`_gt_binding(...)` 直接读取：

- `var_id`
- `app`
- `entity_id`
- `field`
- `operator`

例如直接知道：

```text
release_date
  → calendar.E1.date / move_event
  → taskboard.T1.deadline / set_deadline
  → taskboard.T2.deadline / set_deadline
```

这就相当于：

> 系统还没有看屏幕，就已经拿到了答案册，上面写着“发布会议是数据库里的 E1，要调用 move_event；两个任务是 T1/T2，要调用 set_deadline”。

当前代码也明确把它称为 mock binding，并说未来再替换为 compiler binding。

与此同时，你真正用于开放世界发现的：

```python
compile_binding(...)
```

虽然已经实现了“目标 + 可见文本/截图 → TaskBinding”，但目前没有接到 `workspace_ui/server.py` 的实际 seed 主链路上。

这是当前 prototype 最关键的断点。

---

### 第三步：用 scripted driver 生成预定工作流

`seed_session(...)` 接下来调用：

```python
drv = make_scripted_driver(fixture.task_id)
binding = _build_minimal_binding(drv.task)
events = []
while True:
    ev = drv.next_event()
    ...
sess.workflow_plan = interp.interpret_as_workflow(events, vm, task=drv.task)
```

这相当于：

> 不仅地图是预先给的，连驾驶路线也是测试脚本提前写好的。

`GovernanceInterpreter.interpret_as_workflow(...)` 并不是根据任意自然语言目标规划任务，而是把一批预先生成的 `UserBehaviorEvent` 分类成三种结构：

- `SEQUENTIAL`
- `PARALLEL`
- `LOOP`

分类规则也非常简单：

```text
有 loop_field → LOOP
一个 edit_field 且 fixture binding 跨多个 App → PARALLEL
否则 → SEQUENTIAL
```

并且判断是否跨 App 时，直接读取 `task.bindings`。

因此当前的“WorkflowPlan 动态生成”准确说是：

> **根据预定事件和 GT binding 做结构分类。**

还不是：

> **根据任意用户目标、当前屏幕状态、依赖关系、风险和验证条件动态生成语义工作流。**

---

### 第四步：可选地调用一次模型建议里程碑

在 `/seed` 中，如果 `suggest_milestones=True`，会调用：

```python
_suggest_milestones(fixture.goal)
```

它让模型根据目标提出若干里程碑。

例如：

```text
C1：确认会议已改期
C2：确认所有依赖任务已同步
C3：完成跨 App 一致性检查
```

这是一次真正的模型调用。

但目前“采纳里程碑”主要改变 UI 中的展示和 adopted 状态，没有重新生成或修改 `WorkflowPlan`。换句话说：

> 现在它更接近一个可采纳的任务清单，而不是会真正控制执行图的运行时 checkpoint。

# 二、Task VM 界面是怎么生成出来的

工作区页面通过：

```python
render_two_zone_html(sess)
```

生成。

你设计中的两个区域已经比较清晰：

## 1. 只读区

只读区展示真实 App 状态，例如：

```text
Calendar
  项目发布会议：2026-08-14

TaskBoard
  发布文案：deadline 2026-08-14
  QA 测试：deadline 2026-08-14
```

当前值通过：

```python
resync_values(...)
project_readonly(...)
```

得到。

但需要注意一个非常重要的问题：

```python
resync_values()
    → adapter.read_canonical(sid)
```

而 `read_canonical(...)` 实际调用的是各个模拟 App 的内部 HTTP API，例如 `/api/events/<sid>`，再归一化成 entity map。turn487147view0

所以当前只读区不是严格意义上的：

> “从任意现实 App 屏幕中实时编译出的状态投影”

而是：

> “从已知 App 的内部 canonical API 中读取状态，再投影到 VM”。

这对 benchmark oracle 很好，但对真实开放世界 harness 是一个重大限制。

你需要把两个概念彻底分开：

### 生产运行时状态

只能来自：

- screenshot
- accessibility tree
- 可见文本
- 可见 UI 结构
- 用户允许的公开接口

### Benchmark oracle 状态

可以来自：

- 内部数据库
- 测试 API
- hidden canonical state
- deterministic evaluator

现在这两个角色混在同一个 `StateAdapter` 里了。

---

## 2. 可写治理区

可写区可以有两种生成方式。

### 方式 A：传统 f-string 表单

系统按 binding 直接渲染输入框。

### 方式 B：真正的 GenUI decoder

当：

```python
sess.use_genui = True
```

时，调用：

```python
decode_genui(binding, values)
```

模型决定：

- 用 Card 还是 List；
- 用 TextField、ChoicePicker 还是 DateTimeInput；
- 哪些组件可编辑；
- 两个 zone 如何组织。

然后薄渲染器：

```python
render_a2ui_to_html(...)
```

把 A2UI 消息转成 HTML 表单。

这个设计方向是正确的：**模型负责界面语义组织，renderer 只负责安全渲染。**

但是当前 `_build_user_prompt(...)` 会把以下信息给 GenUI 模型：

```text
Variable: label [var_id]
app.entity_id.field
operator
```

也就是 `var_id`、`entity_id` 和 `operator` 都进入了 GenUI 模型上下文。

如果你的 GG 红线是：

> 所有参与 TaskVM 的模型都只能看到用户可见信息

那么这里是明确违规的。

如果红线只限定 CUA 模型，这仍然会削弱“substrate-independent GenUI”的论证，因为 GenUI decoder 仍依赖内部 schema，而不是纯 VM semantic state。

正确做法应该是给 GenUI：

```json
{
  "semantic_key": "release date",
  "label": "发布日期",
  "type": "date",
  "value": "2026-08-14",
  "editable": true,
  "scope": ["Calendar", "TaskBoard"],
  "effects": "Changing this will update 3 visible items"
}
```

而不是：

```text
calendar.E1.date(move_event)
taskboard.T1.deadline(set_deadline)
```

# 三、用户点击“开始执行”后发生什么

入口是：

```python
start_workflow(sid)
```

它启动一个 daemon thread，并调用：

```python
WorkflowExecutor.execute(...)
```

执行过程中通过 SSE 推送：

- lane running
- lane done
- barrier
- workflow complete



可以把 `WorkflowExecutor` 想成一个舞台监督：

- `WorkflowPlan` 是演出节目单；
- 每个 `WorkflowNode` 是一幕；
- 每个 `SubgoalInstruction` 是演员的任务；
- `dispatch(...)` 是把任务交给演员；
- verifier 是每幕结束后的验收员。

---

## 1. Sequential：线性工作流

例如：

```text
先改 Calendar
  ↓
验证 Calendar
  ↓
再改 TaskBoard T1
  ↓
验证
  ↓
再改 TaskBoard T2
  ↓
验证
```

当前 executor 会逐个 subgoal 调用：

```python
dispatch(sg.patch_ops, ...)
```

再对每一个 PatchOp 做 canonical reread，检查目标字段是否真的变成预期值。

它的优点是：

- 简单；
- 容易定位错误；
- 容易 rollback；
- 不会出现并发冲突。

缺点是：

- 慢；
- 每个 App 都重新走一遍 CUA；
- 长任务成本很高。

---

## 2. Parallel：并行工作流

逻辑上可以是：

```text
                  ┌─ Calendar 改期 ─┐
release_date ─────┼─ Task T1 改期 ──┼─ verifier barrier
                  └─ Task T2 改期 ──┘
```

API executor 模式下，代码使用 `ThreadPoolExecutor`，可以真正并发。

但 GUI agent 模式下，所有 App 共用一个 resident Playwright page，`GuiExecutor` 还有一把 lock，因此所谓并行实际上会串行执行：

```text
Calendar → T1 → T2
```

只是工作流结构上保留了 parallel node 和最终 barrier。turn775421view0

所以论文里必须诚实地区分：

- **logical parallelism**
- **physical execution parallelism**

当前只有前者。

要得到真正并行，需要：

- 每条 lane 独立 browser context/page；
- 每个 App 独立 CUA execution context；
- verifier barrier 汇合；
- 对共享资源做冲突检测。

---

## 3. Loop：循环工作流

当前 LOOP 的实现不是“模型根据状态判断是否继续”，而是：

1. 事件里预先带有 `loop_values`；
2. 取一个 template PatchOp；
3. 依次把其中的 `entity_id` 替换为 T1、T2、T3；
4. 每次执行后独立验证。

例如：

```text
for entity_id in [T1, T2, T3]:
    set assignee = Bob
    verify
```

这叫：

> **有限集合迭代**

还不是一个完整的 agentic loop。

真正需要支持的 loop 至少包括：

### 固定集合循环

```text
对当前发现的所有逾期任务执行一次
```

### 条件循环

```text
不断处理下一页，直到没有下一页
```

### 修复循环

```text
执行 → 验证失败 → 重观察 → 修正 → 再验证
```

### 持续监控循环

```text
只要外部状态发生变化，就更新 VM 投影和受影响计划
```

当前实现主要覆盖第一种。

# 五、到底有几个模型角色，调用多少次

先区分一个概念：

> **模型角色数量，不等于物理模型数量。**

你完全可以用同一个 frontier model 承担多个角色，但从系统设计上，它们是独立上下文、独立职责。

当前代码里实际出现了六类可能的模型角色。

| 模型角色 | 作用 | 当前主路径是否使用 |
|---|---|---|
| Binding Compiler | 从目标和屏幕发现变量、实体和绑定 | **没有接到 Workspace 主路径** |
| Milestone Suggester | 初始化时建议检查点 | 默认使用一次 |
| Workflow/Subgoal Generator | 把 PatchOp 写成 CUA 可理解的目标语言 | 存在，但当前有重复与 flag 问题 |
| GenUI Decoder | 根据 VM state 生成 A2UI | 可选 |

| Rollback NL Generator | 描述 rollback 会撤销什么 | 某些 GovernanceInterpreter 路径可选 |

# 六、用户不操作时，系统怎么运行

这一部分当前实现比较清楚。

浏览器会连接：

```python
/<sid>/poll
```

这是一个 SSE stream。

每隔 5 秒，服务器：

```python
resync_with_conflicts(
    sess.binding,
    sess.last_projection,
    sess.adapters,
    sid
)
```

也就是：

1. 重新读 canonical state；
2. 和上一次投影比较；
3. 如果外部 App 被修改，发 `conflict`；
4. 如果没有变化，发 `ok`；
5. 同时转发 workflow progress。



## 模型是否会一直调用

通常不会。

当用户不操作、世界状态也没有变化时：

- 每 5 秒调用 adapter；
- 不调用 CUA；
- 不调用 planner；
- 不调用 compiler；
- 不调用 GenUI。

这点是合理的。

但它当前只做：

> **value-level reconciliation**

也就是检查已有 binding 中的值是否变化。

它不会做：

- 新 App 发现；
- 新实体发现；
- 旧实体消失；
- UI schema 变化；
- 原有 visible locator 失效；
- binding confidence 下降；
- 计划依赖关系改变；
- 自动重新 compile binding。

所以它现在更像：

> “拿着旧地图每五秒查看几个固定地址有没有变”

而不是：

> “持续观察世界，并在地图结构变化时重绘地图”。

理想 idle loop 应该是：

```text
cheap observer heartbeat
  ↓
计算视觉/可访问性结构指纹
  ↓
没有结构变化：只更新 data model
  ↓
有局部结构变化：incremental rebind
  ↓
binding 受影响：invalidate 对应 plan nodes
  ↓
局部 replan
  ↓
更新只读区和工作流图
```

并且绝大多数 heartbeat 不应调用模型。

# 七、用户动态干预时，现在会发生什么

## 1. 用户暂停

调用：

```python
/<sid>/pause
```

它只是设置：

```python
sess.paused = True
```

`WorkflowExecutor` 只在每个 node 开始前检查。

因此：

- 当前 node 会继续完成；
- 当前 GUI gesture sequence 不会被中断；
- 下一个 node 不再执行。

turn297382view3

这是诚实而安全的初版设计，但 UX 上必须写成：

> “安全暂停：完成当前动作后暂停”

不能显示成“立即停止”。

未来可以增加两级暂停：

### Soft pause

当前 node 完成后暂停。

### Emergency stop

在 CUA 每一步 action 后检查 cancellation token；不再执行下一次点击或输入。

不可逆动作，例如最后一个“发送”“购买”“提交”，应在执行前单独检查。

---

## 2. 用户修改一个字段

例如在 GenUI 中把发布日期改成 8 月 18 日：

```text
POST /<sid>/edit
  ↓
compile_patch(edit, sess.binding)
  ↓
多个 PatchOp
  ↓
WorkflowExecutor / dispatch
  ↓
App 写入
  ↓
重新投影
```

这是你双向绑定最核心的实现。

但它依赖的仍然是 session 里已经存在的 binding。当前这个 binding 来自 GT fixture，而不是当前屏幕。

所以目前它证明的是：

> 给定正确 binding 后，用户编辑 VM variable 可以 fan-out 到多个 App。

还没证明：

> 系统能够在任意 App 中自主发现这个 binding。

---

## 3. 用户回退到 checkpoint

回退流程的核心不是让 LLM“猜怎么撤销”，而是：

```text
checkpoint_id
  ↓
VMStateSnapshot.sagas_after_checkpoint(...)
  ↓
找出 checkpoint 后发生的 sagas
  ↓
LIFO 顺序执行 RollbackLog.undo_saga(...)
  ↓
每个 inverse op 重新通过 adapter.mutate(...)
```

turn297382view3

这个设计非常好。

可以把它理解成银行流水：

- 每次跨 App 修改是一笔 saga；
- 每个 checkpoint 是一个结算点；
- 回到 C1，就是把 C1 之后的流水按倒序冲正；
- 某笔流水不能冲正，就明确标记 partial failure，而不是假装成功。

尤其 WeChat 发消息这种不可逆操作，当前代码会诚实返回失败，不用 hidden `set_state` 伪造撤回。

这是一项可以强化成论文贡献的设计：

> **TaskVM 的 rollback 不是 UI 动画，也不是历史快照伪恢复，而是经过真实执行路径的补偿性重执行。**

---

## 4. 用户要求重新设计最终目标

例如任务进行一半时，用户说：

> “不再推迟到 18 日了，改成 20 日；而且不要同步已经完成的任务。”

当前系统没有完整支持。

原因是：

- 没有真正的 arbitrary goal update route；
- `Replanner` 是 `NotImplementedError` stub；
- `set_milestone` 的多步推进仍标注为 future；
- adopted milestone 没有重写执行图；
- `WorkflowPlan` 是 seed 时一次生成的；
- 没有 subtree invalidation 和 dependency-aware replan。

所以现在用户能做的是：

- pause；
- 手动编辑已有 variable；
- rollback；
- resolve conflict；
- adopt 一个展示型 milestone。

但不能真正做到：

> “保留已验证的历史，修改最终目标，只重规划受影响的未来部分，然后继续。”

这恰恰应该成为 TaskVM 相比普通 CUA 的核心差异。

# 八、线性、树状和 Loop：当前到底支持到什么程度

## 1. 线性

当前支持较完整：

```text
A → verify → B → verify → C → verify
```

优点：

- 可解释；
- 易回退；
- 易显示 checkpoint；
- 易统计成功率。

适合：

- 有严格依赖的任务；
- 高风险任务；
- 同一个 App 内的连续操作。

---

## 2. 当前所谓 Parallel，不等于树状工作流

现在的 parallel 是：

```text
一个节点里有多个并行 subgoals，最后一个 barrier 汇合
```

它缺少真正树状工作流需要的：

- 条件分支；
- choice node；
- fallback branch；
- exception branch；
- nested branches；
- 分支级 checkpoint；
- 分支级 rollback；
- dynamic branch creation；
- 只重规划一棵子树。

因此严格地说：

> 当前支持“fan-out/fan-in”，还不支持完整 tree 或 DAG。

---

## 3. 当前 Loop 是预枚举循环

当前 loop 依赖预先给出的 `loop_values`，而不是 runtime condition。

真正的 TaskVM 工作流应该统一成一个图，而不是把 linear、tree、loop 当三个互不关联的模式。

建议的统一节点类型是：

```text
ActionNode
VerifyNode
ChoiceNode
ParallelNode
BarrierNode
LoopNode
HumanDecisionNode
CheckpointNode
CompensationNode
TerminalNode
```

其中：

- 线性是图的一条链；
- 树状是 Choice/Parallel 产生的分支；
- loop 是有回边的子图；
- rollback 是沿 Compensation edge 反向执行；
- user intervention 是插入一个 HumanDecisionNode；
- replan 是替换尚未 commit 的子图。

这会让你的系统论述从：

> “我们支持三种流程”

上升到：

> “TaskVM 提供了一个可验证、可重写、可补偿的任务控制流运行时。”

后者更像真正的 VM，也更有 CHI 范式贡献感。

---

# 九、它现在能不能面对未见 App、未见任务、任意平台

## 模型侧限制是什么

当上述 harness 闭环后，剩下的以下问题才可以合理归因于模型：

- 看不懂一个复杂的新 UI；
- grounding 点错；
- 不知道某个专业软件的操作知识；
- 长程任务丢失上下文；
- 对模糊目标判断错误；
- 无法发现隐藏在多层菜单中的入口。

真正好的论文实验应该能区分：

```text
失败是因为 compiler 没发现绑定？
失败是因为 planner 生成错依赖？
失败是因为 CUA grounding 错？
失败是因为 App 没有对应操作？
失败是因为 verifier 判断错？
失败是因为 rollback 不可行？
```

现在不少失败会被 `_gt_binding` 和预设 plan 隐藏，因此还不能做到这种归因。

# 十、与同类工作相比，你的差异到底够不够强

我认为**理论差异是够强的**，但必须把实现补到与理论一致。

## 相比 ALLOY

ALLOY 的重点是：

- 用户示范程序化偏好；
- 从 demonstration 生成可复用 workflow；
- 可视化、编辑和泛化程序流程。



TaskVM 可以与它拉开的差异是：

> ALLOY 主要让用户编辑“过程”；TaskVM 让用户操纵“跨 App 的 live task state”，系统再把状态变化编译为过程。

一句话：

```text
ALLOY：procedure-first
TaskVM：state-first
```

这是有价值的差异。

---

## 相比 Morae

Morae 的重点是：

- 自动识别关键决策点；
- 主动暂停；
- 让用户在多种选择中表达偏好；
- 保护 user agency。



TaskVM 可以更进一步：

- 不只是在选择点暂停；
- 用户可以在任意时候直接重写目标状态；
- 用户可以 rollback 到任意 checkpoint；
- 用户修改的是持续存在的 task representation，而不是一次问答。

但前提是你真的实现 dynamic replan。否则目前 Morae 在“什么时候暂停、为什么需要用户”的闭环反而更完整。

---

## 相比 AgentLens

AgentLens 的重点是根据任务情境在：

- Full UI
- Partial UI
- GenUI

三种视觉交互方式中动态切换，并强调后台执行与 just-in-time awareness。

TaskVM 的差异不应写成“我们也有 GenUI”，而应该写成：

> GenUI 在 TaskVM 中不是展示层，而是一个可执行的、双向绑定的任务状态控制面。

也就是：

```text
AgentLens：适应性地展示 Agent 正在做什么
TaskVM：让用户通过生成式状态界面改变 Agent 接下来必须实现什么
```

这个差异是强的。

---

## 相比 OSWorld / AndroidWorld 类工作

OSWorld 提供真实桌面环境和 execution-based evaluation；AndroidWorld 强调动态参数化任务、可复现 initialization、success checking 和 teardown。

到 2026 年，OSWorld 2.0 已经把重点推进到超长程真实工作流，任务规模远高于早期几十步 GUI 操作。

因此你的 benchmark 不应该试图和它们比“App 数量最多”，而应该回答它们没有直接回答的问题：

> **在同一个 CUA 模型能力下，TaskVM harness 是否因为状态投影、独立验证、用户可控 checkpoint、局部 replan 和跨 App binding，而获得更高的成功率、更低的恢复成本和更少的人类操作？**

这才是 HCI + systems 的合理交叉点。

# 十一、当前 prototype 达到 CHI 或 Award 水平了吗

## 作为概念：有 Award 潜力

我认为以下组合有范式贡献潜力：

```text
live task-state projection
+ executable two-way binding
+ user-editable task state
+ autonomous cross-app execution
+ independent verification
+ checkpoint-level rollback
+ dynamic human intervention
```

它不是普通 CUA，不是普通 GenUI，也不是普通 workflow editor。

---

## 作为当前实现：还没有达到 Award-grade prototype

主要原因不是 UI 不够漂亮，而是：

### 1. 核心 claim 与真实主链路不一致

文档说 bottom-up compile，真实 Workspace 用 GT binding。

### 2. 没有任意目标入口

用户不是在真实界面输入任意任务。

### 3. 没有真正 goal-to-workflow planner

当前只有 scripted events + rule classifier。

### 4. 没有 replanner

用户改变目标时无法保留历史并局部修改未来。

### 5. Runtime 与 benchmark oracle 混合

真实投影依赖内部 canonical API。

### 6. 所谓 open-world 证据过窄

新 operator 不等于未见 App × 未见任务 × GUI execution。

### 7. 模型调用预算没有系统级控制

理论上一个多 PatchOp 任务可能达到数百次 CUA prediction attempts。

### 8. Benchmark 还没有达到文档承诺的规模

生成器注释说 40 templates / 800 instances，但当前实际 `TEMPLATES` 只有四类。turn671903view3

因此我的评价是：

> **现在是一套研究方向很强、模块工程相当丰富、已经超过普通 paper demo 的 prototype scaffold；但还不是能够经受 Award-level reviewer 对核心 claim 逐链路追问的 artifact。**

这不是否定。恰恰相反，你现在距离真正强的系统差的不是“再堆十个功能”，而是把几个已有模块接成一条不能绕过的主链路。

---

# 十二、我建议的全新 TaskVM 工作流

建议把整个系统重新定义为一个：

> **Event-sourced、incrementally compiled、verification-gated Task Runtime**

核心循环如下：

```text
OBSERVE
  ↓
COMPILE STATE
  ↓
PLAN CONTROL GRAPH
  ↓
PROJECT TASK UI
  ↓
EXECUTE ONE COMMIT UNIT
  ↓
VERIFY
  ↓
COMMIT / REPAIR / ESCALATE
  ↓
REPROJECT
```

## 阶段 1：初始化

用户界面初始只显示：

```text
你希望完成什么？
[自然语言任务输入框]

在哪些环境中执行？
[当前桌面] [浏览器标签页] [手机] [选择窗口]
```

用户输入目标后：

### 第一次模型调用：State/Binding Compiler

输入：

- 用户目标；
- 当前可见窗口截图；
- accessibility visible text；
- App/window names；
- 不含内部 ID 和 operator registry。

输出：

```json
{
  "variables": [
    {
      "semantic_key": "release_date",
      "label": "发布日期",
      "type": "date",
      "current_value": "2026-08-14",
      "evidence": [
        {
          "surface": "Calendar",
          "visible_locator": "项目发布会议",
          "field_label": "日期",
          "confidence": 0.94
        },
        {
          "surface": "TaskBoard",
          "visible_locator": "发布文案",
          "field_label": "截止日期",
          "confidence": 0.89
        }
      ]
    }
  ]
}
```

注意：这里不要要求 compiler 立刻生成 `move_event` 或 `entity_id`。

它首先应该发现：

> 哪些可见状态代表同一个任务变量。

---

### 第二次模型调用：Goal Planner

输入：

- 用户目标；
- compiled task state；
- observed affordances；
- reversibility/risk metadata。

输出一个语义 DAG：

```text
C0 初始状态
  ↓
N1 修改发布会议日期
  ├─ N2 同步发布文案 deadline
  └─ N3 同步 QA deadline
       ↓
B1 全部验证
       ↓
C1 跨 App 日期一致
```

Planner 只负责：

- 依赖；
- 分支；
- checkpoint；
- loop termination；
- verification intent；
- 不可逆边界。

它不负责每一步坐标操作。

---

### 第三次模型调用：GenUI Decoder

输入的是去除内部实现细节后的 Semantic Task State。

生成：

- 只读区；
- 用户可编辑目标区；
- checkpoint timeline；
- dependency preview；
- risk indicators；
- “修改此字段将影响 3 个 App”的影响说明。

之后只有结构变化才重新调用。

---

## 阶段 2：自主执行循环

系统每次只执行一个 **commit unit**：

```text
选取 ready node
  ↓
生成/复用 goal-level instruction
  ↓
CUA 执行
  ↓
独立观察验证
  ↓
成功：commit + checkpoint
失败：局部 repair
高不确定性：请求用户
不可逆：显式确认
```

关键是不要让整个任务一口气成为一个黑箱长 trajectory。

---

## 阶段 3：人类不干预时

```text
Observer heartbeat
  ↓
没有结构变化
    → deterministic data update
  ↓
当前节点完成
    → verifier
  ↓
成功
    → 自动选择下一个 ready node
  ↓
直至 terminal node
```

用户能看到：

- 当前正在实现哪个目标；
- 哪个 App 正在执行；
- 已完成哪些 checkpoint；
- 哪些结果已经 verified；
- 哪些只是 Agent 自己认为 done；
- 总模型调用预算还剩多少。

---

## 阶段 4：用户干预时

所有干预统一转换成 `GovernanceEvent`：

```text
PauseRequested
GoalPatched
VariableEdited
CheckpointRollbackRequested
BranchDisabled
BranchAdded
ConflictResolved
ExecutionModeChanged
ResumeRequested
```

处理方式统一：

```text
记录事件
  ↓
计算哪些已 commit 状态仍然有效
  ↓
找出受影响的未完成子图
  ↓
invalidate 受影响节点
  ↓
必要时增量重编译 binding
  ↓
只重规划受影响子树
  ↓
更新 GenUI
  ↓
用户 resume 或系统自动继续
```

---

# 十三、怎样让用户觉得更有控制感、玩乐感和成就感

不要把“玩乐感”简单做成积分和动画。TaskVM 更适合提供一种：

> “我正在操纵一个活的任务世界，而不是观看机器人乱点屏幕”

的感受。

建议保留你已经有的 milestone celebration，但增加四个层次。

## 1. 可见因果关系

用户编辑发布日期时，先预览：

```text
这次修改将影响：
✓ Calendar：项目发布会议
✓ TaskBoard：发布文案
✓ TaskBoard：QA 测试

预计 3 个写操作
预计 18–30 个 GUI actions
全部可回退
```

---

## 2. Verified progress，而不是 Agent 自报 progress

节点状态区分：

```text
○ waiting
◐ executing
◉ agent says done
✓ independently verified
! conflict
↶ rolled back
🔒 irreversible
```

只有 verifier 通过后才庆祝。

---

## 3. 用户能够修改未来，而不是不断纠正过去

在 timeline 上允许：

- 拖动 checkpoint；
- 禁用一个 branch；
- 改写目标值；
- 增加一个终结条件；
- 让某条 lane “先不要执行”。

这会显著区别于传统 CUA 的 pause/continue 模式。

---

## 4. Earned autonomy

系统根据实际可靠性逐渐减少打扰：

```text
首次执行此类操作：执行前预览
连续 5 次验证成功：自动执行，可随时撤回
高风险或不可逆：永远确认
发现 UI 漂移：恢复预览模式
```

这比固定的“每步确认”或“永远全自动”更符合人类治理。

---

# 十四、如何把模型调用开销压下来

建议设立任务级硬预算，而不仅是 `max_steps`。

例如：

```text
Compiler：最多 2 次
Planner：初始化 1 次，单次干预最多 1 次
GenUI：初始化 1 次，结构变化最多 2 次
CUA：每 commit unit 最多 12 次
Repair：每 node 最多 1 次
整个任务：最多 60 次模型调用
```

达到预算时进入：

```text
budget exhausted → pause → 给用户展示已完成状态和失败原因
```

具体优化如下。

## 1. 删除重复 SubgoalGenerator 调用

修复 `mock_subgoal` flag。

并让：

```python
SubgoalInstruction.natural_language
```

真正传入：

```python
adapter.mutate(..., instruction=...)
```

不要在 `gui_write` 内再次生成。

---

## 2. GenUI 只生成结构一次

只读数值变化使用：

```text
updateDataModel
```

而不是重新 decoder。

---

## 3. 让 CUA 执行语义 macro

例如模型第一次发现：

```text
list row → View → Edit → field → Review → Confirm
```

后，存为带视觉锚点的 action macro。

后续相似实体先尝试 macro，失败才退回模型。

这不是硬编码 operator，而是从已验证轨迹中学习 affordance pattern。

---

## 4. 失败后不要从头重走

保留：

- 当前 screenshot；
- 当前 URL；
- 对话框状态；
- 已完成 action history；
- 最近一次 verifier discrepancy。

Repair prompt 应该是：

> “字段值仍为 8/14；当前已在 Review dialog；请完成剩余步骤。”

而不是重新给完整任务。

---

## 5. 用 uncertainty gate 控制调用

只有以下情况才调用 planner/compiler：

- structure fingerprint 变化；
- visible locator 消失；
- verifier 发现意外 diff；
- CUA 连续两步无进展；
- 用户修改终结目标；
- 出现多个同等合理选择。

---

# 十五、Benchmark 当前的优点和问题

## 当前已经做得好的部分

你们的 benchmark 有几项明显强于一般 prototype：

- hidden canonical graph；
- expected diff；
- non-interference set；
- independent verifier；
- negative-control no-op/wrong-target；
- rollback fidelity；
- OOD reskin；
- model backend ablation；
- token/call accounting；
- API mode 和 GUI mode 分离。

这些都是值得保留的。

---

## 问题一：Full-loop 仍使用 GT binding

`run_full_loop_killtest.py` 自己明确说明：

> seed_session 使用 `_gt_binding`，这个测试只验证 UI → edit → dispatch → verify，不测试 binding discovery。



所以它不是 claim-level full loop。

真正 full loop 必须是：

```text
goal
→ screen observation
→ compile_binding
→ plan
→ GenUI
→ human/UISim edit
→ GUI execution
→ independent verify
→ reproject
```

全程不允许 `_gt_binding`。

---

## 问题二：Open-world 测试不够 open

当前主要验证一个新 `update_rsvp` operator，而且使用已知 Calendar App 和注册过的 operator mapping。turn487147view0

需要至少四种 holdout：

| Split | 训练/开发阶段未见什么 |
|---|---|
| Task holdout | 新自然语言任务组合 |
| App holdout | 新 App UI 和 affordances |
| Operation holdout | 新字段或新操作方式 |
| Cross-product holdout | 已见 App 与已见任务概念的全新组合 |

最重要的是：

> App holdout 的 runtime harness 不可以有该 App 的 adapter/operator mapping。

Evaluator 可以有 oracle adapter，但 harness 不可以导入它。

---

## 问题三：当前 800 instances 主要是实例数量，不是结构多样性

当前 generator 实际只有四个 template families：

- date move cross-app
- file move
- mail state change
- outlook date move

turn671903view3

把四个 template 各随机生成 200 次，不等于 800 个独立任务结构。

Reviewer 会认为这是 parameter variation，不是 task diversity。

至少需要 20–40 个结构模板，覆盖：

- create
- edit
- delete
- move
- copy
- search
- filter
- aggregate
- compare
- send
- schedule
- conditional choice
- multi-page navigation
- loop over result set
- cross-app dependency
- conflict resolution
- irreversible action
- partial failure
- permission denied
- external state drift。

---

## 问题四：Interaction compression 是分析模型，不是实测 baseline

当前计算：

```text
baseline_actions
= n_apps navigates
+ 3 × n_bindings
```

这是一个理论下界，不是用户或 baseline agent 的真实 action trace。

可以保留为 analytical lower bound，但论文主表应该实测：

- 人类 native-app 路径；
- direct CUA；
- planner + CUA；
- TaskVM；
- TaskVM without editable projection；
- TaskVM without rollback/replan。

---

## 问题五：Non-interference 还需要字段级检查

当前有些测试只检查 unrelated entity 是否完全不变。

但如果目标实体是 M1，任务只想改 `state`，Agent 同时误改了 M1 的 `priority`，只检查 M2 不变可能抓不到。

OOD fixture 注释也承认这类字段级 non-interference 尚未完整覆盖。

应同时检查：

```text
entity-level unrelated set
field-level allowed diff mask
cross-app allowed diff mask
temporal side effects
```

# 十六、建议的新 Benchmark 架构

建议分成三个层次。

## Layer A：组件能力

用于快速定位失败，不作为最终 headline。

### A1 Binding compilation

指标：

```text
variable precision / recall / F1
entity grounding accuracy
field grounding accuracy
cross-app binding F1
confidence calibration
```

### A2 Workflow planning

指标：

```text
node precision / recall
dependency-edge F1
checkpoint quality
branch correctness
loop termination correctness
risk classification
```

### A3 GenUI

指标：

```text
semantic coverage
editable/read-only correctness
action wiring fidelity
schema validity
structural stability
```

### A4 Execution

指标：

```text
GUI action success
steps per successful mutation
grounding error rate
stuck-loop rate
```

### A5 Verification/Rollback

指标：

```text
false positive rate
false negative rate
rollback success
rollback fidelity
partial-failure detection
```

---

## Layer B：真正 End-to-End

所有任务必须从自然语言目标开始。

主要指标：

### Task Success Rate

最终目标是否完成。

### Round-trip Correctness

目标字段正确、非目标状态未损坏、VM 已重投影。

### Open-world Generalization Gap

```text
ID success − OOD success
```

分别报告：

- task holdout；
- app holdout；
- operation holdout；
- cross-product holdout。

### Substrate Invariance

同一语义任务换 UI skin 后：

```text
成功率差异
binding F1 差异
调用次数差异
执行轨迹差异
```

轨迹应该不同，但语义结果应该相同。

### Cost

```text
model calls
vision calls
input/output tokens
wall-clock latency
p50 / p90 / p95
GUI actions
repair count
```

你们当前 `CostModel` 明确把 token 当预算记录而非研究指标；对于这篇工作，我建议把 cost 正式升级为研究指标，因为 interaction compression 和 harness efficiency 本来就是你的贡献之一。

---

## Layer C：治理与恢复 Benchmark

这是最能和普通 GUI agent benchmark 拉开差距的一层。

设计自动注入事件：

### C1 外部冲突

Agent 执行期间，另一个进程修改同一字段。

测量：

```text
conflict detection recall
detection latency
silent overwrite rate
reconciliation success
```

### C2 用户中途改目标

在第 k 个 node 后注入：

```text
GoalPatched(old=8/18, new=8/20)
```

测量：

```text
already-completed work reused
nodes invalidated
replan calls
extra GUI actions
final success
```

### C3 Rollback

随机选择 checkpoint 回退。

测量：

```text
rollback success
state fidelity
unavoidable irreversibility correctly surfaced
```

### C4 Pause

随机时刻 pause。

测量：

```text
pause latency
actions after pause request
irreversible actions after pause
resume success
```

### C5 UI drift

运行过程中：

- 改按钮文字；
- 改布局；
- 增加 distractor；
- 移动目标对象；
- 分页；
- 弹窗。

测量：

```text
rebind success
recovery calls
wrong-target rate
```

### C6 Partial failure

一条 parallel lane 失败。

测量：

```text
successful branches preserved
failed branch isolated
replan quality
rollback scope
```

# 十七、必须包含的 Baselines 和 Ablations

建议最少有：

| 系统 | 作用 |
|---|---|
| Direct CUA | 证明纯模型能力 |
| Planner + CUA | 证明不是单纯多一个 planner |
| TaskVM with GT binding | oracle upper bound |
| TaskVM full | 主系统 |
| TaskVM – live projection | 验证状态投影价值 |
| TaskVM – independent verifier | 验证 verifier 价值 |
| TaskVM – rollback/replan | 验证治理价值 |
| TaskVM – GenUI | 验证生成界面是否必要 |
| TaskVM static workflow | 对比 dynamic graph |
| TaskVM API executor | 分离 harness logic 与 CUA grounding 能力 |

最重要的对照是：

```text
同一个 CUA 模型
同一个任务环境
只改变 harness
```

这样才能回答：

> 性能提升到底是 TaskVM harness 带来的，还是换了更强模型带来的。

# 十八、接下来 prototype 的具体代码修改顺序

## P0：不做完就不能声称开放世界

### P0-1：重写 `/seed`

从：

```python
{"task_id": "..."}
```

改成：

```python
{
  "goal": "...",
  "surfaces": [...],
  "execution_policy": {...}
}
```

fixture seed 只能由 benchmark orchestrator 调用，不能成为生产 Workspace API 的语义。

---

### P0-2：把 `compile_binding(...)` 接进真实主路径

真实链路必须变成：

```text
capture_obs
→ compile_binding
→ binding validation
→ WorkspaceSession
```

`_gt_binding(...)` 只允许在：

```text
tests/
evaluation oracle upper bound
```

使用。

最好加一个静态 killtest：

```text
workspace_ui/
governance/
execution/
不得 import fixture.bindings 或 _gt_binding
```

---

### P0-3：拆开 Runtime Adapter 与 Oracle Adapter

建议变成：

```text
RuntimeSurface
  observe_visible()
  act_gui()

BenchmarkOracle
  reset()
  seed()
  read_hidden_state()
  evaluate()
```

生产 harness 永远不能调用 `BenchmarkOracle.read_hidden_state()`。

当前 `StateAdapter` 同时承担两类职责，必须拆开。

---

### P0-4：实现真正 Goal Planner

替换：

```python
make_scripted_driver(...)
interpret_as_workflow(prewritten_events)
```

为：

```python
plan_goal(goal, observed_task_state)
```

输出统一的 DAG。

scripted driver 只用于 benchmark 注入用户事件。

---

### P0-5：实现 `Replanner`

接口建议：

```python
replan(
    old_plan,
    committed_nodes,
    current_observed_state,
    governance_event,
    verifier_discrepancies
) -> PlanPatch
```

输出不是整个新 plan，而是：

```text
nodes_to_keep
nodes_to_invalidate
nodes_to_add
edges_to_rewrite
new_checkpoints
```

---

### P0-6：修复 Subgoal 单一真源

- 修复 `mock_subgoal` 布尔值；
- planner 只生成一次自然语言目标；
- `WorkflowExecutor` 把该 instruction 传给 adapter；
- `gui_write` 不再自行重复生成；
- 所有模型调用都纳入同一个 task-level CostLedger。

---

### P0-7：清理所有 model-facing hidden identifiers

至少检查：

- GenUI prompt 中的 `var_id/entity_id/operator`；
- rollback NL prompt 中的 `entity_id/operator/saga_id`；
- loop natural language 中附加的 `(entity=...)`；
- debug history 中的 `row_event`、`row_task`；
- compiler 输出是否被回送给其他模型。

`GovernanceInterpreter._infer_rollback_nl(...)` 当前会把 `entity_id`、`operator`、`saga_id` 发给模型；这和“所有模型只看可见信息”的强版本红线不一致。

---

## P1：把 prototype 变成真正 Task VM

### P1-1：Event Store

记录：

```text
ObservationEvent
BindingCompiled
PlanCreated
ActionDispatched
ActionObserved
VerificationPassed
VerificationFailed
CheckpointCommitted
GovernanceEvent
RollbackApplied
ConflictDetected
```

这样：

- UI 能重放历史；
- rollback 可审计；
- benchmark 能统计每个阶段；
- replan 能知道哪些状态已 commit。

---

### P1-2：Incremental compiler

不要每五秒重新看完整世界。

维护：

```text
surface fingerprint
entity locator signature
binding confidence
last observed version
```

只对变化区域重新 compile。

---

### P1-3：真正的 Tree/DAG/Loop runtime

增加：

- condition；
- fallback；
- nested parallel；
- barrier；
- bounded loop；
- verifier-directed repair edge；
- human decision edge。

---

### P1-4：任务级预算管理

例如：

```python
TaskBudget(
    max_model_calls=60,
    max_vision_calls=45,
    max_replans=3,
    max_repairs_per_node=1,
    max_wall_clock_s=600
)
```

一旦接近预算，系统应调整策略，而不是继续盲点。

# 最后的总体评价

你们现在最应该避免的是继续横向增加更多 App、更多 operator、更多 fixture，然后把数量当成泛化。

真正应该做的是纵向打通这一条不可绕过的链：

```text
任意目标
→ 可见观察
→ 动态 binding
→ 动态 DAG
→ executable GenUI
→ GUI execution
→ independent verification
→ event-sourced checkpoint
→ human intervention
→ incremental replan
→ rollback
```

当前 prototype 最有价值的部分不是某个单独模型，也不是 A2UI renderer，而是以下组合：

> **用户操纵的是跨 App 的任务状态；Agent 负责把状态差异编译成行动；Verifier 决定现实是否真的追上了目标；Checkpoint 和 Replanner 让用户可以修改时间线，而不只是暂停一个黑箱 Agent。**

这确实有机会成为一种与 ALLOY、Morae、AgentLens 和普通 CUA 都不同的交互范式。

但当前版本的最准确评价是：

> **概念已经接近 Award ambition，工程模块已经具备强论文 prototype 的骨架；真实主链路仍停留在 benchmark-scripted 闭环。完成上述 P0 后，它才会从“设计得像 Task VM”变成“实际上就是 Task VM”。**

# 1.3 `entity_id` 是什么？

这里我要非常明确：

**当前代码里的 `entity_id` 不是 TaskVM 自己随便编的 cache ID。**

它就是 App 内部实体的数据库 primary key。

代码注释直接写着：

```python
entity_id: DB primary key, not on screen
```

例如：

```text
Calendar:
E1

TaskBoard:
T1

Drive:
F1

Mail:
M1
```

`EntityBinding` 当前结构是：

```python
EntityBinding(
    var_id,
    app,
    field,
    operator,
    entity_id,
    locator
)
```

其中设计意图是模型产生：

```text
locator = "标题为项目发布会议的会议"
```

然后 harness 再把 locator 翻译成：

```text
entity_id = E1
```

后面 PatchOp 和 adapter 都继续使用 E1。

### 那它算不算违规？

要分两层。

**按当前 GG 红线字面定义：**

只要 `entity_id` 不进入模型 prompt，它存在于 harness control plane，可以不算红线违规。

**但按你现在提出的更严格原则：**

> “真实手机/真实 App 拿不到的东西，不应成为 runtime 必需品。”

那么：

> **当前 runtime 对 `entity_id` 的依赖是不合格的。**

因为真机上你根本未必有一个 E1 可以查。

所以我建议改成真正的 TaskVM-owned cache handle。

例如：

```python
SurfaceHandle(
    id="h17",
    surface="calendar-window",
    role="listitem",
    visible_name="项目发布会议",
    nearby_text="8月14日 10:00",
    bbox=(...),
    fingerprint="...",
    last_seen_version=37
)
```

这里 `h17` 是 TaskVM 自己生成的。

它没有任何 App 内部含义。

它只是：

> “我刚才在这块屏幕上认识的这个东西，我给它贴个便利贴叫 h17。”

这就非常适合你说的 **cache 降模型调用成本**。

只要页面没发生明显结构改变：

```text
“项目发布会议”
→ h17
→ 上次在哪里
→ 周围有什么文字
```

都可以复用。

不用每次再问 Binding Compiler：

> “这个会议在哪里？”

一旦：

- 元素消失；
- 名称冲突；
- 页面重排；
- fingerprint 不匹配；

再 invalidate `h17`，重新调用 compiler。

**这个 cache 我非常支持。**

```text
TaskBoard 的任务 deadline
```

用户把它改成：

```text
8月20日
```

`compile_patch(...)` 会生成：

```text
PatchOp 1:
Calendar 那个会议
date → 8月20日

PatchOp 2:
TaskBoard 那个任务
deadline → 8月20日
```

所以：

> **PatchOp ≠ 鼠标动作。**
>
> **PatchOp ≠ subgoal。**
>
> **PatchOp ≠ 一次大模型调用。**

它只是：

> “现实世界里有一个字段应该发生这样的语义变化。”

代码本身也是这么定义的：

```python
@dataclass
class PatchOp:
    app
    entity_id
    field
    operator
    value
```

而 `compile_patch()` 本身是**纯 deterministic Python，0 次模型调用**。

## 当前一张 PatchOp 后面发生什么？

当前理想链路可以画成：

```text
PatchOp
  ↓
SubgoalGenerator
  ↓
一句给 CUA 听的人话
  ↓
GuiExecutor
  ↓
CUA 看截图
  ↓
click/type/scroll
  ↓
继续截图
  ↓
```

比如 PatchOp：

```text

```

SubgoalGenerator 可能翻译成：

> 在 Calendar 中找到“项目发布会议”，打开编辑界面，将日期修改为 8 月 20 日并确认。

然后 CUA 才开始操作。

## 当前一次 PatchOp 会产生多少模型调用？

### 第 0 步：`compile_patch`

```text
0 次模型调用
```

---

### 第 1 步：SubgoalGenerator

如果走 LLM 模式：

```text
2 次
```

因为当前代码故意生成两个 candidate，然后自己选一个。

我认为这个设计应该删掉，后面第 3 点解释。

### 第 2 步：CUA

假设完成这个修改用了：

```text

click edit
click date
```

可能是 6 次 CUA prediction。

因为 CUA 每一次都：

```text

```

所以粗略就是：

```text

```

当然也可能模型调用失败，没有产生合法 action，那就只增加 attempt、不增加 step。

### 第 3 步：verifier


真正贵的是 `k`，不是 PatchOp 本身。

# 2.1 `canonical` 到底是什么意思？

这个词本身没有神秘 AI 含义。

**canonical = 统一格式、标准形式。**

比如三个 App 各自的数据长这样：

```text
Calendar:
{
    eid: E1,
    date: 8/20
}

TaskBoard:
{
    tid: T1,
    deadline: 8/20
}

Drive:
{
    fid: F1,
    publish_date: 8/20
}
```

TaskVM 把它们统统翻译成：

```python
{
    "entities": {
        "...": {
            "field": value
        }
    }
}
```

这就是 canonical representation。

可以理解成：

> 三个地方的人讲四川话、上海话、广东话；canonical state 就是大家都翻成普通话之后的账本。

问题不是 canonical 这个概念。

**问题是现在 canonical state 从哪里来。**

当前：

```python
read_canonical()
    → requests.get("/api/events/...")
```

也就是直接读模拟 App 内部 API。

因此我建议以后名字都直接区别开：

```text
RuntimeObservedState
    真人也有可能获得的信息

BenchmarkOracleState
    实验环境内部 GT
```

不要两个都叫 canonical，不然很容易混。

# 2.2 `_mutate_via_gui → gui_write → GuiExecutor.execute` 一层层到底干嘛？

这三个名字确实容易把人绕晕。

我用“老板—领班—司机”解释。

---

### `_mutate_via_gui(...)`

这是 **Adapter 层的老板**。


4. 如果失败，再试；
5. 最后返回 old/new/trace。

现在具体是：

```text

↓

↓

↓

失败
```

并没有把：

传下去。

也就是说现在有一个很明显的架构裂缝：


# 3.1 PatchOp 什么时候会重新产生？绝对不只有 rollback

而且我建议把它明确做成三类 Patch。

这样学术叙述也很干净。

## A. Local/Subgoal Patch

**不改变最终目标和工作流拓扑。**

例如：

> 原来计划把会议改到 18 日，执行到 Calendar 时用户说“Calendar 先改成下午 4 点。”

或者：

> conflict 出现，用户选择“用 TaskVM 的值覆盖”。

这属于：

```text
LocalPatch
```

只调整现有路径上的局部动作。

通常：

```text
不 replan
不重新生成 milestone
```

---

## B. Goal Patch

改变：

- 终结状态；
- scope；
- constraint；
- workflow topology。

例如：

> “不要 18 日了，整体目标改成 20 日，而且已经完成的任务不要动。”

这应该：

```text
GoalPatch
↓
Task Architect
↓
重新生成受影响 milestones
↓
重新组织 workflow
↓
重新生成受影响 projection
```

这是你第 10 点说的东西，我非常赞同。

---

## C. Compensation Patch

就是 rollback。

例如：

```text
8/20 → 回到 8/14
```

它不是新目标，而是：

> “让现实回到某个历史 commit state。”

所以：

```text
CompensationPatch
```

---

如果再要一个但不增加主要概念，可以有：

```text
Rebind Patch
```

页面漂移导致原来 h17 失效，重新找到对应 visible object。

但我不建议把它写成论文主概念。

**论文就讲 LocalPatch / GoalPatch / CompensationPatch 三种，已经有厚度，而且非常整齐。**

# 6. `max_steps=18`、`max_attempts=54`、外层重试 3 次分别是什么？

这个非常容易混。

举个例子。

## `steps`

代表：

> CUA 真正给出了合法动作，而且 Playwright 真执行了。

比如：

```text
step 1 click
step 2 click
step 3 type
step 4 press Enter
```

最多：

```text
18 个真实动作
```

---

## `attempts`

代表：

> “我向模型问了一次下一步是什么。”

有时候你问模型：

```text
下一步干嘛？
```

结果：

- 429；
- timeout；
- JSON 不合法；
- 无法 parse。

这一次：

```text
attempt += 1
```

但 Playwright 什么都没做：

```text
step 不加
```

所以代码设置：

```python
max_attempts = max_steps * 3
```

18 steps → 最多 54 次 model prediction attempts。代码注释也明确说 attempts 是为了防止 429/parse fail 无限重试。

---

## `_mutate_via_gui` 的 3 次是什么？

这是更外面的一整轮“重新做这个 PatchOp”。

例如第一轮：

```text
CUA 操作了 8 步
↓
自认为 done
↓
Verifier 看
↓
实际上日期还是 8/14
```

那么整个 GUI execution 判失败。

于是：

```text
Attempt 1：完整 GUI execution
失败

Attempt 2：再完整 GUI execution
失败

Attempt 3：最后再来一次
```

代码是：

```python
GUI_WRITE_RETRIES = 2
for attempt in range(1, GUI_WRITE_RETRIES + 2)
```

= 初始 1 次 + retry 2 次。

所以是三层：

```text
PatchOp
└─ full execution attempt × 最多3
      └─ CUA model attempt × 最多54
            └─ 成功 parse 的最多18个成为真正 GUI step
```

所以我之前说理论极端：

```text
3 × 54 = 162
```

没错。

但这是极端 protection bound，不代表正常情况真的 162。

最终我会把预算重新设计得更紧：

```text
每 PatchOp:
max_actions ≈ 10–12
max_invalid_predictions ≈ 3–5
max_full_repair = 1
```

不要三级都给 3 倍富余。

# 7. SSE 是什么？它和 Flask / CSS / Playwright 是什么关系？

把整个系统想象成一个剧院。

## Flask = 剧院后台

它负责：

```text
网页路由
session
TaskVM state
start/pause/edit
```

比如：

```text
/start
/pause
/edit
/poll
```

---

## HTML/CSS = 舞台布景

HTML 决定：

> 这里有一个日期框、这里有一个 timeline。

CSS 决定：

> 日期框长什么样，checkpoint 是蓝的还是红的。

CSS 没有智能。

---

## JavaScript = 舞台上的工作人员

它可以：

- 用户点按钮后发请求；
- 收到状态变化后更新 DOM；
- 播放动画。

---

## SSE = 后台给前台开的“单向广播电台”

全称：

> Server-Sent Events

普通 HTTP 像：

```text
前端：有消息吗？
后台：没有。
连接断掉。

5秒后：
前端：有消息吗？
后台：有。
```

SSE 是：

```text
前端：我打开一个长连接，之后你有事直接广播给我。

后台：
……workflow step finished
→ 发一条

……conflict
→ 发一条

……checkpoint reached
→ 发一条
```

浏览器里：


# 9. Saga 是什么意思？Rollback 到底有没有模型？有没有快照后门？

## Saga 这个词来自分布式系统

普通数据库 transaction：

```text
BEGIN

A
B
C

全部成功 → COMMIT
任一个失败 → 全部 ROLLBACK
```

但是：

```text
Calendar
TaskBoard
WeChat
```

三个真实 App 没有共享一个数据库事务。

你不能说：

> “Calendar 和微信一起 transaction rollback。”

所以有一种经典思想：

> 一串独立的外部操作，每一步记录一个“补偿动作”。如果后面要撤销，就反向一个一个补偿。

这个就叫 **Saga**。

在 UI 上不用出现 Saga 这个词。

可以显示：

> “一次跨应用操作”

内部工程里叫 saga 没问题。

# 9.1 当前 `undo_saga()` 是不是直接恢复 snapshot？

Calendar / TaskBoard / Drive 这条主路径：

**不是。**

它保存：

```text
before
after
```

例如：

```text

8/14 → 8/20
```

rollback：

```text
8/20 → 8/14
```

然后代码：

```python
ad.mutate(
    entity,
    same_operator,
    before_value
)
```

而不是：

```python
database.restore(snapshot)
```

`undo_saga()` 本身也不调用一个专门“想逆动作”的 LLM。

它只是把 compensation operation 重新交给正常 `mutate()`。

```text
↓

↓
_mutate_via_gui
↓

真实点击
```

所以真的会让 CUA 在界面上：

> 找到原来的字段，再设置回旧值。

因为 API executor 还存在：


时 rollback 还是可能直接 API 写回。

因此现在不能说：

只能说：

# 12. Award-grade prototype 和“刹车”怎么同时做到？

我现在会把 Award-grade prototype 的必须项压缩成**六个东西**。

5. **真正的 projection runtime**：Persistent `ProjectionStore`；数值改变 0 次 GenUI 调用；结构失效才 incremental compile / recomposition。

6. **硬 benchmark**：同模型 direct-CUA vs TaskVM，测 success、cost、interaction compression、recovery、goal-change、rollback、open-world holdout。

这六个做完，我会非常愿意叫它：

# 这次审计得到的关键结论

## 1. 当前最大问题不是“功能少”，而是协议层没有真正成立

当前公共 `gg-phase` 中，`workspace_ui/server.py` 仍同时知道：

- Flask route；
- HTML；
- SSE；
- fixture；
- GT binding；
- adapter；
- workflow；
- GenUI 模型；
- rollback；
- App 和 MobileGym 布局。

`substrate/base.py` 又同时承载：

- 所有 App adapter；
- API/GUI 双 executor；
- reset/seed/read；
- App port；
- operator mapping；
- MobileGym 特例。

因此现在只是“目录看起来分开”，还不是：

> 一个目录对外只暴露协议，其他层完全不知道内部实现。

交接包把这一点改成了硬 Gate：

```text
workspace_ui 不得 import substrate 实现
governance 不得 import Playwright
autonomy 不得 import具体 App
kernel 不得读取 benchmark oracle
substrate 不得包含 workflow 语义
Runtime 不得存在 API mutation
模型输入不得出现 entity_id/operator/saga_id
```

---

## 2. 前端 405 的高概率直接根因已经定位

当前 fallback form 使用：

```html
<form method="post" action="edit">
```

而页面地址是：

```text
/<sid>
```

浏览器对相对 URL 的解析可能将它提交到：

```text
/edit
```

但真正的 Flask POST route 是：

```text
/<sid>/edit
```

所以请求会被其他 GET 路由匹配后返回 `405 Method Not Allowed`。代码注释声称它会提交到 `/<sid>/edit`，实际 HTML 却使用相对 `action="edit"`，这是静态代码中直接可见的不一致。turn658145view1

更严重的是，现有测试还显式接受这个相对表单：

```html
action="edit"
```

并把 API-mode full loop 当作通过条件。也就是说，当前 Gate 不仅没有抓住错误，还在保护旧错误和旧架构。

我在前端工单里没有只要求改成：

```html
action="/<sid>/edit"
```

因为那只是止血。最终方案是：

- 所有治理操作统一走 versioned JSON API；
- 前端 route 不再靠 HTML form 相对地址拼装；
- 一个页面只有一个 SSE connection；
- 页面加载先获取完整 `ProjectionSnapshot`；
- 后续只接收 `ProjectionDelta`；
- 不因 conflict 全页 reload；
- 不因读值变化重新调用 GenUI；
- 所有 route 都有 Flask client test 和 Playwright E2E test。

---

## 3. 当前 Runtime 仍保留 API executor

`make_adapter()` 的默认 executor 仍然是 `"api"`，代码中也明确保留 legacy `requests.post` 写路径；read、seed、reset 也共同留在同一个 adapter 中。

因此 Agent 1 工单要求的不是“默认改成 GUI”，而是：

> **Runtime 类型系统里根本不再存在 API executor 这个选项。**

最终拆成：

```text
Runtime Surface
├── observe_visible()
└── execute_gui_action()

Benchmark Oracle
├── reset()
├── seed()
├── read_hidden_state()
└── evaluate()
```

两者不共享父类，不允许 Runtime 通过依赖注入拿到 Oracle。

---

## 4. 当前模型与内部 ID 的边界仍然泄漏

当前 GenUI 输入会构造包含：

```text
entity_id
field
operator
```

的 binding 数据；编辑 workflow 还会生成：

```text
set app.entity_id.field → value
```

这样的自然语言。这和“模型输入只允许用户可见信息”的规则冲突。turn658145view1

新架构把它改成：

```text
模型可见：
“项目发布会议”
“日期”
“2026-08-20”
“TaskBoard 中的发布文案”

模型不可见：
E1
T1
move_event
set_deadline
saga_173
```

内部寻址改用 TaskVM 自己维护的 `SurfaceHandle` cache，而不是 App 数据库 primary key。

---

## 5. 当前启动脚本不能作为可交付 artifact

公开分支的 `run.sh` 仍硬编码：

- 某位开发者的 Python 绝对路径；
- repo 绝对路径；
- Playwright browser 绝对路径；
- `.chromelibs`；
- 固定端口；
- `fuser -k` 强杀端口；
- Flask debug mode。

Agent 7 工单专门负责：

- 可移植 bootstrap；
- 环境检查；
- 进程生命周期；
- readiness probe；
- 日志目录；
- Ctrl-C 清理；
- 禁止杀死不属于本次启动的进程；
- 一条命令启动；
- 一条命令运行 smoke test。

# 每个任务包已经钉死的边界

## Agent A：只搭 TaskVM 的“内核”

它只负责：

- Task State；
- Projection Schema/Data；
- Workflow primitive；
- Local/Goal/Compensation Patch；
- Event Log；
- Checkpoint；
- Store；
- import dependency gate。

它不能碰 Flask、Playwright、OpenAI、benchmark 或具体 substrate。

这样其他 Agent 才不会再各自发明一套 `PatchOp`、`WorkflowPlan` 和 session state。

## Agent B：所有平台差异只能在 Substrate 目录

它负责把：

- built-in Web；
- MobileGym；
- OSWorld；

全部包装成统一的：

```text
observe
act
capture
close
```

Workspace UI、Kernel、Runtime、Architect 不允许知道当前到底是 Web、MobileGym 还是 OSWorld。

它还负责彻底删除：

- `executor="api"`；
- app mutation API；
- `read_canonical()` runtime dependency；
- hidden DB entity ID；
- simulator `setState`；
- snapshot restore；
- `harness/state_adapter.py` shim。

## Agent C：合并高层模型角色

不再保留：

```text
Milestone Suggester
+ Rule Planner
+ GenUI Decoder
+ SubgoalGenerator
```

这种角色堆叠。

新的高层结构是：

```text
State Compiler
Task Architect / Projection Composer
CUA
```

Task Architect 一次产生：

- milestone；
- sequence/fan-out/bounded-loop topology；
- projection schema；
- action contracts；
- risk/reversibility；
- verification intent。

普通数值变化不会再调用 GenUI 模型。

## Agent D：只做 Projection 和前端

该任务包已经把你提出的前端要求全部写成验收项：

- 修复所有 405/500；
- 多 App / 多 surface 卡片；
- 默认只显示高层状态；
- 点击卡片读取已缓存的最新真实截图；
- 点击不重新调用模型，不重新执行 App；
- 实时显示 CUA 当前进度；
- workflow 可视化 sequence、fan-out、fan-in 和 bounded loop；
- milestone/checkpoint 业务化命名；
- LocalPatch、GoalPatch、pause、rollback、conflict 可操作；
- SSE 断线重连；
- 动画与状态变化一致；
- Playwright UI E2E；
- 浏览器 console error 必须为零。

## Agent E：把“用户不操作”真正变成自治运行

这个任务明确要求：

> 用户不操作时，CUA 持续自治推进，不是每五秒静态轮询。

同步改为：

```text
CUA action
→ 新 observation
→ Projection Store delta
→ SSE
→ UI 更新
```

Heartbeat 只补充当前 CUA 没在看的 inactive surfaces。

它也实现你提出的热拔插：

```text
CUA 请求 epoch=17
用户 GoalPatch
current epoch=18
旧回复回来
→ 丢弃，不执行
```

最小打断点从 workflow node 降到单个原子 GUI action。
