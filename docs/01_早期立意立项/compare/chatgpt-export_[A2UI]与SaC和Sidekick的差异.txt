## 先用一句话讲清楚我们的 idea

> **我们不是让 AI 再生成一个新的网页，而是让 GUI Agent 把分散在多个真实软件里的任务状态，临时整理成一个可以直接操作的“任务工作台”。人操作任务，Agent 操作软件。**

这里最重要的不是“界面是生成的”，而是这个界面和底层真实软件是连在一起的。

---

## 用一个例子理解

假设用户说：

> 帮我准备下周五的项目发布。

这件事实际上散落在很多应用里：

- 日历里有发布会议；
- 任务管理器里有测试和文档截止时间；
- 文档里有发布计划；
- 邮箱里有团队通知草稿；
- 可能还有几个没有解决的问题。

现在的做法，要么是用户自己在这些软件之间来回切换，要么是 GUI Agent 替用户点击，然后给用户看一串执行步骤：

```text
打开 Calendar
点击 Create Event
填写日期
打开 TaskBoard
修改 Deadline
……
```

但用户真正关心的并不是 Agent 点了哪个按钮，而是：

```text
项目发布日期：周五
发布会议：已安排
测试：还剩 2 项
文档：等待确认
团队通知：已起草，尚未发送
```

所以我们的系统会临时生成一个“项目发布工作台”。

用户直接把发布日期从周五改到下周一。接下来，Agent 自动去：

- 移动日历会议；
- 调整任务截止时间；
- 更新发布计划；
- 修改邮件草稿中的日期；
- 重新检查几个应用是否真的改成功。

完成后，工作台显示的也不是 Agent 自己声称“已经完成”，而是重新读取真实应用后得到的新状态。

更进一步，如果同事后来直接在任务管理器里修改了截止日期，工作台也要跟着更新，必要时告诉用户：

> 测试截止日期与发布日期产生冲突。

所以它不是把几个应用的信息复制到一个 dashboard 里，而是一个**能够读真实软件、修改真实软件、再核对真实软件的任务界面**。我们最核心的测试甚至可以压缩成一句话：用户修改工作台中的一个变量后，系统能否正确修改三个应用、保持无关内容不变，并在外部状态再次变化时同步回来。fileciteturn2file4

## 我们真正想改变的交互方式

传统软件是按照公司的产品结构组织的：

```text
日历是一个 App
邮件是一个 App
任务管理是一个 App
文档又是一个 App
```

但用户的目标从来不是“使用四个 App”，而是“完成一次项目发布”。

GUI Agent 已经可以替用户点击这些 App，但目前多数系统仍然是：

```text
用户说一句话
→ Agent 在后台执行
→ 用户等待一个结果
```

我们希望中间多出一个真正可操作的任务层：

```text
真实软件状态
→ Agent 整理成任务工作台
→ 用户直接修改任务
→ Agent 把修改落实到真实软件
→ 再读取软件进行核对
```

也就是说，用户以后可能不需要先理解每个软件怎么用，而是直接面对“会议”“发布日期”“预算”“负责人”“阻塞问题”这些任务本身。

名字暂时并不重要，可以先把它理解成一个**随任务出现、任务结束后就可以消失的临时软件**。

---

## 和 DuetUI 最本质的区别

DuetUI 解决的问题主要是：

> 用户一开始也不知道自己到底想要什么，怎样通过不断操作生成的界面，让 Agent 逐渐理解用户？

例如用户说“我想去日本旅游”，DuetUI 生成日期、住宿、景点等控件。用户点击民宿、调低预算，Agent 从这些操作中逐渐理解用户偏好，再修改任务和界面。

所以 DuetUI 的主线是：

```text
用户的需求还不完整
→ Agent 生成界面帮助用户探索
→ 用户操作界面
→ Agent 更理解用户
```

我们的主线不同：

```text
用户的目标可以已经比较明确
→ 但任务状态散落在多个应用里
→ Agent 将真实软件世界整理成任务界面
→ 用户直接修改任务状态
→ Agent 将修改执行回多个应用
```

一句最容易记住的话是：

> **DuetUI 让 UI 帮助 Agent 理解人；我们的 UI 帮助人理解和操作 Agent 正在改变的软件世界。** fileciteturn2file7

因此，DuetUI 更关注“需求是怎样逐渐形成的”；我们更关注“真实任务现在是什么状态，以及用户的一次修改能否可靠地落实到多个软件中”。两者表面上都会出现按钮、卡片和动态界面，但背后的研究问题不一样。fileciteturn2file2

---

## 和普通 Generative UI、A2UI 的区别

普通 Generative UI 更像：

```text
用户提出一个请求
→ AI 生成一个适合该请求的页面或小应用
```

重点通常是生成什么组件、页面是否好用、界面是否漂亮，以及不同设备上怎么显示。

我们的方向恰好是反过来的：

```text
不是从一句 Prompt 生成一个界面
而是从多个正在运行的真实软件中，反向整理出一个界面
```

页面里的“发布日期”不能只是 AI 生成的一段文字，它必须真的对应：

- 日历中的某个会议；
- 任务管理器中的某个里程碑；
- 文档中的某个日期；
- 邮件草稿中的某句话。

用户修改这个日期以后，这些位置也必须真的被修改。

因此，**A2UI 可以成为我们用来渲染界面的工具，但“生成 A2UI 界面”本身不是我们的研究贡献。**现有工作已经覆盖了任务界面生成、动态 mini-app 和跨平台渲染；我们的差异必须建立在真实应用、实时状态、可执行连接和修改后的核对上。fileciteturn2file1

---

## 和 Agent 轨迹监督界面的区别

另一类系统会把 Agent 的计划和执行步骤展示出来，让用户暂停、批准、接管或者回滚。

这种系统主要让用户操作：

```text
Agent 第几步做了什么
下一步准备做什么
某个动作是否允许执行
```

我们的系统不应该以这些低层步骤为核心。

用户不想处理：

> 第 37 步点击错了，请返回上一页，然后修改第三个输入框。

用户更自然的操作是：

> 发布日期改到下周一，其他安排跟着调整。

Agent 的执行轨迹仍然很重要，因为系统需要用它调试、找来源、处理失败，但它更像后台的执行记录。用户主要面对的应该是**世界现在是什么状态**，而不是 Agent 是如何一步步走到这里的。

换句话说：

> 轨迹描述 Agent 如何改变世界；任务工作台描述世界现在变成了什么。

必要时可以展开查看来源和执行证据，但不能让用户每天管理一串 Agent 日志。fileciteturn2file0

---

## 和最接近的 Agent-native OS、Software as Content 的区别

这两类工作已经非常接近我们的宏观愿景：

- Agent 组合多个服务；
- 用户面对任务而不是单个应用；
- 动态生成的软件成为人和 Agent 之间的交互层。

所以我们不能再简单地说：

> 首次让任务代替应用成为交互单位。

这个愿景以前已经有人提出，现在也有多个系统正在实现。

我们需要进一步回答一个更具体的问题：

> **生成出来的任务界面，究竟是不是现有软件世界的一个可信、可执行的简化版本？**

也就是：

- 它有没有漏掉会影响结果的重要信息？
- 一个控件是否绑定到了正确的软件对象？
- 用户修改后，所有相关应用是否都正确变化？
- 无关内容有没有被误改？
- 底层软件被别人修改后，任务界面能否重新对齐？

Software as Content 更强调“动态软件可以成为人和 Agent 的交互媒介”；我们必须强调“这个动态软件是多个既有软件实时状态的可信投影，并且可以写回和验证”。fileciteturn2file11

---

## 这个项目真正难的地方

难点不是让 GPT 生成一个好看的 React 页面。

真正困难的是：

首先，系统要判断不同应用中的哪些对象其实属于同一件事。例如 Calendar 里的“Launch Meeting”、任务管理器里的“Release Milestone”和文档里的“Launch Plan”，可能都属于同一次项目发布。

其次，系统要把复杂的软件状态压缩得足够简单，但不能漏掉会改变结果的信息。太复杂，用户仍然看不懂；太简单，又可能把关键依赖藏起来。

最后，用户修改任务工作台以后，系统要把修改正确传播到多个软件，并重新读取底层状态进行核对，而不是只修改工作台里的一份副本。

所以论文真正研究的可以概括成：

> **一个跨应用任务可以被压缩成多简单的界面，同时仍然忠实地反映和控制真实软件世界？**

# 可以直接和导师这样说

> 我们现在的想法，不是再做一个根据 Prompt 生成页面的 Generative UI，也不是给 GUI Agent 做一个执行日志面板。我们想让 GUI Agent 成为用户和现有软件之间的中间层：它读取日历、邮件、任务管理和文档等应用的实时状态，把这些分散的信息临时整理成一个面向当前任务的操作界面。
>
> 比如用户正在准备一次项目发布，看到的不再是四个应用和几十个 Agent 步骤，而是发布日期、会议、材料、阻塞问题和通知状态。用户直接修改发布日期，Agent 负责把这个修改落实到所有相关应用，再重新读取状态，确认修改成功且没有误改其他内容。
>
> 它和 DuetUI 的主要区别是，DuetUI 用动态界面帮助 Agent 逐渐理解用户的模糊需求；我们假设任务目标可以比较明确，主要解决任务状态被多个应用割裂的问题。我们的界面不是用来让用户不断教 Agent 自己想要什么，而是让用户理解并直接操纵 Agent 正在改变的真实软件世界。
>
> 它和普通 Generative UI 的区别是，界面不是从 Prompt 凭空生成的。页面中的每个状态都要来自真实应用，每个可操作项都要能够写回真实应用，而且执行后还要重新验证和同步。它也不是 Agent 轨迹可视化，因为用户操作的不是第几步点击，而是发布日期、预算、负责人这些任务级对象。
>
> 所以我们真正研究的不是怎么生成一个更漂亮的 UI，而是怎样把多个现有软件编译成一个足够简单、但仍然准确和可执行的任务界面。最简洁的产品表达就是：**人操作任务，Agent 操作应用。**

这版定位既承认了 DuetUI、A2UI、Software as Content 等工作已经占据的部分，也把我们的核心收紧到了“真实软件状态的可执行任务投影”，避免最后变成另一个漂亮但后端写死的跨应用 dashboard。fileciteturn2file16

# 一、GUI Agent 的执行和评测基础

## 1. LlamaTouch
### A Faithful and Scalable Testbed for Mobile UI Task Automation

这篇不是设计新的用户界面，而是在解决：

> 手机 Agent 到底有没有真正完成任务，应该怎么可靠评测？

以前常见的评测方式，是看 Agent 的点击步骤是否和人工标注的标准步骤一致。但同一个任务可能有多种正确路径，例如先搜索再筛选，或者先进入分类再搜索，都可能完成目标。

LlamaTouch 不要求 Agent 走固定路线，而是检查它是否经过并最终达到任务要求的几个关键应用状态。它在真实 Android 设备上执行任务，并通过截图、界面结构和状态匹配来自动判断结果。

例如“在购物 App 中把某个商品加入购物车”，重点不是 Agent 点击了哪几个按钮，而是最后购物车里是否真的出现了正确商品。

**对我们的价值：**非常重要，但它主要是底层评测基础。我们也应该采用类似思想：不检查 Agent 是否走了预定轨迹，而是检查用户修改任务工作台后，真实应用状态是否正确变化。它可以启发我们设计自动 verifier 和 round-trip evaluation。

---

## 2. AppAgent
### Multimodal Agents as Smartphone Users

AppAgent 是比较早期、很有代表性的手机 GUI Agent。

它不依赖 App 提供专门的 API，而是像人一样：

- 看手机截图；
- 点击；
- 滑动；
- 输入文字；
- 在不同页面之间导航。

它有两个主要阶段。第一阶段让 Agent 自主探索 App，或者观察人类示范，并把“这个 App 怎么用”整理成知识；第二阶段再利用这些知识完成用户给出的任务。

可以把它理解成：

> 先让 AI 自己逛一遍 App、写一本使用说明书，以后再按照说明书替人操作。

**对我们的价值：**它可以代表我们系统下层的“执行者”。我们的工作不是重新证明 Agent 能点击手机，而是在 AppAgent 这类执行能力上面增加任务层：用户操作统一的任务界面，Agent 再到真实 App 中执行。

---

## 3. Computer Agent Arena
### Toward Human-Centric Evaluation and Analysis of Computer-Use Agents

这项工作把 Chatbot Arena 的思想搬到了 Computer-Use Agent 上。

用户不是只看一个静态成功率，而是在真实桌面环境中同时观察两个匿名 Agent 完成同一个任务，然后投票哪个更好。系统再根据大量两两比较形成动态排行榜。

它想解决的是：

> 传统 benchmark 觉得最好的 Agent，真实用户是否也觉得最好？

因为用户可能不仅关心任务有没有完成，还会在意：

- Agent 是否乱点；
- 是否容易理解；
- 是否太慢；
- 是否中途卡住；
- 是否采取了让人不放心的操作。

**对我们的价值：**它提示我们，自动 task success 不足以证明交互方式更好。我们的自动实验应该测真实应用状态是否正确，用户实验则应该测用户是否更容易理解、修改和纠错。

# 二、Agent 是否理解人，以及何时应该帮助人

## 4. GUIDE
### A Benchmark for Understanding and Assisting Users in Open-Ended GUI Tasks

大部分 GUI Agent 研究假设：

> 用户已经把目标说清楚，Agent 只要执行即可。

GUIDE 研究的是另一种情况：用户正在 PowerPoint、Photoshop 等复杂软件中探索和创作，目标可能一边操作一边变化。Agent 首先需要理解：

- 用户当前在做什么；
- 用户最终可能想达到什么；
- 用户现在是否需要帮助；
- 应该提供什么帮助。

作者收集了大量新手用户操作软件时的屏幕录像和 think-aloud 讲述，并设计了三个任务：识别用户当前行为状态、预测用户意图、判断何时以及如何帮助。

结果表明，即便是先进多模态模型，也很难稳定判断用户现在处于什么状态、是否真的需要帮助。

**对我们的价值：**GUIDE 更关注“理解正在操作软件的人”，而我们更关注“把 Agent 正在改变的软件状态整理给人”。但它提醒我们：任务工作台不能只根据用户最初一句话生成，还可能需要结合用户操作历史和上下文，判断哪些状态最值得展示。

---

## 5. DiscoverLLM
### From Executing Intents to Discovering Them

这篇研究一个很有意思的问题：

> 有时候不是用户没有把需求说清楚，而是用户自己还不知道想要什么。

比如用户说“帮我设计一张海报”，模型问“想要什么风格”，用户可能根本答不上来。用户需要先看到几个方案，才能发现自己喜欢什么。

DiscoverLLM 构造了一个带有“潜在意图层级”的用户模拟器。模型通过展示选项、探索不同方向，逐渐帮助用户把模糊想法变成具体需求。模型学会在两种行为之间切换：

- 用户还不清楚时，先发散、展示可能性；
- 用户逐渐明确后，再收敛、细化并执行。

**对我们的价值：**它和 DuetUI 一样，核心是“帮助用户形成意图”。我们的主问题不同：我们可以假设用户已经知道要做什么，例如“把发布日期改到周一”，困难在于这个任务对应的状态分散在多个应用中。它可以成为扩展方向，但不应该成为我们当前论文的中心。

---

## 6. The Behavioral Fabric of LLM-Powered GUI Agents
### Human Values and Interaction Outcomes

这篇研究：

> 用户的偏好和价值观，是否真的会影响 GUI Agent 的行为？

作者构建了购物、旅行、餐饮、住房等网页任务，并给 Agent 加入不同用户画像，例如：

- 重视低价格；
- 重视环保；
- 重视健康；
- 重视便利；
- 重视社会责任。

结果显示，偏好确实会改变 Agent 的搜索、筛选和操作轨迹。例如重视某种价值时，Agent 会更多使用相应筛选项。

但论文也发现，网页中的折扣、广告和突出按钮等强界面提示，可能压过用户价值。Agent 嘴上可能给出符合用户价值的解释，行动上却仍然选择最显眼或最快的选项。

**对我们的价值：**任务工作台不仅要展示“最终选了什么”，也可以显式呈现 Agent 当前采用的约束，例如预算、隐私、环保偏好。否则这些偏好很容易被底层应用的界面设计覆盖。

# 三、Agent 的风险、隐私和人类监督

## 7. Dark Patterns Meet GUI Agents
### LLM Agent Susceptibility to Manipulative Interfaces and the Role of Human Oversight

这篇研究网页中的 dark patterns，也就是刻意诱导用户做出某种选择的设计，例如：

- 把接受按钮做得特别明显；
- 把拒绝选项藏起来；
- 默认勾选额外服务；
- 制造虚假的紧迫感；
- 用复杂步骤阻止用户退出。

作者比较了 Agent、普通人，以及人和 Agent 协作时的表现。

一个重要发现是：Agent 即使注意到界面可能有问题，也经常因为“完成任务优先”而继续操作。人类则可能因为习惯、注意力不足等原因被诱导。加入人工监督能够减少一些问题，但也会增加认知负担，而且人不一定能及时看到真正关键的风险。

**对我们的价值：**它说明“让用户一直看着 Agent”并不是理想解决方案。我们的任务工作台应该压缩低层点击，只把真正影响任务结果的变化、冲突和关键决定展示出来。

---

## 8. PrivWeb
### Unobtrusive and Content-aware Privacy Protection for Web Agents

Web Agent 为了帮用户操作网页，通常需要读取整个页面，其中可能包含姓名、地址、邮件、订单、健康信息等隐私内容。

PrivWeb 在 Agent 和网页之间加了一层隐私保护。它使用本地模型识别和匿名化界面中的私人信息，并根据敏感程度采取不同处理：

- 敏感性较低的信息，低打扰地通知用户；
- 高度敏感的信息，暂停 Agent，要求用户明确处理；
- 尽量不让用户为每一个普通字段都反复确认。

核心思想是：

> 隐私保护不能只靠“全部阻止”，也不能每次都弹窗，而应该根据内容和敏感程度分级处理。

**对我们的价值：**它与我们的任务工作台不是同一个问题，但它提供了很好的设计原则：不要把所有状态都同等展示和确认。任务 UI 可以根据影响程度，只突出真正需要用户决定的字段。

---

## 9. Comparing Human Oversight Strategies for Computer-Use Agents

这篇不是提出一种新的 Agent，而是系统比较不同的人类监督方式。

它把监督理解成两个方面：

- 人和 Agent 怎样分工；
- 用户在什么时间、以多高频率参与。

作者在真实网页环境中比较了四种监督策略，例如偏计划阶段的监督、偏执行阶段的监督，以及不同参与程度的组合。

一个重要结论是：

> 监督得更多，不一定纠错得更好。

计划阶段参与可能减少 Agent 后面产生问题，但在执行过程中，即使错误已经出现，用户也未必能够及时认出“这是需要我干预的关键时刻”。真正重要的是，系统能否让关键决定变得清晰、可识别。

**对我们的价值：**这直接支持我们不要做普通轨迹监控器。任务工作台的意义应该是把几十个低层动作变成几个用户能够理解的任务级变量，让真正需要判断的时刻变得明显。

---

## 10. A11y-CUA Dataset
### Characterizing the Accessibility Gap in Computer Use Agents

当前大部分 Computer-Use Agent 都按照视力正常、使用鼠标的人来设计：

- 看完整屏幕；
- 移动鼠标；
- 点击；
- 拖动；
- 在视觉布局中定位元素。

但盲人和低视力用户经常使用：

- 屏幕阅读器；
- 键盘导航；
- 放大视图；
- 不同的顺序式操作习惯。

A11y-CUA 收集了视力正常用户和盲人、低视力用户完成日常电脑任务的操作轨迹，并比较当前 CUA 在默认环境和辅助技术环境中的表现。结果显示，Agent 在键盘操作或放大视图下性能明显下降，也没有真实反映辅助技术用户的操作方式。

**对我们的价值：**它提醒我们，不能默认“人可以像看普通 dashboard 一样看任务工作台”。如果将来声称任务级 UI 对所有用户更简单，就必须考虑键盘操作、屏幕阅读器、信息顺序和非视觉反馈。但这比较适合作为设计要求或后续研究，不宜和当前核心问题并列。

# 四、动态 UI 如何成为人和 Agent 的沟通工具

## 11. GenComUI
### Exploring Generative Visual Aids as Medium to Support Task-Oriented Human-Robot Communication

GenComUI 面向的是人和机器人沟通，而不是桌面 GUI Agent。

例如用户通过语言告诉机器人：

> 从这个位置走到那里，经过桌子旁边，但不要碰到椅子。

只靠语言容易产生歧义，因此系统会动态生成：

- 地图标记；
- 路径线；
- 方向箭头；
- 动画；
- 空间范围提示。

用户看到这些视觉辅助后，可以更容易发现机器人理解错了哪里，并继续通过语言和图形修正任务。系统还可以据此生成机器人任务程序。

**对我们的价值：**它证明了“生成的视觉界面可以成为人和 Agent 之间的共同语言”，而不是只作为最终结果。但它主要用于澄清空间指令，没有连接多个现有软件，也没有把用户操作写回多个真实应用。

---

## 12. DuetUI
### A Bidirectional Context Loop for Human-Agent Co-Generation of Task-Oriented Interfaces

DuetUI 是和我们表面上最接近的工作之一。

用户先给一个比较模糊的目标，例如：

> 帮我规划一次巴塞罗那旅行。

Agent 不直接给最终答案，而是逐渐生成日期、预算、住宿、交通、景点等任务界面。用户通过点击、筛选、拖动和填写来表达偏好；Agent 再根据这些操作修改任务理解和下一版界面。

因此它形成了一个循环：

```text
Agent 理解任务
→ 生成界面
→ 用户操作界面
→ Agent 从操作中理解新意图
→ 更新任务和界面
```

它最重要的贡献，是把 UI 从“Agent 的最终输出”变成了人和 Agent 持续交流的媒介。你前面材料中已经对其系统机制、实验和局限做过详细拆解。fileciteturn2file0

**对我们的价值与区别：**

- DuetUI 主要解决：用户自己还不完全知道想要什么，怎样通过界面逐渐形成需求。
- 我们主要解决：用户可能已经知道要什么，但相关状态散落在日历、邮件、任务管理器和文档中。

可以简单记成：

> DuetUI 用 UI 帮助 Agent 理解人；
> 我们用 UI 帮助人理解并操纵 Agent 正在改变的软件世界。

此外，DuetUI 的外部服务在原型中有较多模拟成分，而我们的重点应放在真实应用状态、跨应用写回和修改后的自动核对。

---

## 13. Macaron-A2UI
### A Model for Generative UI in Personal Agents

Macaron-A2UI 更偏模型和协议层。

它让模型不只是生成文字，还能够同时生成结构化、可执行的 UI 指令。例如用户需要比较几个酒店时，模型可以生成卡片和筛选项；需要收集日期时，可以生成日期选择器；需要确认多个目标时，可以生成一个结构化计划面板。

它不是让模型直接随意写 React 代码，而是让模型输出受约束的 A2UI 指令，再由可信客户端渲染。

作者还构建了 Generative UI 数据集和 A2UI-Bench，并通过监督微调和强化学习，使模型学习：

- 什么时候应该生成 UI；
- 生成什么组件；
- 组件内容如何与对话对应；
- UI 指令是否合法；
- 什么情况下应该继续只用文字。

**对我们的价值：**它可以成为我们的界面生成技术或 renderer，但不能成为我们的主要新意。因为“让模型生成按钮、卡片和滑块”已经被它正面覆盖。

我们的贡献必须放在 A2UI 之前和之后：

```text
真实应用状态
→ 跨应用任务模型
→ A2UI 界面
→ 用户修改
→ 写回真实应用
→ 状态验证
```

Macaron-A2UI 重点处理的是中间的“任务上下文如何变成 UI”，并不主要研究既有应用的实时状态绑定和跨应用执行。

---

## 14. Software as Content
### Dynamic Applications as the Human-Agent Interaction Layer

这篇在概念上可能是与我们最接近的工作。

它认为聊天界面存在三个问题：

- 结构化信息被压缩成线性文字；
- 用户必须不断用自由语言表达，成本很高；
- 聊天内容不断向下滚动，缺少稳定、持续演化的任务状态。

因此作者提出：

> 不要把软件理解为预先安装好的固定 App；Agent 可以根据当前任务生成一个持续存在、不断变化的小型应用，让它成为人和 Agent 的主要交互层。

例如规划东京旅行时，用户不再面对长聊天记录，而是看到一个不断更新的旅行应用，其中包含酒店、路线、预算和日程。用户操作这些控件，Agent 再根据操作继续工作。

它与 DuetUI 的区别是，它更像一个总体交互范式或系统架构：生成的软件本身成为长期、状态化的人—Agent—环境中介。

**对我们的价值与区别：**它已经占据了“动态应用代替纯聊天，成为人和 Agent 的交互层”这个宏观位置。所以我们不能只说自己发明了任务型动态软件。

我们需要更具体地强调：

```text
Software as Content：
用户任务
→ 生成一个新的动态应用
→ 人和 Agent 在其中持续交互
```

```text
我们的方向：
多个既有应用的实时状态
→ 编译成统一任务界面
→ 用户修改任务变量
→ Agent 修改原有应用
→ 重新读取和验证
```

也就是说，Software as Content 研究的是“动态软件怎样成为交互媒介”；我们要研究的是“动态软件怎样成为现有软件世界的可信、可执行投影”。

**DuetUI、Software as Content、Macaron-A2UI**

- UI 可以由 Agent 动态生成；

它们分别对应：

```text
执行器
+

```

**Computer Agent Arena、GUIDE、Comparing Human Oversight Strategies**

它们提醒我们：

- 静态 benchmark 不等于真实用户体验；
- Agent 要理解用户正在做什么；

## 最能帮助我们讨论风险和边界的

**Dark Patterns、PrivWeb、Behavioral Fabric、A11y-CUA**

它们分别告诉我们：

- Agent 会受到操纵性界面的影响；
- Agent 读取网页会产生隐私问题；

这些不应该全部变成我们论文的主问题，但可以帮助我们解释为什么任务工作台需要：

- 明确来源；
- 暴露关键约束；

# 一、整个训练流程：先教格式，再教品味

可以把训练理解为两学期。

```text
构造训练数据
    ↓
第一学期：SFT，学会基本语法和标准动作
    ↓
第二学期：RL，学会什么界面更合适、更完整、更好用
    ↓
A2UI-Bench 考试
```

## 第一步：先制造一本“什么时候该长出什么界面”的教材

作者没有从零人工编写几万条 UI 数据，而是从四类已有对话数据出发：

- MultiWOZ 2.2：订酒店、餐厅、交通等任务型对话；
- Schema-Guided Dialogue：多种服务和槽位收集任务；
- ESConv：情绪支持对话；
- AnnoMI：动机访谈、行为改变对话。

最终从 4,306 个基础对话中构造出 **14,245 个 assistant turn**，其中约 71.7% 带 UI，其余是纯文字。保留纯文字非常重要，因为模型还要学会：

> **不是每句话都应该强行弹出按钮和滑块。**

### 任务型对话：像填表，主要靠规则转换

例如原对话中已经明确：

```text
缺少信息：入住日期
可选酒店：A、B、C
下一步：让用户确认
```

系统可以比较确定地转成：

```text
入住日期 → DateTimeInput
酒店候选 → SelectionList / Card
最终确认 → Button
```

因此 MultiWOZ 和 SGD 主要采用规则和状态机生成 UI，LLM 更多负责把旁边的自然语言润色得自然一点。

### 开放式对话：像设计互动，由两个 LLM 角色协作

情绪支持或动机访谈没有现成的槽位。例如用户说：

> 我最近一直拖延，也不知道先改什么。

这里不一定适合日期选择器，可能更适合：

- 让用户选出最困扰的原因；
- 给信心程度打分；
- 选择一个最小行动计划。

作者采用了一个 **Editor–Author** 流程：

```text
Editor：先从全局判断哪一轮适合出现 UI，UI 承担什么作用
Author：再写具体组件、选项文本和布局
```

相当于先由“产品经理”决定要不要做界面，再由“设计师”把界面填出来。

### 最后还有一位非常严格的“质检员”

生成的 A2UI 会经过四级检查：

1. JSON 能不能解析；
2. 必需字段和组件类型是否正确；
3. 数据绑定是否完整、类型是否匹配；
4. 界面和预期交互是否基本一致。

不合格就把错误反馈给生成器，最多重试三次。经过后处理和重试，论文报告最终 UI turn 的可渲染率达到 **99.2%**。

# 二、第一阶段训练：SFT，让模型先学会“写合法界面”

SFT 可以理解成老师给标准答案，模型照着练。

每条训练样本大致是：

```json
{
  "context": "系统指令 + 历史对话 + 当前用户输入",
  "target": {
    "text_response": "自然语言回复",
    "a2ui": ["结构化 UI 动作序列"]
  }
}
```

例如：

```json
{
  "text_response": "请选择你的预算和出发日期。",
  "a2ui": [
    {"surfaceUpdate": "...预算滑块和日期组件..."},
    {"beginRendering": "..."}
  ]
}
```

模型不是先写文字，再由另一个程序转换成 UI，而是**一次生成文字和 UI 动作**。训练时使用 LoRA，只更新少量低秩参数，而不是把整个大模型重新训练一遍；损失只计算 assistant 最终回答部分。

SFT 主要教会三件事：

```text
什么时候输出 UI
UI 的 JSON 大致怎么写
文字和 UI 怎么放在同一个回答里
```

但 SFT 有一个限制：一个任务可能有很多种都合理的界面，不一定只有唯一标准答案。

比如问用户预算，可以用：

- 滑块；
- 三档单选；
- 数字输入框。

三种都可能正确。因此只模仿一个标准答案还不够。

---

# 三、第二阶段训练：GRPO，让模型学会“挑更好的界面”

第二阶段采用 GRPO 强化学习。

它像是给同一个题目同时找几位学生作答：

```text
候选 A：只给一大段文字
候选 B：生成预算滑块，但没有提交按钮
候选 C：预算滑块 + 日期选择器 + 下一步动作
候选 D：生成十几个控件，信息过载
```

评分器给每个候选打分，模型不是简单背一个标准答案，而是学习：

> 在同一个问题下，哪个答案相对更好？

GRPO 会针对同一 prompt 采样一组候选结果，根据组内相对奖励优化模型。它特别适合优化那些没有唯一正确答案的属性，例如：

- 该不该触发 UI；
- 控件组合是否完整；
- 用户点完以后能否继续下一步；
- UI 是否真正减少操作负担。

## 奖励函数先设了一道“硬门槛”

出现以下情况，直接零分：

- JSON 无法解析；
- 本来应生成 UI，却没有 UI；
- 协议验证失败；
- 存在导致无法渲染的结构错误。

只有先通过“能运行”这一关，才继续评价：

```text
L1：结构是否合法
L2：任务和交互是否构造正确
L3：对用户是否真的有价值
```

对于不需要 UI 的对话，则使用专门的 no-UI 奖励，鼓励模型老老实实只回复文字，而不是“为了炫技什么都生成界面”。

所以可以把两阶段训练总结为：

> **SFT 教模型不要把厨房炸掉；RL 教模型做出来的菜不只是能吃，还要适合客人。**

---

# 四、A2UI-Bench 是怎么出题的？

A2UI-Bench 一共有 **300 个任务**，不是全部都考“单轮生成一个表单”，而是分为三种题型。

## 1. Atomic：单步题

类似：

> 我想订一个周五晚上的餐厅。

考察模型能否在这一轮判断：

- 是否需要 UI；
- 应该用日期时间、人数选择还是文本输入；
- 输出是否合法。

这是最基础的“单题考试”。

## 2. Depth：连续剧题

例如：

```text
第一轮：选择城市
第二轮：选择日期
第三轮：根据前面的答案更新酒店候选
```

评估时会把模型自己上一轮的输出继续喂回去。

这里考的是：

- 是否记得之前已经创建的界面；
- 是更新旧界面，还是错误地再创建一份；
- 状态是否能跨轮保持；
- 前后是否自相矛盾。

这更像连续剧，第一集埋下的角色，第三集不能突然消失。

## 3. Width：一页要处理多个目标

例如用户说：

> 帮我安排去上海的行程，比较两家酒店，并且确认会议时间。

模型需要同时组织：

- 行程信息；
- 酒店比较；
- 会议确认。

不能把它们混成一张巨型表单，也不能碎成十几个互不相关的小窗口。

这里考的是**界面组织能力**，而不仅是会不会生成单个按钮。

基准中还专门加入了 `no_ui_chat` 负样本，检查模型是否知道在安慰、解释或普通聊天时不要乱生成 UI。

---

# 五、评估指标：先查“能不能跑”，再查“有没有用”

整个评估分成两侧：

```text
语言 / 结构侧：直接检查模型输出的 JSON 和语义
视觉侧：把 UI 真正渲染出来，再看截图
```

## L1：协议正确性——这份 UI 能不能启动？

L1 完全由程序自动检查，分成五项：

- **L1-1 JSON parse correctness**：JSON 能不能解析；
- **L1-2 schema compliance**：是否符合 A2UI schema；
- **L1-3 reference integrity**：组件引用、surface ID 等是否指向有效对象；
- **L1-4 required-field completeness**：必要字段是否缺失；
- **L1-5 value-format correctness**：日期、枚举、数据类型等格式是否正确。

L1 是一种很严格的“闸门评分”。

例如模型输出 JSON 都打不开，那么后面四项全部为零；如果 JSON 能解析，但内部结构错误，那么只给 JSON 解析这一项分，其他项清零。只有完全没有结构错误时，才以 5 分为起点，根据 warning 数量扣分。

可以把它想象成建筑验收：

> 房子地基都塌了，就没有必要继续评价窗帘颜色。

---

## L2：任务构造质量——界面是不是“做对了事”？

L2 由 LLM judge 根据任务、对话、文字回复和 A2UI JSON 评分，每项范围是 0–5 分。

五项分别是：

### L2-1 Trigger appropriateness

这一轮到底该不该生成 UI？

例如用户说：

> 我今天心情特别差。

直接弹出十个选项，可能反而不自然。

但用户说：

> 帮我在三家酒店中选一家。

这时卡片和筛选器就非常合适。

### L2-2 Component–intent alignment

控件类型是否符合目的？

例如：

- 选日期用日期选择器；
- 比较几个选项用卡片或单选；
- 连续数值用滑块；
- 多选偏好用 checkbox。

拿滑块让用户填写邮箱，就是明显不匹配。

### L2-3 Text–UI grounding

UI 里的内容有没有依据？

如果文字中说有酒店 A 和 B，UI 却突然出现酒店 C，说明界面在“凭空编选项”。

### L2-4 Data-model utilization

是否正确使用 `dataModelUpdate` 保存动态状态？

例如用户上一轮选了 2000 元预算，下一轮不应忘记或重新设置成 5000 元。

### L2-5 Action completeness

控件是否形成了完整交互闭环？

不能只有一个滑块，却没有任何提交、继续或状态回传动作。用户操作以后，系统必须知道下一步怎么办。

---

## L3：用户体验质量——就算做对了，它真的比文字好吗？

L3 同样由 LLM judge 按 0–5 分评价，但问题更接近 HCI。

### L3-1 Value addition over text

UI 是否真正降低了用户成本？

如果把一段三行文字放进一张卡片，没有任何操作价值，那只是“把文字装进方框”，不能算好的 Generative UI。

### L3-2 Conversational naturalness

UI 出现得是否自然？

好的体验是：

> “为了帮你缩小范围，请选择预算和日期。”

然后出现两个控件。

不好的体验是用户问“你好”，模型突然弹出旅行规划表单。

### L3-3 Cognitive load

这一轮是否塞了太多东西？

例如一次要求用户填写：

- 日期；
- 城市；
- 酒店；
- 航班；
- 餐饮；
- 兴趣；
- 支付方式；
- 联系人；

即使控件都合法，用户也可能直接被吓退。

---

# 六、视觉指标：把 JSON 真正渲染出来再检查

语言侧评分可能觉得一个结构完全正确，但渲染出来以后仍可能：

- 字被裁掉；
- 卡片重叠；
- 按钮跑出屏幕；
- 用户看不出下一步点哪里。

所以论文还有视觉侧评估：

- **V1 Visual integrity**：可读性、裁切、溢出、布局破损；
- **V2 Task alignment**：屏幕上看到的 UI 是否符合任务和文字回复；
- **V3 Action clarity**：用户能不能一眼看懂下一步该做什么。

流程是：

```text
模型生成 A2UI
→ 客户端真实渲染
→ 截图
→ VLM judge 看截图并评分
```

只有 JSON 解析成功、包含非空 UI、且渲染检查通过的样本，才进入视觉评分。

不过开源 benchmark 的默认流程是 **JSON-first**，即默认运行 L1、L2、L3；渲染和 VLM 视觉评估是可选扩展，需要额外启动 renderer。

---

# 七、用一个例子完整走一遍评估

用户说：

> 我在考虑每天锻炼，但不知道从哪里开始。

模型 A 输出：

```text
你可以从每天运动十分钟开始。
```

没有 UI。

可能的评价：

- L1：合法，因为文本-only 是允许的；
- L2 Trigger：可能偏低，因为此处用选择或计划组件可能更有帮助；
- L3：回答自然，但交互价值有限。

模型 B 输出：

```text
先选一个你最容易坚持的活动。
```

界面：

```text
请选择：
○ 散步
○ 跑步
○ 瑜伽
○ 居家力量

信心程度：1 ───── 10

[制定一个七天小计划]
```

如果 JSON 正确、控件绑定完整：

- L1 高；
- L2 中的组件—意图匹配、交互完整性较高；
- L3 的 value-add 较高；
- V3 也较高，因为用户很明确知道该选什么。

模型 C 输出二十个运动选项、五个滑块、三张表：

- L1 可能满分，因为技术上完全合法；
- 但 L3 cognitive load 会较低。

这正是这套评估比较合理的地方：

> **它区分了“代码能运行”和“界面值得存在”。**

---

# 八、实验到底证明了什么？

论文在 30B、235B 和 754B 等不同规模的模型上使用 LoRA-SFT 加 GRPO 训练，并重点测试一种更困难的条件：推理时不把完整 A2UI schema 全部塞进 prompt，让模型把 UI 能力内化到参数里。最佳模型在 A2UI-Bench 上报告 **75.6 的总体成绩**，超过了获得完整 schema prompt 的最强前沿基线。turn855767view0

这说明训练确实可以让模型逐渐学会：

```text
看到对话
→ 判断是否需要 UI
→ 选正确组件
→ 生成合法协议
→ 保持多轮状态
→ 避免无意义或负担过重的 UI
```

但要注意，它主要证明的是：

> **模型能够学习 assistant-side 的 Generative UI 生成能力。**

它没有重点评估：

- UI 是否绑定到了真实外部应用；
- 用户修改 UI 后，真实软件状态是否改变；
- 跨应用状态是否同步；
- 修改之后是否有独立 verifier 核对真实世界。

所以对我们的项目来说，Macaron-A2UI 更像“界面生成器或中间协议层”，而不是完整的跨应用任务闭环。

最容易记住的对比是：

> **Macaron-A2UI 考的是：模型能不能长出一个合适、合法、好用的界面。**
> **我们还需要继续考：这个界面里的每一个值，是否真的来自现实软件；用户改了以后，现实软件是否真的跟着改变。**


【提问 轮数9】
这些数据是怎么来的？sft的数据？rl的奖励信号？，另外使用llm as judge真的靠谱吗？用的是哪个模型？最后有没有人类参与？

【回答内容 轮数9】
可以把 Macaron-A2UI 的数据和训练理解成一条“半自动生产线”：

> **旧对话提供真实语境，规则和 LLM 把它改造成 UI 教材；SFT 学标准答案，RL 再由 GPT-5.1 当教练打分。**

但这里要特别注意：它的“界面好不好”并不是全部由人类标注出来的，很多高层质量信号来自 LLM judge。

---

## 一、SFT 数据到底从哪里来？

它没有让标注员从零设计一万多个界面，而是拿了四个已有对话数据集：

| 数据集 | 原本是什么 | 用来教什么 |
|---|---|---|
| MultiWOZ 2.2 | 酒店、餐厅、交通等任务对话 | 收集参数、展示候选项、确认预订 |
| SGD | 多服务、多槽位任务对话 | 跨服务表单、信息收集 |
| ESConv | 情绪支持对话 | 引导选择、反思和支持 |
| AnnoMI | 动机访谈对话 | 自我评估、信心评分、行动计划 |

最终从 **4,306 段基础对话**中产生 **14,245 个 assistant turn**：

- 10,080 个来自原始对话转换；
- 4,165 个是定向增强数据；
- 10,210 个带 UI；
- 4,035 个保持纯文本。

也就是说，训练样本不是“一段完整对话对应一条数据”，而是对话里的每一个 assistant 回合，都可以变成一条：

```text
输入：
系统提示 + 前面的对话 + 当前用户消息

标准答案：
自然语言回复 + A2UI 动作序列
```

turn887905view0

---

## 二、不同类型的数据，生成方式不一样

### 1. MultiWOZ 和 SGD：主要由规则转换

这两类数据原本就有比较清楚的结构化标注：

```text
用户想订酒店
缺少入住日期
已经知道城市和人数
接下来需要让用户选择日期
```

因此系统可以比较机械地转换：

```text
缺日期
→ DateTimeInput

有几个候选酒店
→ SelectionList / Cards

需要最终确认
→ Confirm Button
```

这里主要依靠 dialogue act、intent 和 slot 等原始标注，以及状态机式的规则。LLM 主要负责把回复文字润色自然，而不是自由决定整个 UI。

这部分数据相对可靠，因为核心结构来自原数据：

```text
缺什么信息
有哪些候选项
下一步要确认什么
```

不是完全由 LLM 凭空想象。

---

### 2. ESConv 和 AnnoMI：主要由 LLM 设计

开放式对话没有“缺少入住日期”这种明确 slot。

例如：

> 我一直想开始运动，但每次都坚持不下来。

原数据并不会告诉系统：

```text
这里应该生成一个信心滑块
这里应该给三个行动方案
这里应该保留纯文本
```

所以作者采用两个 LLM 阶段：

```text
Editor
先看整段对话：
哪几轮应该出现 UI？
UI 应该帮助用户做什么？

        ↓

Author
为选中的回合生成：
组件类型、问题文本、选项、布局和动作
```

这部分本质上是**合成监督数据**。论文明确描述了 Editor–Author 流程，但没有在正文或附录中明确披露生成这些训练标注时使用的具体 LLM 型号。因此不能确定是 GPT、Gemini 还是其他模型。turn428375view4

这也是一个潜在问题：

> 模型学到的可能不仅是“正确的 Generative UI”，还会学到生成数据所用 LLM 的设计偏好。

---

## 三、4,165 条增强数据是怎么来的？

作者发现某些组件在原始数据中很少，例如：

- Slider；
- Tabs；
- Modal；
- Checkbox；
- DateTimeInput；
- Image、Audio、Video 类组件。

如果只按自然分布训练，模型可能永远只会生成 Card、Column 和 Label。

因此，他们专门构造包含长尾组件的样本，增加了 **4,165 条定向增强数据，占总数据的 29.2%**。

这有点像驾校发现学生只会直线开车，于是专门加入：

```text
倒车入库题
坡道停车题
夜间驾驶题
```

它能提升覆盖率，但也会改变真实数据分布。也就是说，模型可能比真实用户需求更频繁地想到某些罕见组件。

---

## 四、生成出来的数据会不会有很多坏 JSON？

他们又加了一套自动质检：

```text
生成 A2UI
   ↓
检查 JSON 是否合法
   ↓
检查 schema 和字段
   ↓
检查组件引用、类型和数据绑定
   ↓
做轻量语义一致性检查
   ↓
失败则把错误反馈给生成器，最多重试三次
```

同时还有规则修复，例如：

- 修改非法 enum；
- 补充缺失字段；
- 修正数据绑定类型；
- 约束简单布局。

最终：

- 91.3% 的 UI 样本第一次就通过；
- 重试又救回 7.6%；
- 最终可渲染率达到 99.2%。



但这里的“99.2%”主要意味着：

> **结构能通过检查、可以渲染。**

它不等于 99.2% 的界面都真正好用。

---

# 五、RL 的奖励信号从哪里来？

它不是收集人类偏好对，也没有先训练一个独立的人类偏好 reward model。

具体流程是：

```text
同一个用户问题
        ↓
当前模型一次生成 8 个不同候选答案
        ↓
每个答案接受结构检查和 GPT-5.1 评分
        ↓
GRPO 比较同组候选谁更好
        ↓
提高高分候选的概率
```

论文的 GRPO 配置是：

- 每个 prompt 采样 8 个候选；
- sampling temperature 为 1.0；
- 训练 50 steps；
- 使用 **openai/gpt-5.1** 作为 judge；
- 最终奖励权重为：

```text
L1 结构和协议质量：0.2
L2 任务与交互构造：0.4
L3 用户体验质量：0.4
```

turn467626view4

---

## 奖励先过硬门槛

以下情况直接得到零奖励：

- JSON 解析失败；
- 本来应该有 UI，但没有生成；
- A2UI 协议验证失败；
- 存在导致渲染失败的结构问题。

通过门槛后，才计算：

```text
Reward =
0.2 × L1
+ 0.4 × L2
+ 0.4 × L3
```

turn467626view2

---

## L1 是程序算的

L1 包括：

- JSON 是否可解析；
- schema 是否正确；
- ID 引用是否完整；
- 必需字段是否存在；
- 值格式是否正确；
- 是否可渲染。

这部分比较可靠，因为它相当于编译器和单元测试，不依赖模型的审美判断。turn467626view2

---

## L2 和 L3 是 GPT-5.1 打分的

### L2：界面是不是“做对了事情”

GPT-5.1 会看：

- 这轮是否应该出现 UI；
- 控件类型和意图是否匹配；
- UI 内容是否来自回复，而不是瞎编；
- data model 是否使用合理；
- 用户操作后是否有完整的下一步动作。

### L3：界面是否“值得出现”

GPT-5.1 会判断：

- UI 是否比纯文字更省事；
- UI 出现得是否自然；
- 是否信息太多、控件过载。

作者为每项都提供了 0–5 分的详细 rubric、扣分规则和场景特定示例，judge 还必须返回一条证据说明。turn887905view2

例如，L3 中有非常具体的规则：

> 如果 UI 只是把文字塞进 Card，而没有增加交互价值，Value-Add 应直接降到低分。

以及：

> 同时展示超过四个独立交互组件或八个选项，会因为认知负担被严格扣分。

# 六、LLM-as-judge 真的靠谱吗？

我的判断是：

> **它适合做大规模、低成本的相对评估，但不足以单独证明真实用户体验。**

## 相对靠谱的部分

### 1. 它没有让 LLM 判断所有东西

结构正确性 L1 是确定性程序检查，而不是 LLM 说“看起来像合法 JSON”。

这避免了最明显的问题：

```text
非法输出
→ judge 心软
→ 仍然给高分
```

### 2. Rubric 写得比较具体

不是笼统问：

> 这个 UI 好不好？

而是逐项判断：

```text
是否该触发 UI？
组件是否匹配？
有没有完整 action？
是否比文字更省事？
信息是否过载？
```

这种窄问题通常比让模型给一个“整体美观分”稳定。

### 3. 输出格式有严格校验

judge 必须输出所有维度、数字必须在 0–5 范围内。格式错误会重试，最多三次。开源代码也不允许缺项后自行填默认分。turn806677view5

---

## 但它仍然有三个明显风险

### 风险一：RL 和最终评价都高度依赖同类 judge

GRPO 用 GPT-5.1 提供 L2/L3 奖励，开源 benchmark 的默认 judge 同样是 GPT-5.1。turn238869view0

这就像：

> 平时训练时一直迎合某位老师的评分标准，最后考试还是这位老师批卷。

模型可能学会的是：

- 什么答案更符合 GPT-5.1 的 rubric；
- 什么 JSON 描述会让 GPT-5.1 觉得自然；
- 如何在没有真实用户的情况下获得“用户体验高分”。

它不一定等价于真实人类更喜欢。

---

### 风险二：L3 本质上是主观 HCI 判断

例如：

- UI 是否真的降低认知负担；
- 交互出现得是否自然；
- 用户是否觉得比文字省事。

这些问题仅看 JSON 很难完全判断。

GPT-5.1 不会真的：

- 点击滑块；
- 犹豫选择；
- 忘记之前的内容；
- 因过多步骤而放弃；
- 产生真实的理解偏差。

所以 L3 更像是**基于设计准则的代理指标**，而不是用户体验本身。

---

### 风险三：论文没有报告 judge 与人类的一致性

我没有在论文或开源协议中看到：

- 人类标注员对同一批结果评分；
- GPT-5.1 与人类的 Pearson/Spearman 相关性；
- Cohen’s κ 或 inter-rater agreement；
- 多个不同 judge 模型之间的一致性；
- judge bias 或 position bias 分析。

论文也没有报告正式的用户实验或人工偏好研究。turn467626view6

因此，它证明的是：

> 模型在作者定义、GPT-5.1 执行的 Generative UI rubric 下得分提高。

还不能强地证明：

> 真实用户使用它时，效率、满意度和理解一定提高。

# 一句话评价这套方法

> **它的数据工程和自动验证做得很系统，足以证明模型学会了稳定生成 A2UI；但“这个 UI 对真实用户到底好不好”主要还是由另一个大模型判断，人的 grounding 明显不足。**

- renderability；
- component/action completeness。

## 为什么参数量看起来奇怪？

因为前两者是 **MoE（Mixture of Experts，混合专家）模型**。

普通稠密模型可以粗略理解为：

> 每生成一个 token，几乎所有参数都参与计算。

MoE 则像一家有很多专科医生的医院：

> 医院总共有 30B 或 235B 的“知识容量”，但每个病人只会被路由给其中少数几个专家。

所以：

```text
Qwen3-30B-A3B
总参数：30B
实际每次激活：约 3B
```

```text
Qwen3-235B-A22B
总参数：235B
实际每次激活：约 22B
```

这里的 `A3B` 和 `A22B` 就是 **Activated Parameters**。因此，235B 并不意味着每生成一个 token 都要做一个 235B 稠密模型那么多的计算。官方 Macaron 模型卡也明确将 Tall 和 Grande 分别绑定到这两个 Qwen3 checkpoint。turn966558view1

## 754B 是什么？

754B 对应的是 **GLM-5.1**，不是 Qwen3。GLM-5.1 官方模型页标注为 754B 参数，并将模型架构标记为 MoE；Macaron-A2UI-Venti 是挂在这个基座上的 LoRA adapter。turn774383view0

所以论文里写：

> trained 30B, 235B and 754B models

更准确的理解不是“作者自己从零训练了三个这么大的模型”，而是：

```text
已有 Instruct 基座
    ↓
LoRA SFT
    ↓
LoRA + GRPO
    ↓
Macaron-A2UI adapter
```

作者只更新少量 LoRA 参数。模型卡显示 LoRA rank 为 16、alpha 为 32，目标模块包括 attention 和 FFN 中的投影层，LM head 没有适配。turn966558view1turn774383view0

## 三个名字怎么对应？

它用了类似咖啡杯尺寸的命名：

```text
Tall   → Qwen3 30B-A3B
Grande → Qwen3 235B-A22B
Venti  → GLM-5.1 754B
```

有一个值得注意的小问题：论文正文主要清楚报告了 Qwen3 两档的训练设定，而 Hugging Face 模型卡进一步给出了 Venti 到 GLM-5.1 的对应关系。模型卡里个别表格存在把 variant 写错成 Tall 的复制粘贴错误，但 foundation checkpoint、加载代码和模型树都一致指向 `zai-org/GLM-5.1`。turn774383view0

# SaC 到底做了什么？

SaC 是 **Software as Content: Dynamic Applications as the Human-Agent Interaction Layer**，2026 年 3 月发布的预印本。

它首先认为聊天界面有三个结构性问题：

1. 复杂、结构化的信息被压成线性文字；
2. 用户每一轮都面对一个空输入框，不知道可以做什么；
3. 任务状态埋在不断增长的聊天记录里，缺少持续、可操作的表示。

它提出的解决办法是：

> 不要让 Agent 每轮只返回一段文字或者一个临时组件，而是动态生成一个持续存在的应用，让用户和 Agent 整个任务期间都通过这个应用交互。

举个例子，用户规划旅行。

普通聊天：

```text
用户：帮我规划东京旅行
Agent：这里有几个酒店……
用户：便宜一点
Agent：这里有几个更便宜的……
用户：第二个离地铁多远？
……
```

SaC 希望变成一个持续演化的旅行 App：

```text
东京旅行
├── 日期
├── 地图
├── 酒店卡片
├── 价格筛选
├── 每日路线
└── 预订操作
```

用户拖动预算、选择酒店或修改日期，这些 UI 操作直接变成结构化指令，触发 Agent 搜索、计算或调用服务；Agent 的执行结果再回来更新应用。

论文甚至明确说：

> 在这个模式中，Agent 充当后端，用户的每次界面操作都可以直接触发 Agent 执行。

所以你觉得像，不是错觉。

# 你关心的三个核心概念，它到底有没有？

## 1. Agentic UI 作为人与 Agent 的交互层

**有，而且这是它最核心的贡献。**

SaC 不只是说“Agent 可以生成 UI”，而是强调：

```text
不是：
Agent → 生成一个 UI 结果 → 用户看完继续聊天

而是：
用户 ↔ 持续存在的动态应用 ↔ Agent
```

这个应用不是一次性的输出，而是任务生命周期中的共享、持续、可操作状态。论文把这个区别总结为：

> 普通 GenUI 是 artifact-as-output；SaC 是 artifact-as-medium。

即界面不再是回答，而是交流媒介。

**这一点我们不能再拿来当 novelty。**

---

## 2. 用户操作 Agentic UI，Agent 在后台执行

**有，而且写得非常明确。**

SaC 中，按钮、筛选器、选择器和滑块不是装饰。这些交互会：

```text
用户操作控件
→ 形成结构化指令
→ Agent 执行
→ 获得新结果
→ 更新动态应用
→ 暴露新的操作
```

所以“用户不再写 Prompt，而是直接操作 UI，Agent 在后台干活”也已经被 SaC 正面覆盖。

不过这里还有一个重要区别：

> SaC 说的是广义 Agent execution，可能包含搜索、计算、数据库和工具调用。它引用了 GUI Agent / Computer Use 的发展，但没有把“通过 GUI Agent 操作多个既有长尾软件”作为核心技术对象。

换句话说：

- **Agent 是 UI 后端：SaC 有。**
- **GUI Agent 是连接任意既有软件的执行后端：SaC 没有作为核心证明。**

但仅凭“我们用了 GUI Agent，不是 API Agent”，区别还不够强。审稿人很可能认为这只是 SaC 的一种执行实现。

---

## 3. 跨应用的实时任务投影层

这里是最关键的。

**SaC 有宽泛的 Human–Agent–Environment 三方模型，也允许 Agent 连接外部信息和服务；但是它没有把“多个已运行应用的实时状态投影”作为核心研究问题。**

我在论文中没有看到它系统性处理以下问题：

- Calendar 中的会议、TaskBoard 中的 milestone 和 Docs 中的发布日期，是否对应同一个任务变量；
- 一个 UI 字段具体绑定到哪些既有软件对象；
- 底层状态是否是实时读取，而不是 Agent 生成或会话中累积的数据；
- 用户修改一个字段后，是否完整传播到所有相关应用；
- 是否误改了无关对象；
- 应用被其他人修改后，动态 UI 能否重新同步；
- 是否有独立 verifier 检查 UI 和真实应用最终状态是否一致。

SaC 的 stated evaluation 是 selection、exploration 和 execution 场景的 scenario-based evaluation，主要证明这种交互范式有表达力、技术上可行；它没有把跨应用 binding、round-trip fidelity 或 reconciliation 作为核心指标。

所以：

> **“跨应用”可以被 SaC 的宏观框架容纳，但“跨应用实时投影的语义正确性”没有被它做透。**

---

# 最本质的区别：谁才是 source of truth？

这是我认为最能救活我们方向的一刀。

## SaC：生成的应用本身就是任务状态

SaC 明确说：

> application itself becomes the interaction state。

用户和 Agent 都围绕这个持续演化的应用工作。这个 App 保存上下文、选项、用户选择和 Agent 结果，是双方共享的任务空间。

可以画成：

```text
用户
 ↕
Agentic Application
 ↕
Agent
 ↕
外部数据与服务
```

它关心的是：

> 如何让动态应用成为比聊天更好的交互媒介？

---

## 我们：生成的界面不能成为 source of truth

我们的工作台只应该是一个**投影**。

真实状态仍然存在于：

```text
Calendar
TaskBoard
Docs
Mail
其他人正在编辑的软件
```

任务工作台只是从它们中抽取出来的一层：

```text
多个真实应用
      ↓ 读取、对齐、压缩
任务工作台
      ↓ 用户修改
多个真实应用
      ↓ 重新读取、验证
任务工作台
```

也就是说：

> **SaC 的应用是任务状态本身；我们的应用是分布式真实软件状态的一个缓存式、可执行投影。**

因为它只是投影，所以天然会出现 SaC 没有重点解决的问题：

- 投影会不会遗漏重要内容？
- 投影会不会过期？
- 一个任务变量绑定了错误对象怎么办？
- 两个应用中的值冲突怎么办？
- 用户改了以后，只改成功三个应用中的两个怎么办？
- 外部软件被其他人修改以后怎么办？

这些问题构成了我们真正的技术和 HCI 张力。

## SaC

```text
用户提出目标
      ↓
Agent 生成动态应用
      ↓
用户操作 UI
      ↓
Agent 获取信息 / 执行工具
      ↓
动态应用继续演化
```

核心问题：

> 动态软件能否替代聊天，成为持续的人—Agent 交互媒介？

## 我们应该做的版本

```text
多个既有应用的 live state
      ↓
跨应用实体和状态对齐
      ↓
生成任务级投影
      ↓
用户修改任务变量
      ↓
编译成多个 GUI / tool 操作
      ↓
操作真实应用
      ↓
独立 verifier 读取最终状态
      ↓
发现遗漏、冲突和不一致
      ↓
重新同步任务投影
```

核心问题：

> 一个被极度简化的任务界面，怎样仍然忠实地反映并控制复杂的真实软件世界？

# 我们应该怎样重新定义论文？

不要再以 **“Agentic UI 是新的交互层”** 为主要问题。

把论文中心正式改成：

## **Task Projection Fidelity**

也就是：

> 如何将多个既有应用中的实时状态压缩成一个简单任务界面，同时保持状态完整、绑定正确、写回一致，并在外部变化后重新对齐？

这样 SaC 成为我们的上位范式，而不是竞争对手：

```text
SaC：
为什么动态应用可以成为人—Agent 交互媒介？

当动态应用代表多个既有软件时，
如何确保这种表示是可信、可执行、可验证的？
```

这就像：

- SaC 提出“自动驾驶是新的驾驶范式”；
- 我们研究“自动驾驶的地图和真实道路怎样保持一致”。

不是同一个 contribution。

# 必须真正做出的技术差异

仅仅在 Related Work 里说“我们连接真实应用”不够。系统和实验必须把区别做实。

## 1. 从既有软件反向生成，而不是从用户 Prompt 正向生成

输入必须包含：

- 应用当前状态；
- DOM / accessibility tree；
- 截图；
- tool schema；
- Agent 执行轨迹；
- 应用对象 ID 和状态。

输出是跨应用 task graph。

---

## 2. 每个 UI 变量都必须有具体 binding

例如：

```text
任务变量：release_date

绑定到：
Calendar.event_17.start_time
TaskBoard.milestone_4.deadline
Docs.document_12.release_date
Mail.draft_8.body.date
```

不能只说“发布日期是 8 月 14 日”。

---

## 3. 用户编辑以后必须真实写回

```text
release_date: Aug 14 → Aug 18
```

应该引起：

```text
Calendar event 修改
TaskBoard deadline 修改
Docs 内容修改
Mail draft 修改
```

而且不能修改无关会议和其他项目。

---

## 4. 必须有独立 verifier

不能由 Agent 自己说：

> 已经修改成功。

需要直接读取真实状态，检查：

- propagation completeness；
- binding accuracy；
- non-interference；
- cross-app consistency；
- round-trip fidelity。

---

## 5. 必须处理外部变化

例如同事直接在 TaskBoard 修改 deadline：

```text
真实软件变化
→ 工作台发现自己过期
→ 更新对应状态
→ 标出与发布日期冲突
```

这一步会非常明显地区分 SaC 的“持续应用状态”和我们的“外部世界投影”。

# 重新定义：不是生成应用，而是虚拟化任务

SaC 从聊天界面的局限出发：线性文字不适合结构化任务、自然语言输入成本高、聊天缺少持续状态，因此让 Agent 动态生成一个应用，作为人与 Agent 的共享交互媒介。它的构造方向基本是：

```text
用户目标 / 对话
        ↓
Agent 理解当前需要
        ↓
生成并演化一个动态应用
        ↓
用户通过应用继续指导 Agent
```

所以 SaC 的基本单位仍然是：

> **Agent 为当前人机交互生成的软件。**

论文确实明确把动态 agentic application 定义为主要的人—Agent 交互媒介，并让它随交互持续演化。citeturn682666academia2

而你的构造方向是：

```text
Calendar / Jira / Docs / Mail / 手机 App
        ↓
GUI Agent 读取状态与可操作能力
        ↓
跨应用实体、变量与依赖对齐
        ↓
形成一个与具体 App 无关的任务状态机
        ↓
把任务状态机呈现为可玩的任务界面
        ↓
用户修改任务语义
        ↓
GUI Agent 编译成不同应用、不同设备上的动作
```

所以你的基本单位不是“生成的软件”，而是：

> **被 GUI Agent 从多个真实软件中虚拟化出来的任务。**

# 最有力的新范式：Task Virtualization

我建议暂时把这个范式称为：

## **CUA-mediated Task Virtualization**
### GUI Agent 驱动的任务虚拟化

可以把它类比成 JVM，但映射关系要讲得非常清楚。

| Java / 虚拟机 | 你的系统 |
|---|---|
| 不同硬件和操作系统 | 不同应用、窗口、设备和 UI |
| JVM | GUI Agent 运行时 |
| 字节码与统一对象模型 | 跨应用任务状态与语义操作 |
| Java 程序 | 用户面对的任务界面 |
| JVM 将字节码编译到机器指令 | Agent 将任务修改编译成 GUI/tool actions |
| 运行时保证一致性 | Verifier 检查真实应用状态并重新同步 |

最重要的变化是：

> 用户不再使用某个 App，也不再管理 Agent 的操作步骤；用户直接操作一个被虚拟化的任务。

这才是你的新 CUA 交互范式。

---

# 交互模型：Lift → Play → Compile → Reconcile

不要继续采用 SaC 那种“用户—动态应用—Agent”的三角图。

你的模型应该是一条明显从下至上的循环：

## 1. Lift：从软件世界提升任务语义

GUI Agent 观察：

- 当前页面和窗口；
- 应用中的对象与字段；
- 跨应用已有状态；
- 可执行的 GUI 或工具能力；
- Agent 已经完成的轨迹。

然后把底层细节提升成任务对象：

```text
Calendar Event #721
Jira Milestone #14
Docs Release Plan
Mail Draft #93

          ↓ Lift

Beta Release
- release_date
- test_deadline
- owner
- blockers
- notification_status
```

这是**反向编译**，不是从 Prompt 凭空生成内容。

---

## 2. Play：用户直接“玩”任务状态

用户看到的不是应用窗口，也不是 Agent 日志，而是一个可直接操纵的任务世界。

例如：

```text
Beta Release

发布日期     [ Sep 3 ─────●──── Sep 10 ]
测试截止     Sep 5
文档截止     Sep 6
阻塞问题     2
通知状态     Draft
```

用户把发布日期拖到 Sep 8。

系统立即显示即将产生的连锁变化：

```text
发布日期           Sep 3 → Sep 8
发布会议           Sep 3 → Sep 8
测试截止           Sep 5 → Sep 6
文档截止           Sep 6 → Sep 7
通知草稿中的日期   Sep 3 → Sep 8
```

这不是“填写表单”，而更像一个**任务模拟器或游戏盘**：用户移动一个有语义的对象，系统世界产生物理般的联动。

---

## 3. Compile：把任务修改编译到底层应用

用户表达的不是：

> 打开 Calendar，修改第三个日期框，再进入 Jira……

而是：

```json
{
  "task": "beta_release",
  "variable": "release_date",
  "new_value": "Sep 8"
}
```

GUI Agent 运行时把这一个修改编译成：

```text
Desktop Calendar：移动会议
Web TaskBoard：修改 milestone 与 dependent tasks
Docs：更新发布计划正文
Mail：更新通知草稿
Phone messaging app：保持未发送
```

不同的应用组合可以产生完全不同的执行轨迹，但对用户暴露的是同一个任务操作。

---

## 4. Reconcile：底层世界变化后重新对齐

执行完成后，系统不是让 Agent说“已完成”，而是重新读取真实应用：

```text
Task Surface
      ↑
验证与重新投影
      ↑
多个真实应用的最终状态
```

如果只改成功三个应用中的两个，任务界面要显示部分失败。

如果同事随后直接在 Jira 修改了测试截止时间，任务界面也要更新，并显示新的冲突。

这使它不是 SaC 式的“持续动态应用”，而是一个类似数据库 materialized view 的**实时任务投影**。

---

# 最本质的差异不是 top-down / bottom-up 本身

“一个从上往下，一个从下往上”是很好的直觉，但论文里还需要更硬的区分。

## 差异一：抽象对象不同

**SaC：**

```text
Agent 动态生成的应用
```

**你：**

```text
由多个已有应用虚拟化出来的任务机器
```

---

## 差异二：Agent 的角色不同

**SaC 中的 Agent：**

- 生成和更新应用；
- 响应用户对应用的操作；
- 获取数据、调用工具；
- 是动态应用的智能后端。

**你这里的 GUI Agent：**

- 是跨应用运行时；
- 发现底层软件对象和能力；
- 建立跨应用 binding；
- 将统一任务操作编译到不同软件；
- 处理同步、故障和外部变化。

所以不只是：

> Agent 在 UI 后面执行任务。

而是：

> **Agent 把不兼容的应用世界虚拟化成统一的任务计算环境。**

---

## 差异三：UI 的身份不同

**SaC 的 UI 是新生成的软件。**

**你的 UI 是虚拟任务机器的一种显示和控制表面。**

这意味着同一个任务机器可以在不同设备上产生不同表面：

```text
桌面：完整依赖图与执行预览
手机：几个关键状态和批准动作
手表：阻塞或异常通知
大屏：团队项目态势
```

UI 只是 projection，不是系统本体。

---

## 差异四：底层能否被替换

这是你应该重点证明的“JVM 时刻”。

假设任务界面是：

```text
项目发布
发布日期 / 会议 / 任务 / 文档 / 通知
```

实验一的底层组合是：

```text
Google Calendar + Jira + Google Docs + Gmail
```

实验二换成：

```text
Outlook Calendar + Linear + Notion + Outlook Mail
```

如果用户看到的任务界面和可执行语义基本不变，只是 GUI Agent 的底层执行轨迹变化，那么你就真正证明了：

> **任务交互与应用实现发生了解耦。**

SaC 不要求证明这一点。

# 用一个“炫酷但有论文意义”的 Demo 把差异打出来

## Demo：Release Mission Control

不是普通 dashboard，而是一个可以操作和播放的任务世界。

### 第一幕：自动形成任务世界

屏幕上同时运行：

- Calendar；
- TaskBoard；
- Docs；
- Mail；
- 手机上还有 Messaging App。

GUI Agent 自动识别这些应用中的关联对象，中心逐渐形成一张任务盘：

```text
Beta Release
  发布日期
  负责人
  测试状态
  文档状态
  会议
  公告
  阻塞依赖
```

导师能看到任务盘不是 Prompt 生成出来的，而是从正在运行的软件中“长出来”的。

---

### 第二幕：把执行变成“玩”

用户直接拖动时间线上的 Release 节点。

相关节点像物理系统一样联动：

- 会议向后移动；
- deadline 自动调整；
- 产生一个依赖冲突；
- 邮件草稿日期改变；
- 一个已完成任务保持不变。

系统先显示半透明的“未来世界”，类似游戏中的行动预览。

用户点击：

> Execute this world state

然后四个应用窗口中的 Agent 同时开始工作。

用户操作的是**世界状态**；Agent 操作的是**软件界面**。

---

### 第三幕：应用替换

演示中途把 Jira 换成 Linear，或者把桌面 Calendar 换成手机 Calendar。

中心任务盘不消失，用户也不需要重新学习。

系统重新寻找 binding，并继续执行。

这一幕会非常直观地表现：

> 任务界面不是某几个 App 拼出来的 dashboard，而是独立于 App 的虚拟交互层。

---

### 第四幕：外部世界反向影响

让“同事”直接在 TaskBoard 中修改某个 deadline。

中心任务盘实时变化，并标出：

```text
测试截止距离发布只剩一天
```

用户可以在任务盘中选择：

- 推迟发布；
- 提前测试；
- 保留冲突并通知负责人。

这证明它是双向同步的任务世界，而不是 Agent 自己维护的一份 UI 副本。

# 新范式的论文表述

我建议把主要 claim 写成下面这种形式，而不是继续说 Generative UI：

> **We introduce CUA-mediated task virtualization, a bottom-up interaction paradigm that lifts state and capabilities from heterogeneous live applications into a substrate-independent task machine. Users directly manipulate task semantics through a playable task surface, while a CUA runtime compiles these manipulations into application- and device-specific actions and continuously reconciles the virtual task state with the underlying software world.**

中文：

> **我们提出 GUI Agent 驱动的任务虚拟化：一种自底向上的 CUA 交互范式。系统将异构真实应用中的状态和能力提升成与底层软件无关的任务机器；用户通过可玩的任务表面直接操作任务语义，CUA 运行时再将其编译成具体应用与设备操作，并持续与真实软件世界保持一致。**

这和 SaC 的关键词看起来就已经非常不同：

| SaC | 你的范式 |
|---|---|
| Dynamic Applications | Virtualized Tasks |
| Software as Content | Applications as Substrate |
| Agent-generated application | CUA-lifted task machine |
| Application as interaction medium | Task surface as runtime view |
| Iteratively guide agent | Directly manipulate distributed task state |
| UI evolves from conversation | UI materializes from live software |
| Expressiveness / viability | Substrate independence / execution fidelity |

SaC 的出发点确实是聊天局限，并将动态应用作为交互媒介。citeturn682666academia2 你的范式应当把“聊天”降成可选输入，甚至在最强 demo 中完全不需要对话：系统可以从用户当前打开的应用和任务状态直接形成任务表面。

# 但需要正视真正更接近的工作：AOHP

这个重构能明显区别 SaC，但会更接近 AOHP 一类 agent-native OS 工作。

AOHP 已经把 Agent 视为 OS 的一等执行者，强调个性化服务组合、Agent 友好的接口、适应性 UI，以及跨应用和数据源的任务执行。citeturn682666academia0

因此你的区别不能停在：

> GUI Agent 统一多个服务和 App。

你必须把中心放在 AOHP 没有主要研究的地方：

- 任务状态如何从 live GUI 中被提升；
- 用户怎样直接操纵虚拟任务状态；
- 一个任务 edit 如何跨不同底层应用保持语义等价；
- 底层应用能否互换；
- 投影是否完整；
- 执行是否产生无关变化；
- 外部修改后怎样 reconcile；
- 用户是否因为这个表面更容易理解和控制任务。

AOHP 更像 Agent OS harness；你的目标是**一种人可直接操纵的任务虚拟化交互模型**。

# Sidekick 到底做了什么？

Sidekick 的出发点是：

> 用户把任务交给 CUA 后，自己去做别的事情；那他怎么知道 Agent 有没有卡住、做到了哪里、回来后发生了什么？

论文做了三个阶段的反馈设计。

## 1. Agent 在后台：让我余光知道它有没有出事

用户在前台做数学题，CUA 在后台填写表格。

屏幕边上有一个常驻小窗口：

```text
绿色：正常执行
黄色：连续出现少量错误
橙色：问题正在积累
红色：可能卡住，自动暂停
```

除了颜色，还会显示一句状态摘要和截图缩略图。

它用 VLM 比较每一步执行前后的截图，判断结果是否符合当前子目标；连续错误达到不同阈值后改变颜色，红色时自动暂停。这里用的是 `gemini-2.5-flash` 做状态判断。

---

## 2. 用户回来：不要让我读五十行日志

用户重新切回 CUA 时，Sidekick 不要求他滚动阅读全部聊天和点击记录，而是生成一段多模态回顾：

```text
Agent 打开了参考表格
→ 填完了前两列
→ 在第三列输入错了一个位置
→ 随后进行了修正
```

系统一边语音讲解，一边重放对应截图和点击位置，并用颜色表示动作的新旧程度。总结播放期间，CUA 会暂停，等用户看完再继续。

---

## 3. Agent 在前台：把推理和动作“演出来”

当用户正在看 Agent 操作时，Sidekick会：

- 读出 Agent 当前的计划；
- 高亮 Agent 所说的 GUI 对象；
- 标记点击位置；
- 显示键盘输入；
- 配上点击、打字等音效。

也就是把：

```text
“我发现 B 列为空，
接下来点击 D2，
然后输入 15。”
```

同步变成语音、方框、点击标记和声音。系统基于 Claude Sonnet 4.5 的 CUA，在 macOS 虚拟机里执行；Gemini 负责把文本消息转换成带时间标记的多模态反馈。

# 它的实验其实比较聚焦

作者做了一个 30 人实验：

```text
前台主任务：做两位数加减法
后台辅助任务：让 CUA 填电子表格
```

四个条件分别是：

1. 人自己完成两个任务；
2. CUA + 普通聊天日志；
3. CUA + 边缘文字状态；
4. CUA + 完整 Sidekick。

为了确保用户确实需要监控，实验里的 CUA 会被要求故意产生一些随机错误。

结果上，Sidekick 的表格任务得分显著高于普通聊天和边缘文字，也把平均错误数从聊天条件的 2.51、边缘文字的 2.32，降低到了 1.31；同时没有显著增加用户切换窗口或监控 Agent 的时间。

不过要冷静看：

- Sidekick 总分相较普通聊天只是边缘显著趋势，`p=.079`；
- Trust、confidence 和易用性没有显著提升；
- 有些参与者觉得语音、颜色、动画同时出现太吵、容易分散注意力；
- 真正显著的优势主要是发现表格错误和及时干预。turn975454view1

所以它是一篇很扎实的 **multitasking + awareness + multimodal feedback** 论文，但没有验证复杂跨应用任务抽象。

# 最关键的一句话：它明确不是执行层

论文自己特别澄清：

> **Sidekick 不是 Agent，也不是 CUA；它不在电脑上执行动作，只向用户提供反馈。**

这句话几乎直接替我们划出了边界。

- 多个 Agent 在多个 workspace 中工作；

- 显示跨 Agent 的冲突和依赖；
- 把低层轨迹转换成结构化报告；
- 汇总重要行为、风险和用户干预。turn273059view1

那是真的危险。

# 但它和我们最本质的问题仍然不同

## Sidekick 的问题

它解决的是：

# **注意力与沟通问题**

用户仍然在监督 Agent。

---

## 我们的问题

> GUI Agent 能否把多个异构应用中的状态和能力提升成一个与应用无关的任务机器，让用户直接修改任务语义？

它解决的是：

# **抽象与控制问题**

用户不是监督 Agent 怎么做，而是在规定软件世界应该变成什么样。

我们此前已经明确把系统冻结成了“人操作任务，Agent 操作应用”，并要求任务界面与真实软件之间形成状态读取、语义修改、执行和验证的闭环。fileciteturn0file1L15-L24

# 最本质的四个区别

| | Sidekick | TaskVM |
|---|---|---|
| 界面代表什么 | Agent 正在做什么、做过什么 | 软件世界当前是什么状态 |
| 用户操作什么 | 暂停、恢复、查看摘要、发现错误 | 日期、预算、负责人、依赖等任务语义 |
| 系统是否执行 | 不执行，只提供反馈 | 将任务修改编译并执行到底层应用 |
| Agent 的角色 | 被监控、被解释的执行者 | 虚拟化异构应用的运行时 |

最容易记住的表达是：

> **Sidekick 的界面是 Agent 的仪表盘。**
> **我们的界面是软件世界的控制台。**

再深一层：

> **Sidekick 压缩的是 actions；我们压缩的是 applications。**

Sidekick 把一百个动作压缩成一句：

```text
Agent 已经填完两列，但第三列出现错误。
```

我们把四个应用压缩成一个变量：

```text
release_date = Sep 8
```

用户修改它之后，四个应用都要发生正确变化。

# 它的“错误检测”也不是我们的 verifier

这一点非常容易混淆。

Sidekick 确实有一个 VLM 检查机制：

```text
执行前截图
+
执行后截图
+
当前子目标
        ↓
这一动作是否看起来出错？
```

然后累计连续错误次数，决定显示绿色、黄色还是红色。

但这是一个 **action-level monitoring signal**。

我们的 verifier 必须检查：

```text
用户把发布日期改到 9 月 8 日以后：

Calendar 会议是否改到了 9 月 8 日？
Jira milestone 是否改到了 9 月 8 日？
Docs 中的发布日期是否更新？
邮件草稿是否更新？
无关会议是否保持不变？
四个应用现在是否一致？
```

这是 **task-state semantic verification**。

前者回答：

> Agent 这一步看起来是不是卡住了？

后者回答：

> 用户要求的软件世界是否真的被完整而无副作用地改变了？

不是同一个 verifier。

- **SaC**：从人—Agent 对话出发，生成持续交互的应用；

这比只说“他们是 top-down，我们是 bottom-up”更硬，因为它同时指出了：

3. 用户对 UI 有什么权力；
4. 操作最终落到哪里。

# Sidekick 对我们真正造成的限制

以后以下表述不要再作为贡献：

- 将 CUA 轨迹转换成易理解的反馈；
- 让用户不用一直盯着 Agent；
- 用颜色表示 Agent 是否卡住；
- 用户回来时自动总结 Agent 做过什么；
- 用截图和语音增强 Agent 透明度；
- 用一个统一界面显示多个 Agent 的进度；
- 把执行轨迹变成结构化报告；
- 让用户更及时发现并纠正 Agent 错误。

Sidekick 已经把这些做成了系统，并进行了 30 人实验。turn273059view2

这些可以成为 TaskVM 的辅助功能，但不能成为论文中心。

我们的用户实验可以不只对比普通聊天，而是比较三种交互层级：

2. Sidekick-style monitoring

这会回答一个非常漂亮的问题：

> **当 CUA 跨应用执行时，给用户更好的执行反馈就够了吗，还是用户需要一个可以直接操纵的任务级抽象？**

Sidekick证明了：

> 比普通聊天更好的反馈，可以改善用户发现错误的能力。

> 当任务跨多个应用时，用户不只是需要更好地看懂 Agent，还需要摆脱对 Agent 执行过程的监督，直接控制任务语义。

# 最终判断

**Sidekick 不是撞车，而是一条非常重要的边界线。**

它告诉我们：

> “让 Agent 更透明、更容易监控”已经足够成为一篇优秀 UIST 论文。

但也迫使我们必须证明 TaskVM 不是一个更豪华的监控器。

最稳的区分句是：

> **Sidekick turns agent execution into effective communication. TaskVM turns heterogeneous applications into a manipulable task machine.**

中文：

> **Sidekick 让用户更好地看懂 Agent 的执行；TaskVM 让用户不必管理 Agent 的执行，而是直接操纵由多个应用共同实现的任务世界。**

因此现在真正要守住的，不是“统一界面”“摘要”“控制感”这些泛化词，而是三个不可退让的属性：

```text
应用无关的任务语义
+
用户对任务状态的直接操纵
+
修改到底层软件的可验证往返
```

只要 demo 把这三件事做实，Sidekick 不仅不会吃掉我们，反而会成为一个非常好的对照：**它代表 CUA 时代更好的监督界面，而我们代表 CUA 时代从监督 Agent 转向直接操作任务的新交互层。**
