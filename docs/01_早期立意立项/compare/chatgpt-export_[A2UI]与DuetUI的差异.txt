## 一句话概括

**DuetUI 不是在训练一个新的基础模型，而是在提出一种新的“人—Agent共同生成界面”交互范式。**
它让 Agent 先把模糊任务拆解成可操作的界面，用户再通过点击、筛选、拖动、填写等操作修改界面；这些操作又被当作隐式意图反馈给 Agent，用于生成下一版任务结构和界面，由此形成一个持续迭代的**双向上下文循环**。论文已被 CHI 2026 收录。turn744523view0

# 1. 论文想解决什么问题？

传统的 LLM 任务系统主要有两种方式：

1. **全自动 Agent**：用户说一句话，Agent 自己完成任务。
   问题是用户意图常常不完整、会变化，而且用户很难中途干预。

2. **一次性生成 UI**：用户描述需求，模型直接生成一套界面。
   问题是用户通常无法一开始就准确描述最终需要什么，看到界面之后才会意识到自己还想改什么。

DuetUI 的基本观点是：

> 用户的意图不是一次性输入出来的，而是在“看到结果—操作结果—继续修改”的过程中逐渐形成的。

因此，界面不应只是 Agent 最后的输出，而应该成为**用户和 Agent 交流、协作和校准意图的共同媒介**。turn569711view1

# 2. 这篇论文具体做了哪些事情？

整篇工作大致分为三个部分。

## 2.1 前期形成性研究

作者先招募了 **12 名参与者**，让他们设计两类复杂日常任务的理想界面：

- 旅行规划；
- 搬到一个新城市。

参与者可以使用：

- Gemini 聊天与搜索；
- v0 类的自然语言 UI 原型工具；
- 记事本；
- 绘图画布。

研究采用远程、约 60 分钟、Think-Aloud 的方式，观察普通用户如何表达任务、修改设计和与 AI 协作。

形成性研究得到四个关键发现：

- 用户意图是逐渐浮现的，不是预先完整定义的；
- 黑箱式 AI 让用户不知道“它能做什么、应该怎样控制”；
- 用户经常把“任务要求”和“界面要求”混在一起表达；
- 用户希望控制权能动态切换：早期让 AI 多做，后期自己精细调整。

基于这些发现，作者提出了 DuetUI 的设计目标和六阶段工作流。turn761898view1

## 2.2 实现 DuetUI 原型

作者实现了一个可以动态生成、更新并执行任务型界面的 Web 系统，核心不是一次生成完整界面，而是：

- 分阶段理解任务；
- 把 Agent 能力做成可直接操作的组件；
- 同步维护任务结构和界面结构；
- 记录用户与 Agent 的全部操作；
- 根据操作历史推断用户不断变化的意图。

## 2.3 做两类实验

作者进行了：

- **技术评测与消融实验**：比较普通 GPT-4、没有循环的 DuetUI、完整 DuetUI；
- **24 人用户实验**：将 DuetUI 与 Google Stitch 进行对比。

# 3. DuetUI 的核心方法

## 3.1 六阶段共同生成流程

DuetUI 不做 one-shot generation，而是把过程划分为六个阶段：

| 阶段 | 作用 |
|---|---|
| Define | 获取用户的高层目标 |
| Empathize | 询问约束、偏好和细节 |
| Plan | 将需求拆成多个子任务 |
| Explore | 为当前子任务搜集数据、探索方案 |
| Refine | 调整具体参数和候选方案 |
| Duet | 人和 Agent 持续交替操作，完成任务 |



例如，用户说“我想去巴塞罗那旅行”：

- Define：确认是独自旅行、家庭旅行还是情侣旅行；
- Empathize：询问交通、预算、住宿偏好；
- Plan：拆成订交通、订住宿、安排景点等子任务；
- Explore：获取航班和住宿候选项；
- Refine：用户用价格排序、地图筛选等功能选择住宿；
- Duet：Agent 根据用户选择了圣家堂附近、低价住宿，推断其偏好，再推荐附近的低价文化景点并组织最终行程。

---

## 3.2 四个关键设计机制

### ① Staged Co-Generation：分阶段共同生成

系统不要求用户一次说清全部需求，而是在不同阶段生成不同的界面，让用户逐步补充和修改。

这解决的是“用户自己也不知道最终想要什么”的问题。

### ② Tangible Agency：可触摸、可操作的 Agent 能力

传统方式要求用户通过 Prompt 控制 Agent；DuetUI 则把 Agent 能力转换成具体组件，例如：

- 输入框；
- 单选、多选；
- 日期选择器；
- 按钮；
- 滑块；
- Dashboard。

用户不必说“请把住宿价格限制到 1000 欧元以下”，可以直接拖动预算滑块。组件既是操作工具，也是向 Agent 表达意图的中间语言。turn862060view0

### ③ Task–Interface Duality：任务—界面对偶

系统同时维护两棵对应的层级结构：

| 任务结构 | 界面结构 |
|---|---|
| Task | Navigation |
| Subtask | Page |
| Data | Component |

例如：

- “规划旅行”对应整个导航空间；
- “选择住宿”对应一个页面；
- “预算、评分、距离”对应页面中的滑块、卡片和筛选组件。

这样，任务语义的改变可以比较明确地映射到界面改变，而不是让 LLM 自由生成一整段不可控代码。turn862060view0

### ④ Bidirectional Action History：双向操作历史

系统记录：

- 用户点击了什么；
- 用户修改了什么；
- 用户选中了哪些候选项；
- Agent 搜索或推荐了什么；
- 界面发生了什么变化。

这些记录既用于向用户展示 Agent 的行为，也被送回 Agent 作为下一轮推理上下文。

例如，用户点击住宿模块并选择“B&B”，系统不只是更新一个筛选标签，而是推断：

> 用户正在修改住宿任务，并明确偏好民宿；后续数据范围和界面展示都应该改成民宿。

# 4. 系统架构和 Agent 是怎么组织的？

DuetUI 是一个三层、多 Agent 架构。

## 4.1 Core Layer：基础层

包含三个管理器：

- **MemoryManager**：为任务分配 session ID，以键值形式存储状态；
- **LLMManager**：负责 Prompt 组装、模型调用、重试和 JSON 解析；
- **SchemaManager**：用 Pydantic 约束不同 Agent 之间的数据结构。

SchemaManager 很重要，因为多个 Agent 的输出必须稳定地组成任务树和 UI 树，而不能每次生成完全不同格式的自然语言。

## 4.2 Context Layer：上下文层

ContextManager 是系统的“共享黑板”或单一状态源，主要保存：

```text
ContextState = {
    TaskStage,
    TaskDecomposition,
    InterfaceDescription,
    ActionHistory
}
```

也就是：

- 当前处于六个阶段中的哪一步；
- 当前任务如何分解；
- 当前界面由哪些页面和组件组成；
- 用户与 Agent 到目前为止做了什么。

turn862060view1

## 4.3 Agent Layer：Agent 层

共有四个专门 Agent：

- **TaskAgent**
  维护任务、子任务和数据三级结构。

- **InterfaceAgent**
  将任务结构转换成导航、页面和组件等 UI 描述。

- **ServiceAgent**
  获取任务需要的数据。论文原型中的外部服务主要是由 LLM 模拟，并非完整接入真实服务 API。

- **RenderingAgent**
  将结构化的 InterfaceDescription 转换为可交互 Web 界面，使用 Vue.js 和 Element Plus。

# 5. “双向上下文循环”具体如何运行？

可以把一次循环抽象成：

```text
用户操作
   ↓
写入 Action History
   ↓
TaskAgent 根据任务结构和操作历史推断意图
   ↓
更新 Task Decomposition
   ↓
ServiceAgent 获取或模拟所需数据
   ↓
InterfaceAgent 根据新任务和历史生成 Interface Description
   ↓
RenderingAgent 更新真实界面
   ↓
用户看到新界面并继续操作
```

论文将其分成两个连续过程。

## Task Loop

负责更新“任务语义和数据”。

例如用户选择 B&B：

1. 操作被写入历史；
2. TaskAgent 判断这是住宿偏好的明确变化；
3. 更新住宿子任务；
4. ServiceAgent 获取 B&B 类型的数据。

## Interface Loop

负责更新“这些任务变化应该如何显示”。

1. InterfaceAgent读取新任务结构和操作历史；
2. 判断 B&B 更适合图片丰富的卡片，而非普通酒店列表；
3. 生成新的 InterfaceDescription；
4. RenderingAgent 更新页面。

所以用户不是在编辑一个静态 UI，而是在通过操作 UI 间接修改 Agent 对任务的理解。turn862060view1

# 7. 技术实验是怎么做的？

## 7.1 测试任务

作者构建了 10 个复杂日常任务，包括：

- 周末独自旅行；
- 面试准备；
- 团建活动；
- 手机比价；
- 学习手工技能；
- 月度预算分析；
- 健身计划；
- 家装计划；
- 宠物领养；
- 搬家计划。



GPT-4 为每项任务生成不同的用户画像和偏好，测试框架再模拟相应用户行为。一名资深 UX 设计师为每个场景标注理想任务结构和界面 Ground Truth。

## 7.2 三个实验条件

### Baseline：GPT-4

直接 Prompt 生成，没有中间结构、多个 Agent 或循环反馈。

### DuetUI No Loop

保留六阶段和四个 Agent，但删除 ContextManager，线性运行一次，不根据用户操作继续迭代。

### DuetUI Full Loop

完整系统，包含 ContextManager、操作历史和双向上下文循环。

这实际上是一种消融实验，用于回答：

> 提升来自多阶段、多 Agent 本身，还是来自“循环反馈机制”？

# 8. 技术评测指标

作者没有使用文本完全匹配，因为同一个任务可以存在多种合理 UI，而是采用**功能等价匹配**：

- **信息等价**：表达相同核心信息；
- **操作等价**：支持相同用户操作。

GPT-4 作为自动裁判，对生成结果与 Ground Truth 进行两次独立匹配，作者再人工复核。

评测层级包括：

- Task；
- Subtask；
- Data；
- Navigation；
- Page；
- Component。

主要指标为：

- Precision；
- Recall；
- F1；
- 跨层级加权的 W-F1；
- 两次评判一致性 Cohen’s κ。

此外，两名有五年以上经验的专家——资深 UX 设计师和前端工程师——以五点量表评价：

- Efficiency；
- Layout；
- Completeness；
- Aesthetics；
- Matching，即与用户意图的匹配程度。

# 9. 技术实验结果

## 9.1 Ground Truth 匹配

| 系统 | W-F1 |
|---|---:|
| GPT-4 Baseline | 0.277 |
| DuetUI No Loop | 0.459 |
| DuetUI Full Loop | **0.508** |

完整 DuetUI 在各层级的 F1 为：

- Subtask：**0.798**
- Data：**0.367**
- Page：**0.541**
- Component：**0.325**

自动评判的 Cohen’s κ 均超过 0.95。turn862060view2

值得注意的是，Full Loop 的 Recall 较高，但部分细粒度层级的 Precision 低于 No Loop。例如 Data 层：

- Full Loop：Precision 0.318，Recall 0.466；
- No Loop：Precision 0.435，Recall 0.312。

作者认为循环让系统生成了更多用户可能需要、但 Ground Truth 未明确包含的元素。另一种理解则是：**循环提高了覆盖率，但也可能导致过度生成。**

## 9.2 专家评分

总体评分：

| 系统 | Overall |
|---|---:|
| GPT-4 Baseline | 3.64 |
| DuetUI No Loop | 3.80 |
| DuetUI Full Loop | **4.11** |

Full Loop 各维度均最高：

- Efficiency：3.80；
- Layout：4.10；
- Completeness：4.15；
- Aesthetics：4.10；
- Matching：4.40。

其中完整性和总体质量相对 Baseline 达到显著改善。turn862060view2

# 10. 用户实验怎么做的？

作者招募了 **24 名参与者**，采用被试内设计，将 DuetUI 与 **Google Stitch** 比较。

每位参与者：

1. 从 10 个任务中选择一个自己感兴趣的；
2. 再随机分配两个任务；
3. 三个任务分别在 DuetUI 和 Stitch 上完成。

因此每人完成：

```text
3 个任务 × 2 个系统 = 6 次任务
```

总计得到：

- 144 份有效问卷；
- 25.86 小时屏幕和音频记录。

系统使用顺序进行了平衡，以降低学习效应。turn569711view5

# 13. 这篇论文真正证明了什么？

比较准确的结论是：

### 它证明得比较充分的

- 将任务拆解、结构化 UI 和用户操作历史结合起来，明显优于单次 GPT-4 生成；
- 双向循环不仅仅是多 Agent 的附加包装：Full Loop 优于 No Loop；
- 用户更愿意通过按钮、选择器、滑块等方式表达偏好，而不是反复写 Prompt；
- 早期阶段用户倾向让 Agent 主导，后期则倾向自己直接修改，说明动态控制权切换确实存在。

### 它尚未完全证明的

- 没有证明真实世界端到端任务成功率显著提高；
- 没有证明真实 API 调用、支付、预订等操作可靠；
- 没有证明整体任务时间显著缩短；
- 没有与更强的真实 GUI Agent 或人工构建 UI 进行完整比较。

# 14. 论文的主要局限

## 14.1 外部服务大量由 LLM 模拟

ServiceAgent 调用的外部服务在原型中主要通过 LLM 模拟，所以旅行价格、住宿信息、商品信息等并不等同于真实服务结果。用户实验中也出现了参与者把模拟信息视为事实错误，从而失去信任的问题。turn259852view7

## 14.2 技术评测存在模型自评问题

GPT-4 同时参与了：

- 用户画像生成；
- 数据集构造；
- Baseline；
- LLM-as-judge。

虽然作者做了双次评判、人工复核并报告较高 κ，但仍可能存在模型偏好或同源偏差。

## 14.3 Ground Truth 和样本规模有限

- Ground Truth 主要由一名资深 UX 设计师标注；
- 技术评测只有 10 个任务和 30 个最终输出；
- 形成性研究 12 人；
- 用户实验 24 人，且参与者主要为较年轻的校园人群。

因此结果更适合作为 proof-of-concept，而不是成熟通用系统的验证。

## 14.4 W-F1 仍然不高

完整系统的 W-F1 是 0.508，说明即使相对基线提升明显，它与人工 Ground Truth 之间仍然存在较大差距。尤其 Data 和 Component 层 F1 分别只有 0.367 和 0.325。

## 14.5 渲染器能力受组件库限制

系统紧耦合 Element Plus：

- 定制化视觉风格能力有限；
- 外部数据依赖无法完全支持；
- 存在 JSON 格式错误、编译失败、网络不稳定；
- 多操作同时发生时延迟较长；
- 有时无法捕捉较细微的隐式偏好。

论文记录了 5 次即使重试三次仍无法得到有效输出的生成失败。

# 15. 最核心的贡献应该怎样理解？

这篇论文最有价值的部分不是“用了 GPT-4o 还是 LLaMA3”，而是提出了一个很清晰的交互设计思想：

> **不要把 UI 看作 Agent 输出的最终产品，而要把 UI 看作人和 Agent 持续共享、持续修改的外部记忆和沟通语言。**

Agent 通过任务分解来生成界面，用户通过操作界面来“反向编程”Agent。
这种反馈不要求用户理解 Prompt Engineering，也不要求用户显式说出全部偏好。

所以 DuetUI 可以被概括成：

```text
LLM 多 Agent
+ 结构化任务树
+ 结构化 UI 树
+ 用户操作日志
+ 任务循环与界面循环
= 可持续迭代的任务型生成界面
```

它本质上是一篇**HCI 系统与交互范式论文**，而不是新的模型架构或训练算法论文。


【提问 轮数2】
没太懂，能不能给我形成一个易懂的心智模型

【回答内容 轮数2】
可以。把 **DuetUI** 想成：

# 一个“会跟着你操作不断改造自己的任务面板”

它不是普通聊天机器人，也不是一次性帮你生成一个网页。

更像是：

> **你和 AI 一起在一块会自动变化的白板上做事情。**

AI 负责先搭框架，你通过操作白板表达偏好；AI观察你的操作，再调整任务和界面。

---

## 最核心的心智模型：边做事，边改工具

普通 AI 的流程通常是：

```text
你写需求 → AI 猜你的意思 → 给出最终结果
```

DuetUI 的流程是：

```text
你说一个大概目标
    ↓
AI 生成一个可以操作的任务界面
    ↓
你点击、选择、拖动、修改
    ↓
AI 从你的操作中理解你真正想要什么
    ↓
AI 修改任务计划和界面
    ↓
你继续操作
```

也就是：

> **不是先把需求说清楚，再做任务；而是在做任务的过程中，需求逐渐变清楚。**

# 用“旅行规划”理解最容易

假设你只说：

> 我想去巴塞罗那玩几天。

你自己可能也不知道：

- 预算多少；
- 住哪里；
- 喜欢景点还是美食；
- 是想轻松还是安排得很满。

## 第一步：AI先搭一个临时工作台

AI不会立刻给你最终行程，而是生成几个区域：

```text
巴塞罗那旅行
├── 日期
├── 交通
├── 住宿
├── 景点
└── 预算
```

界面上可能出现：

- 日期选择器；
- 预算滑块；
- 酒店卡片；
- 地图；
- 景点筛选按钮。

这时，界面不是最终产品，而是一套**用来澄清需求的工具**。

---

## 第二步：你通过操作表达想法

你做了几个操作：

- 把预算滑块调低；
- 选择“民宿”；
- 点击圣家堂附近的住宿；
- 勾选“历史文化”；
- 取消“夜生活”。

你没有写一大段 Prompt。

但 AI 可以推断出：

```text
这个用户：
- 比较在意价格
- 更喜欢民宿
- 希望住在圣家堂附近
- 喜欢文化类活动
- 不太需要夜间娱乐
```

所以，你的点击本身就是一种语言。

---

## 第三步：AI不仅换内容，还会换界面

普通网页可能只是更新搜索结果。

DuetUI 会进一步思考：

> 既然用户现在重点是找文化景点和附近住宿，那么界面结构也应该变化。

于是它可能：

- 把地图放大；
- 把夜生活模块删除；
- 新增“步行距离”筛选；
- 把住宿和景点放在同一张地图上；
- 增加每日路线安排页面。

这就是它特别的地方：

> **AI不仅帮助完成任务，还会根据任务变化，重新设计你正在使用的工具。**

# 可以把系统想成两个同步更新的笔记本

DuetUI 内部一直维护两个东西。

## 笔记本一：任务笔记本

记录：

```text
用户到底要完成什么？
任务分成哪几步？
当前偏好和约束是什么？
```

例如：

```text
规划巴塞罗那旅行
├── 找住宿
│   ├── 民宿
│   ├── 低预算
│   └── 圣家堂附近
├── 找景点
│   ├── 历史文化
│   └── 步行可达
└── 生成行程
```

## 笔记本二：界面笔记本

记录：

```text
这些任务应该用什么界面来操作？
需要哪些页面？
每个页面需要什么组件？
```

例如：

```text
旅行界面
├── 住宿页面
│   ├── 预算滑块
│   ├── 民宿筛选
│   └── 地图
├── 景点页面
│   ├── 文化标签
│   └── 距离筛选
└── 行程页面
    └── 每日时间线
```

两个笔记本始终对应：

```text
任务变了 → 界面跟着变
界面被操作了 → AI对任务的理解跟着变
```

这就是论文标题中的：

> **Bidirectional Context Loop，双向上下文循环。**

---

# “双向”到底是什么意思？

因为信息在两个方向流动。

## 方向一：AI → 界面 → 用户

AI理解任务，然后生成界面给你操作。

```text
AI的理解 → 页面、按钮、卡片、滑块
```

## 方向二：用户 → 界面 → AI

你操作界面，AI通过这些操作理解你的新意图。

```text
点击、筛选、拖动 → 用户偏好 → AI更新任务
```

所以界面像一个翻译器：

```text
AI的想法被翻译成界面
用户的操作被翻译成意图
```

---

# 它和聊天机器人的区别

普通聊天机器人像是：

> 你必须不断跟它说话，把要求写清楚。

DuetUI 像是：

> AI先给你一套控制面板，你通过操作控制面板和它沟通。

例如修改预算：

普通聊天：

```text
请把住宿预算从每晚150欧元降低到100欧元，
并重新推荐圣家堂附近评分较高的民宿。
```

DuetUI：

```text
拖动预算滑块到100欧元
点击“民宿”
在地图上选中圣家堂区域
```

后者的认知负担更低。

---

# 它和普通生成式 UI 的区别

普通生成式 UI：

```text
你描述需求
→ AI生成一个网页
→ 完成
```

DuetUI：

```text
AI生成第一版界面
→ 你操作
→ AI理解变化
→ 生成第二版
→ 继续操作
→ 再调整
```

所以普通生成式 UI 更像“AI设计师交稿”。

DuetUI 更像：

> **设计师一边观察你怎么用，一边现场改工具。**

# 为什么需要多个 Agent？

可以把几个 Agent 想象成一个小团队。

### TaskAgent：项目经理

负责理解：

- 目标是什么；
- 应该拆成哪些步骤；
- 哪些任务发生了变化。

### ServiceAgent：资料员

负责找数据：

- 航班；
- 酒店；
- 商品；
- 活动；
- 预算信息。

论文原型里不少数据是模拟的。

### InterfaceAgent：交互设计师

负责决定：

- 应该有几个页面；
- 使用地图还是列表；
- 用按钮、滑块还是卡片；
- 哪些功能应该增加或删除。

### RenderingAgent：前端工程师

负责把界面描述真正渲染成可操作网页。

所以可以把系统理解成：

```text
项目经理决定做什么
资料员准备数据
设计师决定怎么操作
工程师把界面做出来
```

用户则一直在和这个团队共同工作。

---

# 它真正创新的点

不是模型更聪明，也不是用了新的神经网络。

创新在于：

> **把“用户操作界面”变成了给 AI 的反馈。**

传统 AI 很依赖用户继续输入文字。

DuetUI认为：

- 点击一个酒店，是反馈；
- 调低预算，是反馈；
- 删除一个模块，是反馈；
- 反复查看某一类结果，也是反馈。

AI应该利用这些行为，持续调整任务。

---

# 一个最简公式

你可以记住这个公式：

```text
DuetUI
=
聊天 Agent
+
动态任务面板
+
用户操作记录
+
根据操作不断重做任务和界面
```

或者更口语化一点：

> **AI先给你一个能操作的草稿；你一边使用，一边“教”AI；AI再一边理解你，一边改草稿。**

# 最后用一个比喻总结

普通聊天 AI 像一个服务员：

> 你必须把订单说清楚，它再去执行。

DuetUI 像一个和你一起逛超市的私人助理：

因此，**你不必一开始就知道自己要什么，你可以在选择过程中发现自己真正想要什么。**

# 1. 先纠正一个细微之处

DuetUI 不能完全称为 `task-step-oriented`。

它更接近：

> **Hierarchical Task-State-Oriented UI**
> 面向层级任务状态的动态界面

因为它内部主要维护的是：

```text
Task
 └── Subtask
      └── Data
```

然后映射成：

```text
Navigation
 └── Page
      └── Component
```

也就是说，它首先问的是：

> “当前任务被分成了哪些子任务？每个子任务应该对应什么页面和组件？”

用户点击、筛选和选择之后，系统更新当前子任务，再生成下一版界面。论文确实记录了人和 Agent 的 Action History，但这个历史主要被当作**推断用户意图的上下文**；它没有被建模为一个可以直接查看、修改、分支、回滚和接管的完整执行轨迹。

所以可以这样区分：

```text
DuetUI：
任务结构 → 生成界面
用户操作 → 更新任务结构 → 再生成界面

你们：
执行轨迹 → 生成统一工作空间
用户操作 → 修改轨迹的未来走向
Agent执行 → 更新轨迹状态 → 工作空间持续演化
```

---

# 2. “任务”和“轨迹”到底差在哪里？

这是你们能否与 DuetUI 拉开距离的核心。

## Task 是“应该做什么”

例如：

```text
组织一次上海出差
├── 确认日期
├── 订机票
├── 订酒店
├── 创建日历
└── 提交报销
```

这是一棵任务分解树。

DuetUI 根据它生成：

- 日期页面；
- 机票卡片；
- 酒店筛选器；
- 预算组件；
- 行程页面。

## Trajectory 是“事情实际上如何发生”

真实执行可能是：

```text
读取日历
  ↓
发现周三有冲突
  ↓
读取邮件，确认会议可以延后
  ↓
重新确定周四出发
  ↓
查询公司差旅政策
  ↓
搜索机票
  ↓
发现首选航班超预算
  ↓
请求用户在两个方案间选择
  ↓
预订航班
  ↓
酒店价格发生变化
  ↓
重新规划酒店
  ↓
修改日历
  ↓
保存发票
  ↓
填写报销系统
```

这里包含的不只是步骤，还包括：

- 当前环境状态；
- 已执行动作；
- 动作结果；
- 应用和服务之间的数据依赖；
- 分支和备选路径；
- 失败与重试；
- 不可逆操作；
- 用户审批点；
- 信息来源和证据；
- 当前承诺和未完成事项。

这才是“轨迹”。

---

# 3. 你们的核心心智模型

你们可以把系统想成：

> **Agent 在后台穿越多个应用；用户在前台操作的不是这些应用，而是任务的“数字驾驶舱”。**

传统 GUI Agent 是：

```text
用户
 ↓ 下发任务
GUI Agent
 ↓
打开 Gmail
 ↓
打开浏览器
 ↓
打开日历
 ↓
打开差旅系统
 ↓
用户盯着它点击
```

你们设想的是：

```text
              Gmail
                 ↘
用户 ↔ 统一任务工作台 ↔ Agent ↔ Calendar
                 ↗
       Browser / ERP / Slack / Files
```

用户不需要知道 Agent 当前在哪一个应用里。

用户看到的是语义层面的对象：

- “出差日期”
- “候选航班”
- “预算冲突”
- “需要审批”
- “已预订”
- “待报销”
- “来源与执行记录”

而不是：

- Gmail 第几个标签页；
- 浏览器当前打开哪个网站；
- ERP 的哪个菜单；
- Agent 刚刚点击了哪个坐标。

---

# 4. 真正的区别：应用不再是用户的交互单位

传统计算中：

```text
应用 = 交互单位
```

用户想完成一件事，需要在应用间切换。

你们的范式是：

```text
任务轨迹 = 交互单位
应用 = Agent 的执行后端
```

这是一个非常强的观点。

就像数据库出现以后，用户不再关心数据具体存在磁盘的哪个扇区；在你们的系统里，用户也不再需要关心一个操作具体由 Gmail、Chrome、Excel 还是 SAP 完成。

可以把原应用理解为：

> **被 Agent 编译和调用的执行目标，而不是人类直接面对的界面。**

---

# 5. 和 DuetUI 重合在哪里？

## 重合一：都想把界面变成人和 Agent 的共同媒介

DuetUI 的核心主张是：

> 界面不只是 Agent 的输出，而是用户与 Agent 共同操作、共同修改的共享媒介。

你们也有这个核心思想。

## 重合二：都试图弱化原有应用和服务的边界

DuetUI 明确讨论了复杂、多步骤、跨服务任务，并主张生成一个统一且连贯的任务界面，把完成任务所需的功能汇聚起来。

所以“把多个服务统一到一个生成式 UI 中”本身，不能单独作为你们的创新点。

## 重合三：用户操作都会反过来指导 Agent

DuetUI 把用户的点击、筛选、输入记录进双向 Action History，用来更新任务结构和界面。你们也希望用户在统一 UI 上的操作改变 Agent 的后续执行。

## 重合四：界面会随着任务进展而变化

两者都不是一次性生成一个固定页面，而是随着任务不断演化。

---

# 6. 真正没有完全撞车的地方

## 6.1 DuetUI 的基本状态是“任务树”

它的核心状态是：

```text
TaskStage
TaskDecomposition
InterfaceDescription
ActionHistory
```

其中 TaskDecomposition 是 task–subtask–data 三层结构，InterfaceDescription 是 navigation–page–component 三层结构。

你们需要把核心状态改成：

```text
Goal
Execution Graph
Environment State
Artifacts
Commitments
Provenance
Risk
Human Decisions
```

也就是说，你们的源数据不是“页面应该有什么”，而是：

> 整个跨应用任务目前走到了哪里，发生了什么，接下来有哪些可能路径。

---

## 6.2 DuetUI 的 Action History 不是一等交互对象

在 DuetUI 中，历史主要是 Agent 的上下文：

```text
用户选了 B&B
→ Agent 推断偏好
→ 更新住宿任务
→ 更新住宿页面
```

但用户通常不会直接操作：

- 整条轨迹；
- 轨迹分支；
- 依赖关系；
- 已执行动作；
- 未执行计划；
- 回滚边界；
- 某一步的证据；
- 某个动作的替代方案。

你们可以让这些成为界面的一部分：

```text
已完成
✓ 从日历读取可用日期
✓ 从邮件提取会议地点
✓ 检查公司差旅政策

等待决策
! 直飞航班超预算 18%

接下来
○ 选择转机航班
○ 向经理申请预算例外
○ 将行程缩短一天
```

这不是简单的 Action Log，而是：

> **可操作的轨迹表示。**

---

## 6.3 DuetUI 没有真正解决跨应用执行

DuetUI 的 ServiceAgent 在原型中大量通过 LLM 模拟外部服务，并没有完整解决真实系统里的写操作、事务、权限、部分失败和状态同步。

而你们需要处理：

- 真实 Gmail、Calendar、Slack、ERP、浏览器或本地应用；
- 权限和身份；
- 跨服务的数据传递；
- 一个服务成功、另一个失败时怎么办；
- 修改外部系统后，统一 UI 如何保持一致；
- 如何避免重复付款、重复发送、重复提交；
- 哪些操作可以回滚，哪些不可以。

这会让你们从 HCI 原型进入：

> **Cross-application agent orchestration + human interaction architecture**

这是明显更难、也更实质性的研究贡献。

---

## 6.4 DuetUI 更像逐个子任务推进

它的常见模式是：

```text
住宿子任务
→ 用户筛选
→ Agent 更新住宿数据和页面
→ 进入下一个子任务
```

你们的轨迹可能是并发、交叉和异步的：

```text
申请审批 ───────────────┐
                        ↓
查航班 → 等审批 → 预订 → 保存发票
     ↘
      同时查酒店 → 价格变化 → 重新规划

日历冲突 → 联系参会者 → 等待回复
```

这不是普通的任务树，而更像：

- DAG；
- 状态机；
- 事件流；
- 带有分支和补偿动作的工作流；
- 部分可观察的执行轨迹。

# 7. 一个特别直观的例子

用户说：

> 帮我组织下个月去上海参加客户会议的行程，预算尽量控制在公司标准内。

## DuetUI 风格

系统可能生成：

- 日期选择器；
- 航班页面；
- 酒店页面；
- 预算页面；
- 日程页面。

用户逐项选择，界面逐步变化。

## 你们的轨迹级系统

Agent 先开始执行：

1. 从邮件里找到会议时间和地点；
2. 从 Calendar 检查冲突；
3. 从公司知识库获取差旅政策；
4. 查询航班与酒店；
5. 发现用户日历有冲突；
6. 发现直飞票价超标；
7. 发现会议酒店虽然贵，但免交通费用。

前台只显示一个统一工作台：

```text

会议
4月18日 10:00
浦东新区
来源：客户确认邮件

A. 直飞，¥1,820，超标准 ¥220
B. 转机，¥1,460，多 2.5 小时
[选择 A] [选择 B] [申请预算例外]

住宿方案

附近酒店：房价更低，但需交通

执行进度
✓ 读取会议信息
✓ 检查差旅政策
✓ 查询航班和酒店

○ 更新日历

```

用户不知道背后分别打开了：

- Gmail；
- Calendar；
- 公司 Wiki；
- 携程；
- 地图；
- 报销系统。

他只在语义层面进行决策。

这就是你们最强的价值：

> 用户监督的是“任务世界”，而不是“Agent 如何操作软件世界”。

# 8. 但有一个比 DuetUI 更接近你们的工作

我需要很坦率地提醒你：截至 2026 年 3 月，有一篇名为 **Software as Content: Dynamic Applications as the Human-Agent Interaction Layer** 的预印本，与你们的上位愿景非常接近。

它提出：

- 生成的应用不是 Agent 一轮对话的输出；
- 应用是贯穿整个任务生命周期的持久交互层；
- 它跨轮次积累状态；
- 人和 Agent 都通过该应用行动；
- 应用随着用户和 Agent 的交互不断演化；
- 原始环境包括网页、API、数据库、本地文件和可执行服务。turn264220view2

它甚至明确区分了：

```text
artifact as output
vs.
artifact as medium
```

也就是：

```text
界面作为输出
vs.
界面作为人和 Agent 共同活动的媒介
```

这和你描述的“人只和 Agent 的统一界面沟通，不再盯着各个应用”高度相似。

不过，它也明确承认当前实现还不能可靠执行外部写操作，例如提交表单、修改外部系统、触发服务；它把跨系统事务一致性、部分失败和前后端状态同步列为尚未解决的核心问题。

所以真正最接近你们的不是只有 DuetUI，而是：

```text
DuetUI
+ Software as Content
+ Human-in-the-loop GUI Agents
```

交叉形成的研究区域。

# 9. 怎么把你们的贡献钉牢？

不要把论文主张写成：

> 我们让 Agent 为跨应用任务生成一个统一 UI。

因为这个叙事已经比较拥挤。

更有辨识度的主张是：

> **我们把跨应用执行轨迹建模为一等交互对象，并从实时轨迹状态生成一个持久、可干预的任务工作空间，使用户能够在语义层监督和控制 Agent，而无需观察底层应用操作。**

其中至少需要四个明确贡献。

## 贡献一：Trajectory Representation

提出一种统一轨迹模型，例如：

```text
Trajectory =
  Goal
+ States
+ Actions
+ Observations
+ Dependencies
+ Branches
+ Artifacts
+ Provenance
+ Commitments
+ Risks
+ Compensation Actions
```

DuetUI 的 task–subtask–data 不足以表达这些内容。

## 贡献二：Trajectory-to-UI Compilation

不是简单地“让 LLM 生成网页”，而是定义：

```text
当前轨迹状态
+ 用户角色
+ 风险等级
+ 待决策节点
+ 可逆性
→ 当前应该展示的界面
```

例如：

- 普通进行中步骤折叠；
- 高风险动作突出；
- 需要人类价值判断的分支生成比较 UI；
- 失败步骤生成诊断与恢复 UI；
- 不可逆操作生成审批 UI。

## 贡献三：Semantic Intervention

用户不需要说：

> 停止在 Chrome 里点击，返回上一个页面，然后选另一个航班。

用户可以说或点击：

> 不要超预算，优先保持直飞。

系统自动把这个干预传播到未来轨迹：

```text
修改约束
→ 使部分计划失效
→ 保留仍然有效的结果
→ 重新规划受影响子图
```

## 贡献四：Cross-App Execution Consistency

真正解决：

- 多应用动作的事务边界；
- 外部状态同步；
- 去重与幂等；
- 失败补偿；
- 恢复和断点续作；
- 权限与审批；
- 行为证据和来源追踪。

这会使你们不仅是一篇 GenUI 论文，也是一篇 Agent Systems + HCI 论文。

---

# 10. 建议给这个范式起一个更准确的名字

“Trajectory-oriented UI”方向是对的，但可以再突出 Agent 与统一工作空间，例如：

- **Trajectory-Oriented Generative Workspace**
- **Agent-Mediated Task Workspace**
- **Cross-App Trajectory Interface**
- **Trajectory-Centric Human-Agent Interaction**
- **Task World Interface**
- **Semantic Oversight Workspace**

我个人最推荐：

> **Trajectory-Centric Agent Workspace**

它表达了三件事：

1. 核心对象是 trajectory；
2. 用户操作的是 workspace；
3. Agent 负责跨应用执行。

一句完整的定位可以是：

> **A trajectory-centric agent workspace that compiles live cross-application execution into a persistent, semantically meaningful interface for human oversight and intervention.**

# 11. 最终判断

我的判断是：

| 层面 | 与 DuetUI 的关系 |
|---|---|
| 生成统一任务 UI | 明显重合 |
| 界面作为人—Agent 沟通媒介 | 明显重合 |
| 用户操作反向引导 Agent | 明显重合 |
| 隐藏多个服务的界面差异 | 部分重合 |
| 真实跨应用读写执行 | DuetUI 基本未解决 |
| 完整轨迹作为一等对象 | 区别明显 |
| 分支、回滚、恢复、事务 | 区别明显 |
| 轨迹级语义监督 | 区别明显 |
| 用户完全不观看原始 GUI | 是你们可以强化的独特主张 |

所以最准确的说法不是“完全没撞车”，也不是“已经被做了”，而是：

> **DuetUI 已经提出了生成式任务界面和双向反馈循环；你们可以进一步把它从“围绕任务结构共同生成 UI”，推进到“围绕真实跨应用执行轨迹共同操作一个持久工作空间”。**

真正需要警惕的近邻是 **Software as Content**。你们最有机会拉开差异的地方，恰好是它目前明确没有解决的部分：

> **真实、长程、可写、会失败的跨应用执行，以及人在统一界面上如何安全地观察、理解、干预和恢复这条轨迹。**

# 案例：帮 10 人团队安排周五晚上的团建

用户最开始只说：

> 帮我安排这周五晚上的团队活动，10 个人，预算 3000 元左右。

此时用户自己也没完全想清楚：

- 吃饭还是娱乐？
- 在哪里？
- 有人忌口吗？
- 是轻松聊天，还是更有参与感？
- 是否需要订场地？

DuetUI 不会立刻给出最终方案，而是进入逐步共同生成过程。

---

# 第一步：Define——先确认大目标

系统先生成一个非常简单的界面：

```text
团队活动规划

人数
[ 10 人 ]

日期
[ 本周五 ]

总预算
[ ¥3000 ]

活动倾向
○ 聚餐
○ 娱乐
○ 聚餐 + 娱乐
○ 还不确定

[继续]
```

用户选择：

```text
聚餐 + 娱乐
```

这次点击被记录成：

```text
User selected:
activity_type = dinner_and_entertainment
```

TaskAgent 更新任务：

```text
安排团队活动
├── 安排聚餐
└── 安排娱乐活动
```

---

# 第二步：Empathize——补充约束和偏好

系统根据当前任务，生成第二版界面：

```text

[ 请选择区域 ]

饮食限制
 素食
 清真
 不吃辣
 海鲜过敏
 暂无

团队氛围
○ 轻松聊天
○ 热闹互动
○ 有竞争性
○ 安静放松

结束时间
[ 22:00 ]
```

用户做了几个操作：

- 地点选择“徐汇区”；
- 勾选“1 人素食”；
- 选择“热闹互动”；
- 把结束时间从 22:00 调到 21:30。

系统推断：

```text
地点：上海徐汇
饮食要求：需要素食选项
活动偏好：互动性强
时间约束：不宜太晚
```

注意，用户没有专门输入：

> 请安排一个互动性强、含素食选择、最晚九点半结束的活动。

这些信息是通过界面操作表达的。

---

# 第三步：Plan——把任务拆成子任务

TaskAgent 生成任务结构：

```text
周五团队活动
├── 确定活动时间线
├── 选择聚餐地点
├── 选择娱乐活动
├── 检查交通距离
├── 控制总预算
└── 生成最终安排
```

InterfaceAgent 将它映射成一个导航界面：

```text
团建规划

[概览]
[聚餐]
[活动]
[预算]
[最终方案]
```

此时 UI 已经不再只是问卷，而变成一个任务工作台。

# 在这个过程中，四个 Agent 分别做了什么？

## TaskAgent：负责“做什么”

它持续维护：

```text
安排团建
→ 选餐厅
→ 选活动
→ 处理预算
→ 解决时间冲突
→ 输出方案
```

## ServiceAgent：负责“拿数据”

例如：

- 餐厅价格；
- 菜单和素食信息；
- 活动费用；
- 两地距离；
- 营业时间。

论文原型中，这类数据可能由 LLM 模拟，不一定是真实 API。

## InterfaceAgent：负责“怎么让用户操作”

例如，它决定什么时候生成：

- 单选按钮；
- 候选卡片；
- 预算面板；
- 时间线；
- 冲突解决选项；
- 最终确认界面。

## RenderingAgent：负责把描述变成网页

InterfaceAgent 可能输出：

```text
需要一个预算警告组件
包含四个调整方案
使用单选框
显示每个方案的最终费用
```

RenderingAgent 再将它渲染成真正可点击的 UI。

# 这个案例里，双向循环发生在哪里？

第一次：

```text
用户增加饮料套餐
↓
预算超出
↓
Agent 修改任务状态
↓
界面生成四个预算调整方案
```

第二次：

```text
用户改选桌游馆
↓
活动地点和时间改变
↓
Agent 发现时间冲突
↓
界面生成冲突解决选项
```

第三次：

```text
用户看到剩余预算
↓
提出增加甜品或饮品
↓

↓

```

所以它不是固定地按照预先写好的流程运行，而是：

> **用户每做一次有意义的操作，任务模型和界面模型都有可能重新变化。**

# DuetUI 实际做到了哪一层？

以团建为例，它真正完成的大致是：

```text
用户提出模糊目标
    ↓
DuetUI 询问并收集偏好
    ↓
生成餐厅、活动、预算等操作界面
    ↓
用户不断点击和修改
    ↓
系统逐渐形成明确的任务方案
    ↓
生成一个用户满意的最终任务 UI
```

它主要解决的是：

> **怎样通过动态 UI，让人逐渐表达清楚自己想要什么。**

而不是：

> **怎样让 Agent 在真实应用中把事情完整执行掉，并用统一 UI 向人反馈进度。**

论文虽然在概念模型中把最后一个阶段称为“Finalize and execute”，但原型评测关注的是生成出来的任务描述、页面和组件是否合理，并没有评测“是否真的订到了酒店、买到了机票或完成了外部事务”。turn245900view1

甚至论文在介绍 task-oriented UI 方向时，明确把它与“Agent 从头到尾不透明地自动执行任务”区分开来：它更强调让最终用户直接操作聚合后的功能界面。

# 给 DuetUI 最后接一个 UI Agent，可以吗？

技术上可以：

```text
DuetUI
负责澄清意图、生成最终方案
        ↓
UI Agent
打开美团、搜索、下单
```

这样系统就可能落实到真实执行。

但这时 UI Agent 更像一个**最后阶段的执行器**：

```text
人和 DuetUI 把方案商量清楚
             ↓
把最终方案交给 UI Agent 执行
```

即使 UI Agent 执行期间出了问题，例如：

- 商家已经满座；
- 价格发生变化；
- 登录过期；
- 某个套餐不可用；

DuetUI 原本的核心循环仍然不是围绕这些真实执行状态设计的。它可能需要重新询问用户，再生成一版界面，但“真实应用中的连续执行轨迹”不是它的中心对象。

# 你们的系统确实不一样

根据你现在的澄清，你们并不是在做：

> 人和生成式 UI 反复沟通，逐渐澄清或改变意图。

你们做的是：

> **用户给出相对稳定的意图，Agent 自主执行；生成式 UI 持续把真实执行状态转换成一个统一、可操作的任务界面。**

这里真正的主循环不是：

```text
DuetUI：

人操作生成式 UI
    ↓
系统理解人的新意图
    ↓
系统重新生成 UI
    ↓
人继续调整意图
```

而是：

```text
你们：

UI Agent 操作真实应用
    ↓
真实应用返回新状态
    ↓
统一 UI 根据执行状态更新
    ↓
统一 UI 向 UI Agent 提供结构化控制或约束
    ↓
UI Agent 继续执行
```

人只在必要时介入，例如：

- 确认付款；
- 授权敏感操作；
- 填写 Agent 无法获得的信息；
- 在执行失败时选择恢复方案；
- 紧急暂停或接管。

也就是说，你们的主要闭环是：

```text
UI Agent ↔ 真实应用 ↔ 执行状态 ↔ 统一 UI
```

人位于这个循环之外，或者只是作为低频的控制节点：

```text
                    人
                    ↓
UI Agent ↔ 执行状态 ↔ 统一 UI
    ↕
多个真实应用
```

# 最本质的区别：谁驱动 UI 变化？

## DuetUI：人的意图变化驱动 UI

```text
用户修改偏好
→ 任务理解改变
→ UI 改变
```

例如用户从“酒店”改为“民宿”，系统重新生成住宿界面。

它假设：

> 用户的意图是不完整且不断变化的。

## 你们：Agent 的执行状态驱动 UI

```text
Agent执行动作
→ 外部世界改变
→ 轨迹状态改变
→ UI 改变
```

例如：

```text
Agent 在美团搜索餐厅
→ 发现首选餐厅已满
→ 统一 UI 自动变成“正在寻找替代餐厅”
→ Agent继续搜索
```

用户的意图可能始终没有变化：

> 周五给十个人安排一个不超过三千元的团建。

变化的是环境和执行状态，而不是用户想法。

这是非常重要的差异。

# 你们的 UI 不是“意图形成界面”，而是“执行代理界面”

可以用下面四个词来区分。

| 维度 | DuetUI | 你们 |
|---|---|---|
| 用户意图 | 模糊、持续演化 | 相对稳定 |
| 主要行动者 | 人与 Agent 共同操作 | Agent 自主执行 |
| UI 更新依据 | 用户的直接操作 | 真实执行状态和环境反馈 |
| 外部应用 | 模拟的数据服务 | 真实执行环境 |
| 人的责任 | 持续选择、调整和塑造方案 | 少量授权、确认、异常处理 |
| 最终目标 | 形成贴合意图的任务界面 | 改变真实外部世界 |
| 核心闭环 | Human ↔ UI ↔ Agent | Agent ↔ Environment ↔ UI |
| 核心对象 | Task decomposition | Execution trajectory |

# “UI 和 UI Agent 来回反馈”该怎样准确表述？

严格来说，不应该让视觉 UI 本身承担全部状态逻辑。更合理的系统结构是：

```text
                  用户
          少量确认 / 授权 / 暂停
                    ↓
            统一生成式 UI
                    ↕
        Shared Execution State
        共享的执行状态与轨迹
                    ↕
               UI Agent
                    ↕
美团 / 微信 / 日历 / 地图 / 企业系统
```

中间的 `Shared Execution State` 很关键。

它保存的不是普通聊天历史，而是：

```text
当前目标
当前执行计划
已经完成的动作
每个动作的真实结果
当前外部应用状态
生成的文件和订单
失败与重试
待执行步骤
风险和权限
需要人确认的操作
```

于是：

### UI Agent 写入状态

```text
餐厅搜索完成
找到 8 个候选
首选餐厅不可订
自动选取第二候选
准备提交订单
```

### 生成式 UI 读取状态

然后把它渲染成用户能理解的内容：

```text
已找到备选餐厅
价格仍在预算内
距离增加 8 分钟
无需您处理
```

### UI 产生控制事件

例如用户点击：

```text
[暂停任务]
[不允许超预算]
[授权付款]
```

这些不是新的模糊自然语言意图，而是结构化控制信号，再传给 UI Agent。

因此，更准确的循环是：

```text
UI Agent
   ↕
共享执行状态
   ↕
生成式 UI
```

而不是让 UI Agent 直接解析网页界面中的任意人类点击。

# 你们甚至不一定需要频繁重新“生成”UI

这也是一个容易混淆的地方。

你们的系统不应该每执行一步就让 LLM 重新设计整个网页。否则 UI 会不断跳变，用户反而难以理解。

可以把 UI 分成两层：

## 稳定骨架

长期保持位置不变：

```text
目标
进度
当前动作
执行结果
异常
权限请求
最终产物
```

## 动态区域

根据轨迹状态生成：

```text
付款确认卡片
登录请求
验证码输入
冲突说明
失败恢复选项
生成的订单信息
```

这样它更像一个持续存在的 **Agent 执行控制台**，而不是不断重新设计的临时应用。

# 你们与 DuetUI 的关系可以这样定义

DuetUI 是：

> **Intent-centered co-generative UI**
> 以意图形成和共同塑造为中心的生成式 UI。

你们是：

> **Execution-centered agent-mediated UI**
> 以真实执行为中心、由 Agent 中介的统一 UI。

或者更突出轨迹：

> **Trajectory-grounded agent interface**
> 基于真实执行轨迹生成的 Agent 界面。

你们的核心主张不是“帮助人更好地告诉 Agent 做什么”，而是：

> **让 Agent 在多个原生应用中执行，而用户只在一个由实时轨迹生成的语义界面中观察、授权和控制任务。**

# 是否撞车？

经过你这次澄清，和 DuetUI 的核心区别已经相当明确。

重合的部分只有：

- 都生成 task-specific UI；
- 都希望消除固定应用 UI 的限制；
- 都在 Agent 和 UI 之间维护上下文；
- 都允许 UI 根据任务进展变化。

但核心研究问题不同：

```text
DuetUI：
怎样让人通过 UI 与 Agent 共同形成和调整意图？

你们：
怎样让 Agent 在真实应用中连续执行，
同时将执行轨迹编译成一个统一界面，
让人不必观看原始应用？
```

所以不能把你们简单描述成“DuetUI 后面加一个 UI Agent”。

更准确地说：

> 在 DuetUI 中，UI 是人类塑造任务的主要操作空间；
> 在你们的系统中，原应用是 Agent 的执行空间，统一 UI 是真实执行过程的语义投影与控制空间。

这个区别是本质性的，而且比“task-step 还是 trajectory”更加准确。
